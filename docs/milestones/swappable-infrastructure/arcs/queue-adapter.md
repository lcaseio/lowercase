## PR 4 - `MessageLogPort` + Redis-backed adapter - merged (#363)

### Discussion

- **A remote-only concern given the current architecture, not something today's local path needs.** `httpjson` (the primary step type) already dispatches to the worker via a direct in-process call (`JobExecutorPort`), bypassing the bus/router/queue path entirely — only `mcp` (already treated as semi-dead) still goes through the old bus-mediated route. So this adapter's real payoff is specifically for a remote worker; it doesn't unlock anything for today's local-only execution.
- **No separate event bus — resolved, not left open.** The worry going in: worker lifecycle needs to reach both the engine (to advance the run plan) and observability (durable event history for debug/replay), genuinely different consumers needing every event, not a subset. Resolved without a second messaging technology: Redis Streams' consumer-group model already gives multiple independent durable readers of the same stream — exclusivity (an entry delivered to only one consumer) is scoped to consumers _within_ one group, not across groups — so distinct concerns can each run their own consumer group on the same stream and each see everything, acking independently. Messages split across separate streams per category (commands, lifecycle events, telemetry, metrics), matching the category split `docs/component-architecture/model.md` already draws. Redis Streams is the sole carrier; there is no `EventBus` adapter in this milestone.
- **The registries already have a placeholder for this swap.** `packages/runtime/src/registries/bus.registry.ts` and `queue.registry.ts` both already declare a `redis` placement key, currently just falling back to `InMemoryEventBus`/`InMemoryQueue` regardless — the config-selection slot already exists, just unimplemented.
- **Explicitly out of scope for this PR (and this milestone's early PRs generally): swapping the bus behind the engine's own real-time state transitions** (`step.planned`/`started`/`completed`/`failed`). That bus is genuinely load-bearing today and delivers synchronously, same-process — introducing a network-mediated transport there risks real new latency/ordering questions in a system that cares about deterministic behavior, for a proof point (bus-mediated dispatch) the primary step type has already moved away from. If ever revisited, the safer version is additive — mirroring select events to a Redis Stream purely for observability's own consumer group, never gating the engine's own synchronous path — which is the same shape as the already-tracked `LifecycleEventIngress` idea (see `worker-tools-artifacts`'s "Not yet scoped"), not something to build ahead of an actual need.
- **Commissioned research on the runtime-composition/messaging design before locking in a stream shape**, since this PR is where the four-category commitment (commands, lifecycle events, telemetry, metrics) actually has to become real config and real adapter behavior, not just a stated intent. Full output: [`research/runtime-composition-strategies.md`](../research/runtime-composition-strategies.md) and its follow-up, [`research/runtime-composition-follow-up.md`](../research/runtime-composition-follow-up.md) (the latter specifically resolves the messaging shape — topology vs. publication routes vs. subscriptions as three separate concerns, retention owned once at the topology level, and consumer-group naming). PR 9 (below) is where the resulting config vocabulary actually lands; this PR needs it mainly to know what the adapter itself has to support (per-category streams — see below for why the engine's result-reading doesn't need a stream of its own yet).
- **Commands don't ride the same passive-publication path as the other three categories.** A command is an authoritative request that makes a component act, not an observed fact — publishing it to Redis alongside also invoking it directly would create two live delivery paths for the same actionable thing, risking a job executing twice. So command delivery lives under the job-execution _binding_ (`bindings.jobExecution`, `direct` vs. `redis-streams`) rather than a generic publication switch. `commands` is still a real stream in the shared Redis topology — the distinction is who's allowed to treat it as authoritative (only the worker's ingress consumer group), not whether it exists.
- **A job result is conceptually not a lifecycle event, even though the first version deliberately doesn't act on that distinction yet.** Worth recording the conflict this surfaced: the four-category list never named replies, while `docs/component-architecture/model.md` categorizes a reply/result separately and the Worker V2 plan says explicitly `JobResult` is the caller's control-flow answer, not a lifecycle event. A job result is a correlated, one-recipient reply the engine's own forward progress depends on (closer to a function's return value than a broadcast fact any number of independent consumer groups might read on their own schedule), which is a different kind of thing from a durable historical fact observability reads independently.
- **Decided anyway: collapse onto one lifecycle stream for the first version, engine included as its own dedicated consumer group.** No separate `protocolStreams.jobExecutionResults` channel gets built yet. The engine reads the same lifecycle stream as observability, under its own consumer group, and correlates entries to its own pending calls itself. This defers the real cost the conceptual distinction above is about — coupling the engine's control flow to whatever operational policy (retention, throughput, other attached consumers) the shared lifecycle stream ends up needing for unrelated reasons — but that cost only actually bites once there's more than one engine replica or a real external lifecycle consumer, and today there's neither. Revisit if either shows up.
- **When the multi-engine-replica problem does need solving, prefer durable shared state over reply-routing.** The research's own follow-up flagged an unsolved piece of the (now-deferred) private-channel design: once there's more than one engine replica, a correlated reply needs to reach the specific replica holding the matching pending call — solved there via things like per-instance reply streams or partitioned reply routing. The preferred direction here is different: keep run/step state durable and externally readable (e.g. in SQL), so _any_ engine replica can pick up a job's outcome and continue working on it, rather than a reply needing to find its way back to the one replica that originally issued the command. Don't reach for per-replica streams or consumer-group proliferation as the default solution later — treat durable shared state as the first thing to try.
- **The worker's `job.<capability>.completed`/`failed` lifecycle event gets slimmed down as part of this work regardless of the above, not left as-is.** Today it carries the full result payload inline — already flagged in `CLAUDE.md` as a known rough edge, and confirmed here to be exactly that: a relic of not having anywhere else to put the result yet, not a deliberate design. Event payloads should stay small — carrying an entire response body inside a public fact stream is bad hygiene on its own, independent of whether the engine also reads it. So the event narrows to what a lifecycle fact actually needs (job id, status, timing, and whatever reference the engine needs to locate real outputs — e.g. an artifact hash — not the output content itself), and the engine reads that same trimmed event via its own consumer group rather than a separate channel.
- **Redis Streams is not just replacing `QueuePort` — it's the eventual replacement for `EventBusPort` too, and that second one is genuinely load-bearing today, unlike the queue.** `QueuePort` (`InMemoryQueue`, `NodeRouter`) is nearly dead — only the semi-dead `mcp` path still uses it — so retiring it is low-risk, and it's heading for retirement alongside the router itself. `EventBusPort` is different: observability taps it directly for its own sinks, and the engine's own reducer/planner/effect loop is driven by events read off the bus — a deliberate "event-driven" design stance from earlier in the project that's since fallen out of favor in principle, but the engine hasn't been refactored to drop the dependency yet (per `CLAUDE.md`'s "keep engine changes incremental unless a larger rewrite is explicitly intended"). `httpjson`'s move to direct in-process invocation only replaced the worker's own dispatch path — the core+inbound/outbound-port structure that made that possible has so far only been built for the worker, not any other component. So most of the system still runs on `EventBusPort` as its only inter-component transport, and this PR's port design needs to not foreclose eventually backing that role too, even though actually wiring it there stays out of scope for this milestone (same reasoning as the bullet above on the engine's synchronous-ish bus dependency).
- **`EventBusPort`'s actual semantics, confirmed by reading `InMemoryEventBus`: fire-and-forget, not durable.** `publish()` defers delivery via `queueMicrotask` and returns without waiting for subscriber completion; `subscribe()`'s handler isn't awaited or caught, so an async handler's rejection currently goes unhandled — a separate, pre-existing gap, not something this milestone touches. There's no persistence, retry, or delivery guarantee today. This matters for any future `EventBusPort` retrofit onto Redis Streams: the change wouldn't be "synchronous becomes asynchronous" (it's already asynchronous, just in-process and lossy) — it would be trading unordered, best-effort, no-persistence delivery for a durable, ordered, ack/retry-bearing transport with real network latency. That's a materially bigger behavioral shift than a transport swap, and another reason it isn't something to attempt inside this milestone.
- **A concrete prerequisite for ever doing that `EventBusPort` retrofit: the worker's lifecycle events are currently thrown away, not captured.** `createConsoleWorkerLifecycleEventSink()` is an explicit placeholder (its own code comment says so) — it `console.log`s and nothing else, where the worker previously published real events onto the bus that both observability and the engine consumed. Already planned, separately from this milestone: giving the worker — and, by the same reasoning, any other component the observer cares about — a real durable sink is one of the next component refactors to the core+inbound/outbound-port structure now being applied project-wide. Not part of this PR; recorded here because it's a real, load-bearing dependency for the `EventBusPort` question above, not a hypothetical one.
- **The port itself is settled: `MessageLogPort`, deliberately not a Redis-specific or "Streams" name.** What Redis Streams (and Kafka, NATS JetStream, RabbitMQ Streams) actually provide as a category of infrastructure is a durable, ordered, replayable log of discrete messages that independent consumer groups can each read at their own pace — not a byte/chunk transport, which is a different primitive this project already has a real name for. "Streams" specifically was ruled out: it's already spoken for by `packages/ports/src/stream.port.ts`'s `StreamPort`/`ConsumerStreamPort`/`ProducerStreamPort` — a real, working, hand-built mechanism from an early version of this project that let one step's output stream directly to another in-process, deliberately shelved (not abandoned) to cut scope while the workflow engine itself got built, kept intentionally intact as an archive piece worth revisiting long-term. Reusing "Stream" for this Redis-backed port would collide with that already-real meaning. `MessageLogPort`'s own name may still shift later alongside a broader event→message rename already under consideration project-wide; not a blocker now.
- **Method surface, and why `start()`/`health()` aren't on it.** `publish`, `readGroup`, `ack`, `claimPending`, `ensureStream`, `ensureConsumerGroup`, `close()`. Provisioning (`ensureStream`/`ensureConsumerGroup`) is part of the port, not pushed to a separate concern — creating a stream/group is genuinely backend-specific mechanics (`XGROUP CREATE ... MKSTREAM`, handling `BUSYGROUP` on a group that already exists), even though _whether_ to create (`createIfMissing`) stays a config decision made by the caller, not the port. No `start()`/`health()`: checked precedent across every port in `packages/ports` — passive store-shaped ports (`ArtifactStorePort`, `QueuePort`, `EventStorePort`, the `Run*`/`Flow*`/`Sim*` repositories) carry no lifecycle methods at all, relying entirely on external `ManagedResource` wrapping; long-running component-shaped ports (`RouterPort`, `EnginePort`, `LimiterPort`, `ObservabilitySinkPort`/`Tap`) bake `start()`/`stop()` in because they're actual self-driven components. `EventBusPort` and `StreamPort` sit in a third bucket — `close()` only, no `start()` — and that's the shape `MessageLogPort` matches: not inert storage, but not a self-driven component either.
- **Payload type: `AnyEvent`, matching `EventBusPort`'s own precedent, not a generic `publish<M>()`.** One shared envelope is the actual plan — every message this port ever carries (command, lifecycle fact, telemetry, metric) rides the existing `CloudEvent<T>`-based type system, distinguished by a new `kind` field to be added alongside the already-established per-type `domain`/`action`/`entity` fields on `CloudEvent<T>` (pulled from `EventMap[T]`, the same mechanism, purely additive — `type` stays exactly what it already is, the specific dotted event name, not repurposed into a coarse category). That `kind` field isn't part of this PR — it's only needed once command/telemetry/metric message types actually get modeled, likely PR 9 or later — but the port's typing decision assumes it's coming rather than staying generic and deciding later.
- **Redis client: `node-redis` (the official client, npm package `redis`), not `ioredis`.** Redis itself has deprecated its earlier recommendation of `ioredis` in favor of `node-redis` — new features land there first, TypeScript support is built in, and it covers every Stream command needed (`xAdd`, `xReadGroup`, `xAck`, `xClaim`/`xAutoClaim`, `xGroupCreate`). `ioredis`'s real edge — Cluster/Sentinel ergonomics, heavy pipelining — doesn't apply to this milestone's single-Redis-instance scope.
- **Tentative, not settled: idempotency-against-redelivery probably doesn't belong in `MessageLogPort` at all, even as a per-adapter-implemented contract.** Surfaced while reviewing the Redis adapter's use of `xAdd`'s auto-generated entry id (unrelated to any application-level id inside the payload) and whether Redis 8.6+'s `IDMPAUTO`/`IDMP` options could help. Reasoning so far, offered as a thing to think through more rigorously later rather than a conclusion: rejecting a Redis-native dedup mechanism because Kafka/NATS/an in-memory implementation wouldn't have an equivalent is the easy, vendor-neutrality argument — but there's a sharper reason underneath it. The `direct` job-execution binding never touches `MessageLogPort` at all, and has no redelivery mechanism to protect against in the first place (nothing claims or re-delivers a plain in-process call). So "publish is idempotent given a key" would be a guarantee meaningful only for the `redis-streams` binding, not something every implementation of this port could honor in a way that means anything — structurally different from `ensureStream`/`ensureConsumerGroup`, which every real implementation needs regardless of binding. If that reasoning holds, idempotency-against-redelivery belongs one level up, at whoever actually executes a command checking durable state before acting — which is already named, in different words, in the follow-up research doc's note on command consumers needing "idempotent job execution plus duplicate suppression at the terminal write." Not acted on here; flagged so it isn't lost, and to be revisited with more rigor once a real `redis-streams` job-execution binding is actually being built (PR 7 or 9).
- **Testing: real-Redis integration tests as the primary proof, not mocks — narrow unit tests only for any pure logic factored out with no connection involved.** The entire point of this adapter is proving Redis's actual distributed semantics (consumer-group delivery, ack, pending-entry ownership); a mocked client would just replay assumptions about that behavior, hiding exactly the bugs this PR exists to catch — same reasoning PR 1 already applied against real MinIO. `claimPending` specifically needs a deliberate two-consumer scenario, not just a call that doesn't throw: consumer A reads via `readGroup` and doesn't ack (simulating a crash mid-processing); after a short `minIdleMs` window, consumer B calls `claimPending`; assert B receives the message, B can `ack` it, and a fresh `readGroup` for new entries does not return it again. That last assertion is what actually proves ownership transferred through Redis's real pending-entries mechanism, rather than the message being silently duplicated or lost.

### What actually landed

Matches the settled design above on every structural point — `MessageLogPort` in `packages/ports/src/message-log/`, `RedisMessageLog` in `packages/adapters/src/message-log/` against `node-redis` 6.2.1, no wiring into `packages/runtime`, nothing touching `QueuePort`/`EventBusPort`/`NodeRouter` — with several things found or decided only once this got built and reviewed, not just planned:

- **`node-redis`'s reply types needed one explicit inline type annotation `tsc` couldn't infer on its own** — `readGroup`'s `.flatMap`/`.map` callback silently hit an implicit-`any` several layers into the library's own generic reply-mapping machinery, fixed by annotating the callback parameter directly rather than fighting the library's types. Confirmed, not assumed, that the annotation is actually faithful to runtime behavior: read `node-redis`'s own `RESP/types.d.ts` directly and confirmed `MapReply<K,V>`'s default resolved type (no custom `TYPE_MAPPING`) is a plain `Record<string, string>`, even though `createClient()` defaults to RESP3 — so `decodeEntry`'s `JSON.parse`-based decode needed no RESP-version branching.
- **Testing ended up as 4 integration tests (real Redis) plus 1 mocked unit test, not integration-only as originally planned.** The integration suite (provisioning idempotency, publish/read round-trip, ack removing pending state, and the `claimPending` recovery scenario — two consumers, one abandons a read, the other claims and acks it, a fresh read never returns it again) covers everything reachable against a real backend. Review surfaced one branch it structurally can't reach: `ensureStream`/`ensureConsumerGroup` swallowing `BUSYGROUP` as idempotent success only ever gets its swallow path exercised for real; forcing a _different_ `xGroupCreate` failure deterministically against real Redis isn't practical, so that path got one small mocked-client unit test instead — not a parallel suite duplicating the integration coverage, just the one gap.
- **Test env-var handling grew into its own small piece of infra, triggered directly by this PR growing the var count.** Added `.env.test.local`/`.env.test.local.example`, split cleanly from the real `.env`/`.env.example` (which stays `DATABASE_URL`-only, matching Prisma's actual usage), loaded via a new vitest `setupFiles` entry (`packages/adapters/tests/setup-env.ts`) using the same explicit `dotenv.config()` pattern `packages/db-prisma` already uses elsewhere in the repo — not a new convention. Applied retroactively to the existing S3 integration test too, not just Redis, so both now load from one file; verified by running the full integration suite with zero inline/exported vars and confirming both suites picked values up from the file and passed.
- **The `docker-compose.yml`/CI project name changed from `lowercase` to `lowercase-test`** — a repeat ask from PR 3's review, done now — so these containers can't get mixed up with any future non-test docker infra. Old `lowercase-*` containers torn down before the rename rather than left orphaned.
- **Two design questions surfaced during review, resolved differently than first assumed:**
  - Whether `RedisMessageLog` should lean on Redis 8.6+'s `IDMPAUTO`/`IDMP` idempotent-add options for dedup: no — not just because other backends lack an equivalent, but because the `direct` job-execution binding never touches `MessageLogPort` at all and has no redelivery mechanism to protect against in the first place, so an idempotency guarantee at the port level wouldn't be meaningful for every binding that could exist. Recorded above as tentative, not settled — a placement question to revisit with more rigor once a real `redis-streams` binding is actually being built.
  - Whether `MessageLogPort`'s methods should return `DomainError<Code>` (matching `ArtifactStorePort`): no, but not for the reason first given (no HTTP-facing boundary) — `DomainError` isn't scoped to HTTP boundaries at all, it's a general convention applied wherever a structured, closed-union error code helps. The actually-correct reason: none of this port's operations have a genuinely distinguishable _expected_ failure mode to standardize on — its one real error path (`BUSYGROUP`) is already swallowed internally, and everything else (e.g. `NOGROUP` from calling `readGroup` before `ensureConsumerGroup`) represents a caller violating this port's own ordering contract, not a normal outcome to branch on gracefully.
- **Verified**: `packages/ports`/`packages/adapters` typecheck clean individually; full workspace `build` (27 tasks), `typecheck` (26 tasks), and `test` (26 tasks) all pass; the integration suite runs green against a real `docker compose up -d minio redis` with zero inline env vars, purely via `.env.test.local`.

## PRs 5–9 — from one PR to five

What PR 4's discussion originally scoped as one PR ("extend `local-system` with a `redis-streams` messaging branch") turned out, once actually strategized, to be five smaller, mostly-independent pieces — expected, not a sign anything went wrong: every PR ordering here is a best-effort guess at the time it's made, and the milestone's own "Evolution" section already documents this happening once before (the original CAS single-PR plan becoming PRs 1–3). Two cross-cutting conclusions came out of that strategy pass before the per-PR breakdown below:

- **A full `EventBusPort` retirement is not this milestone's next step, and doesn't need to be.** Mapped every real consumer first (`packages/events`' `EmitterFactory`, the engine, observability's tap, the limiter, replay, the already-fully-migrated worker) before concluding this. Most of that surface stays untouched — what actually needs to move for a real remote worker is much narrower than "retire the bus," and is exactly PRs 6–8 below.
- **The engine's own step/run self-loop is a real, separate bug — correct to fix, but deliberately deferred, not part of PRs 5–9.** Eight of the engine's twelve `EventBusPort` subscriptions (`step.planned`/`started`/`reused`/`completed`/`failed`, `run.started`/`completed`/`failed`) exist purely so the engine can react to events it just published itself, to advance its own internal reducer queue — a same-process round-trip through the bus for communication that never actually leaves the process. The corresponding effect handlers (`emitStepPlannedFx`, `emitRunStartedFx`, etc.) currently only publish and rely on that subscription loop-back; `executeHttpJsonJobFx` already shows the fix (enqueue internally *and* publish externally, from one build, no subscription needed). Applying that pattern to the other eight would shrink the engine's real `EventBusPort` dependency from 12 subscriptions to 2 genuinely external ones (`run.requested`, `replay.mode.submitted`). Checked against every PR below and it's genuinely decoupled from all of them — nothing here depends on it, and it doesn't ease anything here either, since the self-loop never touches `MessageLogPort`/Redis at all. Deferred to whenever the engine gets its real core/inbound-outbound refactor; tracked in `MILESTONE.md`'s "Not yet scoped" so it isn't lost.

## PR 5 - Delete `NodeRouter`/`QueuePort` - not started

### Discussion

- **Confirmed fully dead, not just bypassed for `httpjson` — deleting outright, not migrating.** Grepped the whole repo (including `packages/archive`) for any caller of `QueuePort`'s `reserve`/`dequeue`/`peek`: none exist. The comment in `node.router.ts` warning about "a still-running legacy consumer" is stale — that consumer is already gone. Consequence worth naming: `mcp` steps don't just have doubted reliability (as previously recorded) — they're currently unreachable at runtime, full stop. A job enqueued via the router's `mcp` path is never dequeued by anything, so the engine's `job.mcp.completed`/`.failed` subscriptions never fire and the step hangs forever. Deliberately not being fixed as part of this — `mcp` has been intentionally inert since it was never implemented in the worker, not a regression this PR causes or needs to address.
- Also removes a problem that looked real earlier in this discussion: Redis Streams has no wildcard topic matching, which only mattered because of `NodeRouter`'s `"job.*.submitted"` wildcard subscribe. Deleting the router instead of porting it makes that gap moot rather than something to solve.

## PR 6 - `JobExecutorPort` envelope-fidelity fix - not started

### Discussion

- **Local only — no Redis, no `MessageLogPort` — but a prerequisite for PR 7, not a stylistic cleanup.** Building a Redis adapter against the current, already-wrong contract would mean redoing it once this fix lands anyway.
- **Surfaced a real, pre-existing bug while scoping the remote dispatch adapter, not a remote-readiness question: `JobExecutorPort`'s input has already lost envelope fidelity, today, locally.** In `stepPlannedPlanner.ts` (`packages/components/engine/src/planners/step-planned.planner.ts:100-162`), `EmitJobHttpJsonSubmittedFx` (the real `job.httpjson.submitted` CloudEvent envelope, published for observability) and `ExecuteHttpJsonJobFx.request` (the bespoke `JobExecutionRequest` actually passed to `JobExecutorPort.execute()`) are built side by side from the same step data — but as two independently-constructed objects, down to each generating its **own random `jobId`** that doesn't correlate with the other's. The comment there already flags this as "a small, known, accepted divergence." It isn't small: it means the thing observability records and the thing actually dispatched aren't even the same job identity, and it happened silently because local execution never had to prove envelope fidelity — observability was already being fed by a separate publish, so nobody noticed the executor's input drifting into its own bespoke shape.
- **Fix: build the canonical envelope once per submission, and have both the dispatch call and whatever records it work from that same object** — the same "build once, use twice" shape `executeHttpJsonJobFx` already uses correctly on the *completion* side (one event, used for both the internal `enqueue` and the external `publishEvent`). `JobExecutorPort.execute()`'s input moves from the bespoke `JobExecutionRequest` to (or a strict, identity-preserving derivation of) the real envelope. This was always the intent for how message envelopes were meant to work across the system — CloudEvent-shaped messages as the one canonical wire-and-record format, whether a job runs locally or remotely — it just went unenforced locally because nothing forced the question until a real wire format (Redis) made the divergence visible.
- `LocalWorkerJobExecutor` needs updating to translate from the envelope-shaped input instead of today's `JobExecutionRequest` — a contained change to one existing adapter (already in the translation business) plus the port and one planner, not a sprawling rewrite.

## PR 7 - Redis-backed `JobExecutorPort` adapter (engine ↔ worker dispatch) - not started

### Discussion

- **Depends on PR 6 landing first** — this adapter is built against the envelope-shaped contract PR 6 introduces, not today's `JobExecutionRequest`.
- **A Redis-backed adapter behind the existing `JobExecutorPort`, not a new port.** `JobExecutorPort.execute(request) → outcome` already has the right shape for a remote round-trip (request in, correlated result out) — a `RemoteWorkerJobExecutor` implementing it can do a publish-then-await-response round-trip over `MessageLogPort` internally, the same way `LocalWorkerJobExecutor` does an in-process call internally. This also means the engine→worker leg of the once-floated "translation bridge" idea isn't needed at all: dispatch already has a real seam (`JobExecutorPort`) that both a local and a remote adapter can sit behind, so there's no separate bus-to-Redis translator to build for this direction.
- **One Redis publish serves double duty instead of two, because of PR 6's fix.** With a shared canonical envelope, this adapter publishes the submission once; the worker's own consumer group reads it to execute, and observability's separate consumer group (once it can read `MessageLogPort` directly) reads the same entry to record it — the identical multi-consumer-group reasoning PR 4 already established for the lifecycle/completion direction, just applying to submission too, rather than needing two independent publishes per job.
- This is the first PR in this arc that actually exercises `MessageLogPort` for something live, beyond PR 4's own tests.

## PR 8 - Worker lifecycle sink (Redis-backed) + temporary lifecycle bridge - not started

### Discussion

- **Depends on PR 4 (`MessageLogPort`/`RedisMessageLog`, already merged) but not on PRs 5–7** — could in principle land in parallel with 6/7, not strictly after them.
- **What's actually left needing a translation piece, once dispatch is covered by PR 7: worker lifecycle/telemetry, one direction only, Redis → local bus.** Not a general or bidirectional bus↔Redis translator — job submission and completion are both already covered by the `JobExecutorPort` adapter, so the only traffic left outside that request/response shape is lifecycle facts that aren't part of it (heartbeats, progress — not job outcomes). This is exactly the previously-unscoped `LifecycleEventIngress` gap named in `MILESTONE.md`.
- Replaces the `console.log`-only placeholder sink (`console-worker-lifecycle-event-sink.adapter.ts`) with one that publishes onto `MessageLogPort`. A small, temporary bridge component reads that stream via its own consumer group and republishes onto the existing local `EventBusPort`, so every current bus consumer (mainly observability) keeps working completely unchanged.
- **Explicitly framed as throwaway compatibility code, not incremental progress toward the end-state architecture** — it should get thinner over time as components migrate to consuming `MessageLogPort` directly (starting with observability, once it has a real durable sink), not stay as a permanent piece.
- **Idempotency/redelivery: deliberately deferred here too — but the gap doesn't fully disappear, it relocates, and that's worth recording precisely.** "Robust" handling at the `MessageLogPort`-consumption layer (correct `ack`/`claimPending`, no dropped entries) is a different guarantee from "no duplicate side effects downstream." A crash in the bridge between republishing onto the bus and acking the Redis entry causes a redelivery on restart — and a second republish onto the bus. Whether that matters depends on whether the real terminal write (e.g. an observability sink keyed by `event.id`) already tolerates a duplicate; that isn't verified today. Decision: acceptable to leave unresolved for now, for the bridge and other legacy/unmigrated components, consistent with deferring `EventBusPort` retirement generally — the worker itself, as the one component already being built against the new core+inbound/outbound pattern, should attempt to get this right where practical, since it's cheaper to build correctly now than retrofit later. Idempotency work should get built lazily, per-consumer, exactly when a component migrates to real `MessageLogPort` consumption — not centralized or built ahead of an actual need.

## PR 9 - Extend `local-system`'s `jobExecution` binding with a `redis-streams` branch - not started

### Discussion

- **Depends on PRs 6–8.** This is where everything above actually gets exercised end-to-end, not before.
- **Not a new profile — `local-system` keeps the worker in-process, just with a real Redis backend underneath the `jobExecution` binding.** `bindings.jobExecution: direct | redis-streams` (already anticipated in PR 4's discussion and in `cas-adapter.md`'s PR 2 binding-validity bullet). The engine ends up depending on both Redis (for the job executor leg) and the standard bus (for everything else) at once — not a departure from today, since it already depends on the bus for everything; this just gives one leg a live Redis-backed option.

Not a hypothetical: an embedded component using network infrastructure (Redis included) while everything stays in one process is an explicitly named, valid runtime shape in the research doc, not an edge case being accommodated reluctantly.
