# Prove Swappable Infrastructure Milestone — Arc: Queue Adapter (PRs 4–5)

**Previous:** [`cas-adapter.md`](./cas-adapter.md) (PRs 1–3) · **Next:** [`sql-adapter.md`](./sql-adapter.md) (PRs 6–7)

Part of the [`MILESTONE.md`](../MILESTONE.md) PR log, split out to keep that doc scannable. Builds a Redis Streams adapter for job dispatch, replacing `InMemoryQueue`, and wires it into `packages/runtime`'s config selection. Also settles what would otherwise have been a separate "event bus" decision — see below.

## PR 4 - Redis Streams adapter (queue) - not started

### Discussion

- **A remote-only concern given the current architecture, not something today's local path needs.** `httpjson` (the primary step type) already dispatches to the worker via a direct in-process call (`JobExecutorPort`), bypassing the bus/router/queue path entirely — only `mcp` (already treated as semi-dead) still goes through the old bus-mediated route. So this adapter's real payoff is specifically for a remote worker; it doesn't unlock anything for today's local-only execution.
- **No separate event bus — resolved, not left open.** The worry going in: worker lifecycle needs to reach both the engine (to advance the run plan) and observability (durable event history for debug/replay), genuinely different consumers needing every event, not a subset. Resolved without a second messaging technology: Redis Streams' consumer-group model already gives multiple independent durable readers of the same stream — exclusivity (an entry delivered to only one consumer) is scoped to consumers _within_ one group, not across groups — so distinct concerns can each run their own consumer group on the same stream and each see everything, acking independently. Messages split across separate streams per category (commands, lifecycle events, telemetry, metrics), matching the category split `docs/component-architecture/model.md` already draws. Redis Streams is the sole carrier; there is no `EventBus` adapter in this milestone.
- **The registries already have a placeholder for this swap.** `packages/runtime/src/registries/bus.registry.ts` and `queue.registry.ts` both already declare a `redis` placement key, currently just falling back to `InMemoryEventBus`/`InMemoryQueue` regardless — the config-selection slot already exists, just unimplemented.
- **Explicitly out of scope for this PR (and this milestone's early PRs generally): swapping the bus behind the engine's own real-time state transitions** (`step.planned`/`started`/`completed`/`failed`). That bus is genuinely load-bearing today and delivers synchronously, same-process — introducing a network-mediated transport there risks real new latency/ordering questions in a system that cares about deterministic behavior, for a proof point (bus-mediated dispatch) the primary step type has already moved away from. If ever revisited, the safer version is additive — mirroring select events to a Redis Stream purely for observability's own consumer group, never gating the engine's own synchronous path — which is the same shape as the already-tracked `LifecycleEventIngress` idea (see `worker-tools-artifacts`'s "Not yet scoped"), not something to build ahead of an actual need.
- **Commissioned research on the runtime-composition/messaging design before locking in a stream shape**, since this PR is where the four-category commitment (commands, lifecycle events, telemetry, metrics) actually has to become real config and real adapter behavior, not just a stated intent. Full output: [`research/runtime-composition-strategies.md`](../research/runtime-composition-strategies.md) and its follow-up, [`research/runtime-composition-follow-up.md`](../research/runtime-composition-follow-up.md) (the latter specifically resolves the messaging shape — topology vs. publication routes vs. subscriptions as three separate concerns, retention owned once at the topology level, and consumer-group naming). PR 5 (below) is where the resulting config vocabulary actually lands; this PR needs it mainly to know what the adapter itself has to support (per-category streams — see below for why the engine's result-reading doesn't need a stream of its own yet).
- **Commands don't ride the same passive-publication path as the other three categories.** A command is an authoritative request that makes a component act, not an observed fact — publishing it to Redis alongside also invoking it directly would create two live delivery paths for the same actionable thing, risking a job executing twice. So command delivery lives under the job-execution _binding_ (`bindings.jobExecution`, `direct` vs. `redis-streams`) rather than a generic publication switch. `commands` is still a real stream in the shared Redis topology — the distinction is who's allowed to treat it as authoritative (only the worker's ingress consumer group), not whether it exists.
- **A job result is conceptually not a lifecycle event, even though the first version deliberately doesn't act on that distinction yet.** Worth recording the conflict this surfaced: the four-category list never named replies, while `docs/component-architecture/model.md` categorizes a reply/result separately and the Worker V2 plan says explicitly `JobResult` is the caller's control-flow answer, not a lifecycle event. A job result is a correlated, one-recipient reply the engine's own forward progress depends on (closer to a function's return value than a broadcast fact any number of independent consumer groups might read on their own schedule), which is a different kind of thing from a durable historical fact observability reads independently.
- **Decided anyway: collapse onto one lifecycle stream for the first version, engine included as its own dedicated consumer group.** No separate `protocolStreams.jobExecutionResults` channel gets built yet. The engine reads the same lifecycle stream as observability, under its own consumer group, and correlates entries to its own pending calls itself. This defers the real cost the conceptual distinction above is about — coupling the engine's control flow to whatever operational policy (retention, throughput, other attached consumers) the shared lifecycle stream ends up needing for unrelated reasons — but that cost only actually bites once there's more than one engine replica or a real external lifecycle consumer, and today there's neither. Revisit if either shows up.
- **When the multi-engine-replica problem does need solving, prefer durable shared state over reply-routing.** The research's own follow-up flagged an unsolved piece of the (now-deferred) private-channel design: once there's more than one engine replica, a correlated reply needs to reach the specific replica holding the matching pending call — solved there via things like per-instance reply streams or partitioned reply routing. The preferred direction here is different: keep run/step state durable and externally readable (e.g. in SQL), so _any_ engine replica can pick up a job's outcome and continue working on it, rather than a reply needing to find its way back to the one replica that originally issued the command. Don't reach for per-replica streams or consumer-group proliferation as the default solution later — treat durable shared state as the first thing to try.
- **The worker's `job.<capability>.completed`/`failed` lifecycle event gets slimmed down as part of this work regardless of the above, not left as-is.** Today it carries the full result payload inline — already flagged in `CLAUDE.md` as a known rough edge, and confirmed here to be exactly that: a relic of not having anywhere else to put the result yet, not a deliberate design. Event payloads should stay small — carrying an entire response body inside a public fact stream is bad hygiene on its own, independent of whether the engine also reads it. So the event narrows to what a lifecycle fact actually needs (job id, status, timing, and whatever reference the engine needs to locate real outputs — e.g. an artifact hash — not the output content itself), and the engine reads that same trimmed event via its own consumer group rather than a separate channel.

## PR 5 - Extend the `local-system` profile with the `redis-streams` messaging branch - not started

### Discussion

- Expected to be a comparatively mechanical repeat of PR 3's config-selection pattern, applied to the queue/messaging port — but with one real difference in shape from CAS/SQL, worth deciding deliberately rather than copying the pattern blind. Local FS vs. MinIO, and SQLite vs. Postgres, are both genuinely permanent choices — someone might legitimately run this locally forever and never want the "remote" backend. Queue/messaging isn't the same: once local truly becomes direct in-process calls (per Worker V2's own direction, already true for `httpjson` today), an in-memory queue/bus isn't a permanent sibling option to Redis Streams, it's not really infra at all once local stops paying for the abstraction. So this config axis is more honestly "single process, direct calls" vs. "distributed, Redis Streams" than an N-way backend selector — worth keeping that framing explicit rather than modeling it as a third interchangeable "in-memory" backend choice like the other two ports.
- Not "wire a new profile" — adds a real `redis-streams` branch to `local-system`'s existing `messaging` config field (see `cas-adapter.md`'s PR 3), which today only has one legal value. `apps/http-server` and `apps/cli` both pick it up automatically once it lands, no separate retrofit needed.
