## PR 1 - S3-compatible CAS adapter (MinIO-backed) + local/CI scaffolding - merged (#360)

Picked as this milestone's starting adapter — `ArtifactStorePort`'s surface (`getBytes`/`putBytes`, content-addressed) is the narrowest of the three candidate ports and already hardened by the `worker-tools-artifacts` refactor, making it the lowest-risk way to prove the pattern before tackling the queue or SQL.

### Discussion

- **Built against the standard S3 API, not MinIO-specific.** Using `@aws-sdk/client-s3` means the adapter talks the actual S3 HTTP API; MinIO differs only in client configuration (a custom `endpoint`, `forcePathStyle: true`, MinIO access/secret keys instead of AWS IAM creds), not in the calls themselves (`PutObject`/`GetObject`, maybe `HeadObject`). Since the store is already content-addressed (sha256 owned client-side), it has no reason to depend on provider-specific quirks like S3 ETag semantics, which is one of the few places real AWS S3 and MinIO diverge at the edges. Named `S3ArtifactStore`, not `MinioArtifactStore`, accordingly — the same adapter should work unmodified against real AWS S3, Cloudflare R2, Backblaze B2, Garage, or SeaweedFS later, just by changing endpoint/credentials.
- **MinIO chosen over Garage/SeaweedFS** (both real, more-permissively-licensed S3-compatible alternatives) — MinIO is the most standard, best-documented self-hosted option, and since the adapter isn't MinIO-specific, switching later would mean almost no code changes anyway.
- **Scope deliberately includes local/CI scaffolding in this same PR, not a separate infra-only PR beforehand.** An infra-only PR (a compose file + a CI services block, no adapter code) has nothing real to validate itself against; a real integration test that actually puts/gets a blob against a live MinIO container proves both pieces together. This PR is where the "how do integration tests find a real backend, locally vs. in CI" pattern gets established — a `docker-compose.yml` service, env-var-gated integration tests, a GitHub Actions `services:` block (native support — MinIO/Redis/Postgres are all common as GH Actions service containers, not a big ask) — for the later adapters (Redis, Postgres) to reuse rather than reinvent.
- **Secrets**: plain gitignored env vars for MinIO credentials. Real secret management stays deferred, matching the same call already made when `worker-tools-artifacts` punted secrets to a future milestone.
- **Object keys are flat (`hash`), not sharded by prefix.** `FsArtifactStore` shards (`hash.slice(0,2)/hash.slice(2,4)/hash.slice(4)`) because filesystems need it; S3/MinIO don't have the same directory-fanout problem. Only add sharding back if it actually causes a problem for some backend down the line — not preemptively.
- **`S3ArtifactStore` takes an injected `S3Client` + bucket name, not config it builds internally.** All MinIO-specific setup (`endpoint`, `forcePathStyle: true`, MinIO credentials vs. AWS IAM) stays in whatever constructs the client (`packages/runtime`, or a test), keeping the adapter itself backend-agnostic per the S3-not-MinIO-specific decision above, and making it trivial to point at a real MinIO container in integration tests or a mocked client in unit tests.
- **Content-type is native object metadata** (`PutObjectCommand`/`GetObjectCommand`'s `ContentType`), not a `.meta.json` sidecar like the FS adapter needs — a genuine simplification, not just parity.
- **Buffer in, buffer out, matching the port's existing contract** — no streaming. `PutObjectCommand`'s `Body` takes a `Uint8Array` directly; reads use the SDK's built-in `res.Body.transformToByteArray()` rather than manual stream consumption. Revisit only if artifact size ever makes whole-buffer I/O a real problem — that would be a port-level change, not an S3-adapter-only one.
- **A pre-write existence check (`HeadObjectCommand` before `PutObjectCommand`) is optional, not required for correctness.** Content-addressing already guarantees same hash → same bytes, so a blind overwrite is always a no-op; the only reason to check first is to skip a redundant network write. (`FsArtifactStore` already does this check today, for the same optimization reason — nothing to retrofit there.)
- **`ArtifactStorePort.getBytes()` is being widened as part of this PR, not deferred.** Today it returns `T | null`, collapsing "not found" and "read failed for some other reason" into the same `null` — `FsArtifactStore` fail-closes on everything (missing file, missing sidecar, permission error, corrupt JSON) into that one `null`. Since this PR introduces the port's second real implementation, now is the right time to distinguish them rather than revisit both adapters again shortly after. `ArtifactReader.load()` (`packages/artifacts/src/artifact-reader.ts`) is the port's only production consumer, and `ArtifactLoadError` already has an unused `cause?: string` slot ready for this — a new `code` (e.g. `"STORE_ERROR"`) added to its existing union, populated from the store's read failure, is the natural landing spot. One real behavioral call this forces: content present with a missing/corrupt sidecar is today treated as "not found" — under the widened result that's arguably a store error instead, and needs deciding deliberately rather than preserved by accident. `FsArtifactStore` needs its catch blocks (both the primary sidecar read and the legacy-extension fallback loop) rewritten to distinguish `ENOENT` from other thrown errors instead of blanket-catching.
- **New shared error shape adopted for this widening: `DomainError<Code>`.** Surveyed the codebase for existing error-shape conventions and found two already-mature but divergent ones — `ArtifactLoadError`-style (`{code (closed union), message, cause?: string}`) and the worker's `JobExecutionError`-style (`{code (closed union), message, retryable: boolean}`). Rather than add a third shape, consolidating on a shared base:
  ```ts
  export type DomainError<Code extends string> = {
    code: Code;
    message: string;
    cause?: string;
  };
  ```
  `cause` stays a `string` (not `unknown`/`Error`) deliberately — several of these error shapes eventually thread toward HTTP response types, and a string serializes cleanly with no boundary-conversion step. `retryable` isn't part of the shared base (most domain errors have no retry semantics); the worker's type becomes `DomainError<JobExecutionErrorCode> & { retryable: boolean }` on top of it instead of a fully separate shape. Lives in `packages/types` since both `packages/ports` and `packages/components/worker` need it. This does **not** touch the much larger, separate inconsistency of bare-string `Result<X, string>` used across most of `packages/app-services`/`packages/ports`/the HTTP API types — that's real debt but a much bigger migration, deliberately out of scope here. No dedicated ADR for this — the type is meant to document itself at the use site.
- **Contract tests, established here for reuse by later adapters.** No port in this codebase currently has more than one real implementation, so there's no existing shared/parameterized port-contract-test pattern to follow — every adapter test today imports its one concrete class directly. This is the first port getting a second real implementation, so it's a natural place to introduce `runArtifactStoreContractTests(factory: () => ArtifactStorePort)`, parameterized over `FsArtifactStore`, `S3ArtifactStore`, and the existing `createFakeArtifactStorePort()` test fake — reusing the real assertions already in `put-bytes.test.ts`/`get-bytes.test.ts` plus new cases for the widened 3-way `getBytes` result. PRs 3 and 5 (Redis, Postgres) should reuse this pattern rather than hand-writing disconnected test files again.

### What actually landed

Matches the design above on every structural point — flat keys, injected `S3Client`+bucket, native content-type, buffer in/out, no pre-write check, `DomainError<Code>` — with a few things sharpened or added along the way:

- **`getBytes()` ended up fully `Result`-wrapped, not `T | null` plus a bolted-on code.** `ArtifactStorePort.getBytes()` now returns `Promise<Result<ArtifactStoreGetSuccess, ArtifactStoreGetError>>` (both types finalized as `Get`-prefixed, matching the port's own `getBytes`/`putBytes` vocabulary, not the `Read`-prefixed names floated mid-design) — `null` is gone from the port entirely, not left alongside a widened error union. `ArtifactLoadError` was consolidated onto `DomainError<Code>` too, picking up `STORE_ERROR` in its union so `ArtifactReader.load()` forwards `stored.error` straight through with no mapping step.
- **`FsArtifactStore.getBytes()` rewritten as planned**, splitting the old single `Promise.all` catch into sequential content-then-meta reads so `ENOENT` (→ legacy fallback) is distinguishable from a real error (→ `STORE_ERROR`) — including the missing-sidecar case, which now correctly surfaces as `STORE_ERROR` instead of silently `NOT_FOUND`.
- **Contract suite deliberately does _not_ include the fake**, reversing what's sketched above — a later discussion (see `docs/todo.md`'s "should a unit test's fake be a real reimplementation" entry) concluded that running a fake through the _full_ contract would force it to grow real logic to pass, defeating the point of keeping it thin. Suite covers `FsArtifactStore` and `S3ArtifactStore` only.
- **Added beyond the original plan: `s3-artifact-store.test.ts`**, a always-running, mocked-`S3Client` unit test (via `aws-sdk-client-mock`) covering the `STORE_ERROR`/`cause` mapping the contract suite can't easily trigger against real MinIO without deliberately breaking the connection.
- **MinIO image: `bitnamilegacy/minio`, not `bitnami/minio`.** Discovered mid-build — Bitnami moved its free-tier images to a separate `bitnamilegacy` namespace in 2025; the plain `bitnami/minio:latest` tag no longer resolves. Still the right image choice otherwise (runs correctly from env vars alone, no command override needed — what the official `minio/minio` image would require and GitHub Actions' `services:` block has no field to supply).
- **Local dev tooling, not originally scoped**: root `pnpm test:integration` (`docker compose up -d --wait` + fixed local MinIO creds, then `turbo run test:integration`), scoped to just the infra-gated test file via a `.contract.integration.test.ts` filename convention (composing two independent axes — "uses the shared contract suite" and "needs real infra" — so `test:integration` targets only the second without re-running the rest of a package's unit suite). Needed one non-obvious fix: Turborepo 2.x strips undeclared env vars from tasks by default, so the `S3_TEST_*` vars had to be explicitly listed under the task's own `env` in `turbo.json`, or the integration test silently skipped even with MinIO running.
- **Verified against live MinIO, not just typechecked** — full contract suite (round-trip, `NOT_FOUND`, idempotency) run against a real `docker compose`-started container, both from a cold start (image pull + healthcheck wait) and already-running, confirming `docker compose up -d --wait` is a correct no-op either way.

## PR 2 - Wire the CAS adapter into `packages/runtime` config - not started

### Discussion

- **This is where the actual config-selection mechanism gets designed, not just a second hardcoded option.** `CLAUDE.md` already flags `packages/runtime` as unfinished — `createServices()`/`createRuntime()` are "two separate/incomplete wiring paths," with a single, unified config-driven creation system as the stated (not yet built) direction. This PR is likely where that consolidation actually has to happen, since it's the first time more than one real backend per port exists to choose between.
- Expected to be the heaviest of this milestone's three "wire runtime" steps — the equivalent PRs for the queue (PR 4) and SQL (PR 6) should be comparatively mechanical repeats of whatever pattern this one establishes. If either of those turns out to need real new design too, that's a sign this PR didn't actually generalize.
