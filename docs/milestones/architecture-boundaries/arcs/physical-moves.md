## PR 2 - Physical package moves - in progress

### Discussion

- **The clean moves are fully mechanical, already verified**: `packages/flow-analysis`, `packages/json-ref-binder` → `packages/functional-core/*`; `packages/engine`, `packages/worker`, `packages/limiter`, `packages/observability` → `packages/components/*`. Zero import-statement changes anywhere — every cross-package import already goes through `@lcase/<name>`, never a relative path — and npm package names stay as-is. One new `pnpm-workspace.yaml` glob line per subfolder, mirroring the existing `packages/use-cases/*` pattern.
- **`NodeRouter` isn't a `git mv` — it's a new package.** It's just two files (`node.router.ts`, `index.ts`) living inside `packages/adapters/src/router/` today, not a standalone package, so extracting it means scaffolding a real new package from scratch. Settled: name `@lcase/router`, home `packages/components/router`. Re-verified rather than assumed that its only construction site is `packages/runtime/src/runtime.ts:116` (inside `makeRuntimeContext()`) — and confirmed, correcting an earlier read, that `create-services.ts` (the `apps/http-server`/`apps/cli` path) isn't a separate consumer that misses `NodeRouter`: it calls `makeRuntimeContext()` itself, so both wiring paths already funnel through the same construction site. Also found while grepping: `@lcase/events` is used in `packages/adapters/src` *only* by `node.router.ts` — once the router moves out, that dependency becomes dead weight in `packages/adapters/package.json` too.
- **What `NodeRouter` actually does, mechanically**: subscribes to `job.*.submitted`, unconditionally requeues as `job.<capid>.queued` onto the `QueuePort`. No real routing logic (no capability-based rules, no conditionals) — it exists mainly so the engine's step-dispatch is observable on the bus before/while it's queued, not because it makes decisions. Discussed and set aside as future, not this PR's scope: whether `NodeRouter` survives as its own component long-term, or whether the engine could push into queues directly (worker still needs queue infra regardless; the only reason not to have the engine do this itself today is losing that observability step). A separate idea — evolving it into a durable-queue admission/concurrency-control point for run requests — was raised and set aside as overlapping with `packages/limiter`'s existing job, not a `NodeRouter` concern.
- **General package-granularity rule worked out during this arc, not just applied to `NodeRouter`**: a components-tier package boundary isn't a bloat-avoidance decision, it's the tier's own membership test (independently meaningful on the bus, real port, candidate to run standalone — already established in PR 1) restated at the packaging level. Bundling components together would contradict that test, not just be a missed optimization, so "don't split until it hurts" (the right rule for further-splitting something like `adapters`, where no such claim exists) doesn't apply to whether components get their own packages in the first place. Grounded empirically: `worker`/`limiter`/`observability` have zero consumers outside `runtime` today, `engine` has one real consumer plus a dead `@lcase/adapters` dependency (folded into PR 4) — confirming there's no *build-cache* reason to split, while confirming there's no tree-shaking safety net to fall back on either (`tsc` has no dead-code elimination; only `apps/desktop`, via Vite/Rollup, bundles at all — `apps/http-server`/`apps/cli`, the shape any future standalone `apps/engine`/`apps/worker` would likely follow, don't and likely never will). Net: package boundaries are the only real lever for "engine extracts without dragging Prisma/MCP-SDK/siblings along," permanently, for that deployment shape — which is why splitting components now is correct even with today's single-consumer reality.
- **Bus wildcard-routing rules, tangential but worth a paper trail**: `InMemoryEventBus` does publish-side pattern expansion (`generatePatterns()`) plus exact-match subscribe — the inverse of how a real broker (NATS subjects, RabbitMQ topic exchanges, Redis `PSUBSCRIBE`) typically does it, and those rules live only in that one adapter, not on `EventBusPort`. Not part of this PR's scope; captured in `docs/todo.md` for whenever a second bus adapter is actually built.
