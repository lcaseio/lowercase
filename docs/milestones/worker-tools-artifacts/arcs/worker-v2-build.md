## PR 2 - Worker V2 core contract + fake collaborators, no runtime wiring - in progress

### Discussion

**Naming pass done for Phase 1's vocabulary, following the existing `Port`-suffix convention** (checked directly: every real port in `packages/ports/src` is `*.port.ts`, and none double-prefix with an owning-entity name — the owning context comes from the file's package/folder location, not the type name itself):

- `JobExecutionPort` — the inbound port (`execute()`); `WorkerDispatchPort` — the engine's outbound counterpart (Phase 4). Both stay colocated in their owning component's own package per the plan's Illustrative File Shape, so neither needs a `Worker`/`Engine` prefix restated in the type name. Settled as a general pattern: entity + behavior + `Port` (`Job`+`Execution`, `Worker`+`Dispatch`, `Resource`+`Permit` below), only reconsidering a prefix if a port is ever promoted into the shared, flat `packages/ports` package.
- `ExecuteJobCommand`/`JobResult`/`JobExecutionOptions` — confirmed as-is. `ExecuteJobCommand` matches the existing `EngineMessage`/`*Msg` command-union pattern the engine's own reducers already use (`packages/components/engine/src/engine.types.ts`).
- **`ResourceAdmission` renamed to `ResourcePermitPort`; `AdmissionRequest`/`AdmissionGrant` to `PermitRequest`/`PermitGrant`.** "Admission" read as more institutional and less clearly conditional than "Permit." "Permit" also matches the vocabulary `review-results.md` already nudged limiter's own future coordinator toward (`PermitGrant`, `PermitDecisionSink`) — using it now means a real Phase 7 coordinator can slot in behind this same port later without a rename. "Resource" is kept as-is, deliberately the plan's own paired term against "Worker" in its "Two Different Limits" split (worker capacity vs. resource capacity) — the pairing is what disambiguates an otherwise generic word, not the word alone.
- **`WorkerLifecycleEventSink` confirmed fine, with one mechanical difference from this codebase's existing `EventSink` (`packages/ports/src/observability/observability-sink.port.ts`) worth keeping in mind during implementation.** The existing one is a generic bus-fed fanout target (`handle(event: AnyEvent)`, its own `start`/`stop`, attached via `ObservabilityTapPort`); Worker V2's is a direct-call outbound port for one component's own facts (`record(event: WorkerLifecycleEvent)`, no attach/detach, no bus involvement at all). Don't implement `WorkerLifecycleEventSink` as if it must satisfy the real `EventSink` interface — it can't and isn't meant to. Renaming the existing `EventSink` to `ObservabilityEventSink` for disambiguation is logged separately in `docs/todo.md`, not part of this PR.
- **No new artifact port invented — Worker V2 depends on the existing `ArtifactsPort` directly.** A narrow, write-only worker-scoped port was considered first, but checked against `worker.ts`'s actual current usage: `bindValueRefs` (`worker.ts:440`) genuinely reads via `getTextArtifact`/`getMarkdownArtifact`/`getJsonArtifact` for reference resolution, not just writing outputs/exports — so write-only was the wrong shape. `ArtifactsPort` already sits at the correct tier (interface only, zero I/O); its own bloat is real but separate, already-flagged future work (this milestone's own "Not yet scoped": `packages/artifacts`' infra-vs-application-component boundary) — its per-format methods (`putJson`/`getJson`/etc.) are expected to eventually collapse toward one generic, format-agnostic put/get. Inventing a new port shape now risks needing a redo once that happens; revisit then, not before.
- **`ProtocolExecutor`/`WorkerProtocolDeps` confirmed as-is.** Deliberately not reusing today's `ToolBinding`/`ToolInstancePort` vocabulary (`packages/ports/src/tools/tool-instance.port.ts`) — `ToolBinding` is registration/factory machinery being deleted outright (no registry in the target design), and `ToolInstancePort.invoke(event: unknown)` is event-coupled (takes/returns a `ToolEvent`), which `ProtocolExecutor` must explicitly not be. "Executor" continues the same thread as `JobExecutionPort`/`ExecuteJobCommand` rather than either old word, carrying none of the old registration/event-coupling baggage forward on purpose.

Naming is expected to get a further look once these types exist as real code — settled well enough to build against, not necessarily final once seen on the page.

**Scope checked against precedent, not resized**: matches the plan's own "First Useful Pull Request" sizing (types + inbound port + fake collaborators + focused tests, no runtime wiring, no changes to the current worker) and the same additive shape `events-refactor` PR 1 already used successfully.

Starting reference: [Worker V2 plan — Phase 1](../../../component-architecture/worker-v2/README.md#phase-1-core-contract-and-tests), whose own "First Useful Pull Request" section sketches this PR's scope closely.

### What actually landed

Built additively under `packages/components/worker/src/v2/` and `tests/v2/`, matching the plan closely — `job.contracts.ts` (`ExecuteJobCommand`/`JobResult`/`JobExecutionOptions`/`ArtifactRef`/`ProtocolRequest`), `worker-lifecycle.events.ts` (the `WorkerLifecycleEvent` union, keyed on `kind` not `type`, plus factory functions), the three ports (`job-execution.port.ts`, `resource-permit.port.ts`, `worker-event-sink.port.ts`), `protocol/protocol-executor.types.ts`, and `worker.ts`'s `WorkerV2`/`createWorkerV2`. One additive line in `src/index.ts` (`export * from "./v2/index.js";`), `worker.ts` and every existing `tests/*.test.ts` untouched.

`WorkerV2.execute()` reads as a flat sequence — validate → (pre-abort short-circuit) → record started → resolve refs (minimal, `artifacts.getJson` only, result intentionally unbound for Phase 1) → run the protocol → check its result → store outputs → check that result → record completed/failed → return — with `lifecycle.record()` calls kept exclusively in `execute()` itself, never inside a helper. The permit-acquire/protocol-invoke/permit-release sequence and its cancellation classification were factored out into `#runProtocol`/`#runProtocolWithPermit`: the inner method does acquire → invoke → release-in-`finally`, and the outer method classifies any resulting rejection by `signal?.aborted` (not error identity, since no adapter in this codebase shares a canonical `AbortError`) into a typed `ProtocolRunOutcome` (`{kind: "result"}` or `{kind: "cancelled"}`) that `execute()` pattern-matches on — collapsing what were originally two separate, near-identical `try/catch` blocks in `execute()` into one shared classification point. Output/export storage was similarly factored into `#storeExecutionOutputs`, returning a typed outcome rather than touching lifecycle itself. `failedResult`/`completedResult` join the existing `cancelledResult` as the three `JobResult`-construction sites.

`tests/v2/worker.test.ts` covers all 5 required scenarios plus two additional ones added during review — 10 tests total: success; expected (resolved, not thrown) protocol failure; two dedicated output-storage cases (`OUTPUT_STORE_FAILED`, and `EXPORT_VALIDATION_FAILED` while still retaining the already-stored primary output); thrown invariant failure; cancellation mid-permit-wait; and guaranteed-permit-release across four sub-cases (acquire itself failing, success, resolved protocol failure, and a thrown protocol error). All against hand-written fakes (`tests/v2/helpers/`) satisfying the real port interfaces with no `as unknown as X` casts, matching `packages/events/tests/helpers/mock-bus.ts`'s bar. `tests/v2/architecture.test.ts` mechanically enforces the exit condition (no `EventBusPort`/`QueuePort`/`EmitterFactoryPort`/`AnyEvent` import anywhere under `src/v2/`) rather than relying on discipline alone.

**Deltas from the plan, all concrete and worth remembering:**

- The architecture test's first pass checked _all_ source text for the four banned identifiers, not just imports — it produced a false positive on `worker-lifecycle.events.ts`'s own doc comment, which deliberately _names_ `AnyEvent` to explain why `WorkerLifecycleEvent` isn't compatible with it. Fixed by scanning only `import` lines, not full file text — a doc comment is allowed to mention a banned identifier while explaining a deliberate divergence from it; only a real import counts as a dependency.
- `tests/v2/helpers/fake-artifacts.ts`'s `ArtifactsPort.get()` (and the per-format `getJson`/`getText`/`getMarkdown`/`getBytes`/`getAuto` methods) needed several internal `as` casts to bridge a TS limitation: a stored entry's `format` and `value` genuinely correlate at runtime (written together as one `ArtifactPutInput` union member), but TS can't see that correlation once both are read back off a widened `Map` value. Same category of internal cast already accepted in `events-refactor`'s core (`emit.ts`'s correlated-generic-indexed-access casts) — correct by construction, confined to the fake's own read site, not load-bearing production logic.
- The original two-`try/catch` structure in `execute()` (one around permit acquisition, one around protocol invocation) was consolidated into one shared `try/catch` during review, once it was clear both blocks were classifying rejections identically — reduced duplicated cancellation-handling logic without changing behavior (re-verified against all test scenarios). Later factored further into `#runProtocol`/`#runProtocolWithPermit` as part of a broader pass moving orchestration detail out of `execute()` into named private methods, keeping only `lifecycle.record()` calls in `execute()` itself.

A naming question surfaced during review, resolved in favor of keeping `JobExecutionPort` as named rather than switching to something like `WorkerPort`: this codebase has two real, coexisting conventions for how an implementing class relates to its port's name — a dominant one where they share a root (`Worker`/`WorkerPort`, `Artifacts`/`ArtifactsPort`, `RunService`/`RunServicePort`, ~30 examples, always a single canonical implementer), and a second, equally real one for capability-shaped ports with swappable implementations, where they deliberately don't (`InMemoryQueue`/`QueuePort`, `FsArtifactStore`/`ArtifactStorePort`, `InMemoryEventBus`/`EventBusPort`). `JobExecutionPort` belongs to the second group by name (capability-first, not provider-first) even though Phase 1 only has one real implementer — the concrete, checked reason it can't simply be `WorkerPort` right now is that the name is already taken by old `worker.ts`'s own `WorkerPort` (`start`/`stop`/`stopAllJobWaiters`, the unrelated component-lifecycle shell), which stays alive and untouched through this PR. Once Phase 5 deletes the old worker and that name frees up, renaming `JobExecutionPort` to `WorkerPort` (keeping the port name stable, letting the implementer version — `WorkerV2`, eventually maybe just `Worker` again — vary) becomes a real, available option worth revisiting then, not a decision forced now.

Verified: `pnpm typecheck && pnpm vitest run` inside `packages/components/worker` (31/31 tests pass, including the 21 pre-existing old-worker tests, unchanged); `pnpm -w turbo run typecheck` (26/26 tasks pass) confirms the `index.ts` addition doesn't break any downstream consumer. `tests/` isn't covered by the package's own `pnpm typecheck` (the same pre-existing gap `docs/todo.md` already tracks, and this milestone's own "Not yet scoped" repo-hygiene item for this package) — verified separately, twice (after the initial build and again after the later refactor), with a temporary, uncommitted `tsconfig.typecheck.json`-style config to confirm the test files themselves are type-sound, then discarded rather than committed (that hygiene fix stays out of scope for this PR, per the milestone's own note).
