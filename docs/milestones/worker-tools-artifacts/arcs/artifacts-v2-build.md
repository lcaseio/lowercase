## PR 8 - Artifacts read side (`load()`) + legacy migration - in progress

### Discussion

**Scope narrowed explicitly, twice.** This PR is the read side (`load()`) only — not a sweep of every remaining legacy consumer. And within the read side, only the worker gets migrated onto it; engine's effects, `ArtifactService`, and the HTTP routes all stay on `Artifacts`/`ArtifactsPort` for now. Full legacy migration is later work, not this PR's job.

**A new reader port, mirroring `ArtifactWriterPort`'s shape but narrower — only `ArtifactStorePort`, no repository dependency.** Confirmed against worker's actual read call sites (`#resolveOneRef`, `worker.ts:322-346`): it never touches metadata, only content — `text/plain`/`text/markdown` via `getText`/`getMarkdown`, everything else via `getJson` + a JSON-path resolve. Matches the capability-modules research's read/write asymmetry finding exactly.

**`load()` needs two calling modes, both real, not one replacing the other.** A caller that already knows the expected type (worker, always) wants confirmation — decode to the exact shape asked for, fail if the stored contentType doesn't actually match (the "confirmed" behavior named as a requirement back in PR 7). A caller that doesn't know the type up front (the real `getAuto()` successor — future workbench/`ArtifactService` consumers, not this PR) wants inference from whatever contentType is actually stored, handed back alongside the decoded value.

**A real naming collision surfaced designing the auto-mode return shape, caught before writing any code.** Forcing the auto case through the same generic `Result<T, E>` used by the confirming overloads means `T` becomes `{ contentType, value }` — nested one level inside `Result`'s own `value`, producing `result.value.value` to reach content and `result.value.contentType` beside it. `value` doesn't hold up as a name across both cases: it works when the content is the entire payload, breaks once the payload needs to travel with a sibling field. Fix: the auto-mode overload gets its own literal success shape (`{ ok: true; contentType: string; value: ... }`, siblings, no nesting) instead of routing through the shared `Result<T, E>` alias; the confirming overloads keep plain `Result<T, ArtifactLoadError>` as-is.

**Combined reader+writer dependency for the worker: nested, not flat.** `{ reader: ArtifactReaderPort; writer: ArtifactWriterPort }` — the two existing capability modules bundled as fields, no new delegating facade class to keep in sync. Chosen over a flat `{ save(), load() }` single interface specifically to keep the reader/writer distinction (different port dependencies, from the capability-modules research) visible rather than blurred behind one object. Combined port named `ArtifactAccessPort` — picked without strong conviction (no better name surfaced), open to revisiting once it's been lived with a while.

**A real compatibility gap surfaced while planning, before any code was written.** Run params and flow defs are still written exclusively through the legacy path (`ArtifactService.put`/`write`, `run-flow`'s `add-flow.ts`/`create-fork-spec.ts`'s `putJson` — confirmed by grep), i.e. `LegacyFsArtifactStore`'s extensioned files, not the new `FsArtifactStore`'s sidecar format. Moving the worker's reads fully onto the new reader as planned would have broken `ref.scope === "params"` resolution (`NOT_FOUND`), since nothing writes params into the new format yet. Resolved by widening `FsArtifactStore.getBytes()` with a legacy-format fallback probe — symmetric to PR 7's own reverse-direction fix on `LegacyFsArtifactStore`, deriving `contentType` from whichever legacy extension matched. Chosen over the alternative of splitting the worker's reads by ref scope (params staying on the legacy `ArtifactsPort`, only steps/exports moving to the new reader), which would have partly undone this PR's own goal of one combined dependency. Small, temporary, precedented duplication — removed once legacy writers eventually migrate onto `ArtifactWriterPort`.

**Where a `load()` failure surfaces, deliberately left as-is, not decided as "correct."** Checked what actually exists today rather than assumed: `packages/artifacts` has zero HTTP/Fastify references and zero bus/`EmitterFactory` references — translation to an HTTP status or an observable event is exclusively ever done by a consumer, never inside the domain package itself. But the existing consumer-side precedent is weaker than it looks — `apps/http-server` routes today pick a flat 400/500 by call site with no `error.code` switch, and some routes (`get-artifact.ts`, `get-run-detail.ts`) don't set a status at all on failure; this is the same general gap already logged in `docs/todo.md` from PR 7, not solved here. For worker specifically: an artifact-read failure already flows through an existing, working path — `#resolveRefs` wraps it into worker's own `INPUT_RESOLUTION_FAILED` code, which reaches `#finishFailedExecution` → `lifecycle.record(makeJobExecutionFailedEvent(...))`, an existing `WorkerLifecycleEvent`. This PR reuses that path unchanged for `load()`'s errors rather than inventing new plumbing. Explicitly not settled, and flagged as genuinely unknown rather than a deferred-but-obvious answer: whether a failed artifact load is actually well-described as a "lifecycle event" at all, versus some other category not yet named. Revisit later, once the broader error-handling/observability convention work happens.

### What actually landed

Built matching the plan closely. `ArtifactReaderPort` (`packages/ports/src/artifacts/artifact-reader.port.ts`) — the two-mode `load()` (auto-inferring vs. confirming, per the discussion above) plus `AutoLoadResult`/`ArtifactLoadError` (`NOT_FOUND`/`TYPE_MISMATCH`/`DECODING_FAILED`) — and `ArtifactAccessPort` (`{ reader, writer }`) as plain compositions. `ArtifactReader` (`packages/artifacts/src/v2/artifact-reader.ts`) built fresh, structurally symmetric to `ArtifactWriter`'s `encodeContent`/`decodeContent` split.

`FsArtifactStore.getBytes()` widened with the agreed legacy-format fallback probe (`getLegacyBytes`, a small local extension→contentType map, tried only after the sidecar-based lookup fails) — verified both directions with dedicated tests (`legacy-fallback-read.test.ts`) and confirmed live (below).

Worker migrated: `WorkerDeps.artifacts`/`writer` collapsed into one `artifacts: ArtifactAccessPort` field; the two output-storage call sites switch to `this.#deps.artifacts.writer`. `execution-output-storage.ts` itself needed no changes — it already took `writer: ArtifactWriterPort` directly. `create-worker.ts` and `runtime.ts` updated the same way, with `runtime.ts` now constructing one shared `FsArtifactStore` instance for both the reader and writer.

**`#resolveOneRef` simplified after the initial migration, not just ported mechanically.** The first pass mirrored the old code's shape verbatim — four near-identical branches (params/steps × text/plain/text/markdown) each calling `reader.load()` with a literal contentType, falling through to a fifth default JSON branch. Once `load()` actually existed, the real duplication became visible: the four branches differed only in _which field_ supplied the contentType (`ref.paramType` vs. `ref.exportType`), not in what they did with it. Collapsed to one contentType lookup (`(ref.scope === "params" ? ref.paramType : ref.exportType) ?? "application/json"`) followed by a single JSON/text split — JSON applies `resolveJsonPath`, text returns the decoded string directly, matching the old code's behavior exactly (verified by the existing suite plus the two new ref-resolution tests, unchanged). This is the simplification the combined port was meant to enable, made concrete rather than left as an aspiration.

**A real, pre-existing test-coverage gap got closed, not just carried forward.** Every existing `worker.test.ts` case used an empty `refs` array, so `#resolveOneRef`'s actual reader calls had never been exercised by any test — the same category of blind spot that let PR 7's real production bug through. Added two new tests (a `params`-scope `text/plain` ref and a `steps`-scope JSON ref, both resolved through a seeded fake reader into the materialized request) closing that gap for the new code, not just migrating the old fakes mechanically.

**Live end-to-end verification, deliberately repeating the same kind of check that caught PR 7's real bug.** Built a two-step httpjson flow against `httpbin.org` (`getUser` reads a `params`-scope ref, exports a value; `echoAgain` reads a `steps`-scope ref off that export) and ran it through a live `apps/http-server`. First attempt failed on an unrelated mistake (wrong export JSON path, not a code defect — httpbin's response shape has no `.body` wrapper). Second run completed successfully end to end: confirmed via the file layout on disk that the param was genuinely written through the legacy path (`.txt` extension) and reached the worker only via `FsArtifactStore`'s new legacy-fallback probe, while the export chained between steps through the ordinary new-writer/new-reader path unchanged from PR 7.

Full repo `build`/`typecheck`/`test`/`lint` green throughout (27/27 build, 26/26 typecheck, 26/26 test tasks, 26/26 lint).

**Explicitly not done, unchanged from the plan:** every other legacy consumer (engine effects, `ArtifactService`, HTTP routes) still uses `Artifacts`/`ArtifactsPort` — later work.
