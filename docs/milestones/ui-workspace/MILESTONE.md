# Flow-Version Workspace UI Rework

## Summary

This is the direction doc for the ongoing rework of `apps/web-app` away from a page-navigation web app toward a flow-version-centric workspace: drill into one flow version, and work with it entirely through panels/tabs for whichever mode you're in (Edit, View, Run, Run History, Sims, Artifacts, Evals) — rather than navigating to separate top-level pages for runs/sims/artifacts/evals that all have to be manually cross-referenced by id.

Not everything below is equally fleshed out. The point of writing it now is to capture the parts that _are_ settled (so they don't need re-deriving later) and name the parts that aren't (so they read as open, not forgotten). This doesn't map to a single GitHub Milestone or version bump — each concrete chunk below is its own small, closeable unit; this doc is the throughline connecting them.

**The design pivoted partway through, on purpose — worth naming rather than quietly editing away.** This milestone started out as a "Flow-Version Workspace" idea: one flow version as the primary context, with modes (Edit/View/Run/...) inside it. Actually building the Explorer/dockview arc (PRs 1 onward) settled into something related but different: a dockview panel/tree shell where _you_ arrange your own workspace — multiple panels, any versions/runs/sims side by side, not one fixed per-version mode at a time. "Workspace" survived the pivot, but the reason it fits changed. The doc's title stays as originally written, on purpose, matching this doc's own habit of recording deltas rather than rewriting history to look like it was always this way.

The core problem the original page-based UI had, still the actual motivation: nearly everything lived at the "list all runs / list all sims / list all artifacts" level, globally, with no real organizing entity underneath it. The rework's actual daily unit of work is _one specific flow version_, drilled into via panels/tabs inside one persistent shell — not separate top-level pages.

Longer-term context worth keeping in view even though it's not being built yet: the eventual target runtime is Electron (not just a browser tab), with real multi-pane coexistence (view + edit + preview at once, like an IDE) rather than one panel at a time, and an explicit non-goal of supporting small/phone-sized screens. Also an explicit constraint: this UI is being hand-designed and understood, not generated wholesale by an AI/design tool in one shot, the same ownership stance as the rest of this codebase.

## Current state

- The routing shell: `/spike/:flowId/:versionId/<mode>` via `FlowVersionWorkspace` (real flow-version fetch) + `FlowVersionModeNav`, replacing the old flat `Spike.tsx` prototype — this is the older, page-based tier that the Explorer arc (below) is progressively superseding, not the primary surface anymore.
- **Explorer arc** — the primary surface now: a `/explorer` page with a real-data Flow → Version tree, `dockview-react` as the tab/panel host (open/close/switch/drag-and-drop, true multi-instance), a Postman-style right-rail with Parameters/Run Input/Simulate/Problems/Step Details/Step Results/Settings tabs, Runs/Sims/Artifacts lists in the tree (each opening its own Flow Graph or artifact panel), an EventGraph singleton panel, custom flow-graph node types for all five step types, and replay of a completed run's event history. See the PR index below for the full build history.
- **Sims mode** — fully built (pre-Explorer, its own PR sequence) and since migrated into the Explorer tree (PR 15/18). Full design narrative in [`sims-mode.md`](./sims-mode.md).
- **Artifacts mode** — fully built (pre-Explorer, its own PR sequence) and since migrated into the Explorer tree (PRs 21–24). Full design narrative in [`artifacts-mode.md`](./artifacts-mode.md). Payoff still not fully cashed in: the curated/associated artifact set is meant to replace the fully-unfiltered global artifact list some pickers still draw from in places — tracked in `docs/todo.md`.
- Panel state (params, run selection, side-panel tab, layout direction, viewport, replay state, etc.) survives switching between tabs, in-app navigation away and back, and a real reload — via a keyed Redux slice per panel kind, persisted to `sessionStorage`/`localStorage`. See [`research/state-management.md`](./research/state-management.md) for the full reasoning trail and `docs/adr/0004-panel-state-management-and-persistence.md` for the distilled decision.
- **Evals** — deliberately its own separate milestone now, not a section of this one. See `docs/milestones/evals/`.

## Design principles

Durable guidance for this arc's ongoing and future work, carried over from the "Global workspace / navigation direction" discussion that motivated the original Explorer pivot (PR 1 onward) — the origin-story half of that discussion now lives in [`arcs/explorer-foundation.md`](./arcs/explorer-foundation.md)'s own intro; this is just the guidance that's still actively load-bearing.

- **The concrete shape being aimed at: a left-side explorer tree (Flows → Versions → Runs/Artifacts/Sims/Evals) plus a dynamic tab/panel system, with a detail panel that follows the active tab.** Deliberately _not_ a flat global "all artifacts" browser — scoped browsing, nested under the flow/version that owns it. A true flat global browse, if ever built, is a different root in the same tree.
- **A working heuristic for sorting which modes become tree branches vs. stay closer to a standalone action**: is this fundamentally _a list you browse, then open something from_, or fundamentally _a distinct workflow/action_ that doesn't reduce to browse-then-open? Artifacts and Run History read as the first kind; triggering a _new_ run reads more like the second.
- **Naming collisions across scope levels are resolved structurally by tree position, not by inventing different words.** A node nested under a specific flow version's branch is unambiguous by where it sits in the tree.
- **List scale/navigability is deliberately deferred, and solved by a different mechanism than the tree itself** — a huge folder isn't made navigable by better tree design, it's made navigable by pairing the tree with a separate fuzzy filter/search that skips the hierarchy entirely. Not worth building before there's enough real content for it to bite.
- **Picker-mode vs. browse-mode clicks is a real, already-solved-elsewhere interaction pattern** — a dumb component driven entirely by whichever callback prop the caller wires up (`onOpen` vs. `onSelect`), not a new pattern to invent.
- **State/lifecycle implication, genuinely underappreciated at first**: a tab that's merely hidden and re-shown never unmounts the way a real route change used to. Patterns built assuming real unmount/remount timing need rethinking, not just porting. A singleton slice assuming exactly one "current" thing stops being coherent once multiple tabs of the same content type can be open at once — a keyed-by-panel-id slice is the general fix, already the established pattern in this codebase (see `research/state-management.md`).
- **Visual direction: shift from web-page density toward desktop-tool density is three separable things, not one dial** — padding/type scale; information architecture (how much shows by default vs. on demand); interaction model (small toolbar-icon actions instead of large always-visible CTA buttons). A traditional top menu bar is explicitly not the starting interaction model.
- **Audience/positioning**: this is primarily a developer/orchestration tool. "Friendly to non-technical people" is scoped specifically to _installation_ (the Electron packaging goal), not to simplifying the feature set or this UI's density.
- **Deliberately not adopting a docking/tab-management library until the simple skeleton's real limits were actually felt** — this played out for real (`dockview` adopted in PR 5, after PR 2-4's hand-rolled tab registry hit a real, felt limit), confirming the instinct was right, not just cautious.

## Next up

Real order, not just a bucket of candidates — but explicitly changeable. Several of these already have fuller write-ups in `Not yet scoped` below or in `docs/todo.md`; this list is the sequencing commitment, not a duplicate of that detail.

- **PR 39 — Fix `CodeEditor` (Monaco)'s spacebar input bug.** Sometimes stops accepting spacebar entirely, in both the flow-authoring and artifact-authoring editors — a real, high-priority usability problem (blocks typing at all, not a narrow edge case), re-sequenced ahead of PR 39's original slot (now PR 40) for that reason. One theory (a debounced-value echo racing Monaco's own value-prop resync) was already implemented and tested live during PR 38 — it did not fix the symptom, so that mechanism is ruled out, not just untried. Full trace and untried diagnostic steps in `docs/todo.md` and `arcs/code-editor-spacebar-bug.md`.
- **PR 40 — SSE instead of WebSocket, or at least real WebSocket client/session management.** The current WebSocket client is fundamentally broken, not just unpolished — a single global socket keyed by the literal string `"client"` means a second browser tab steals live-run monitoring from the first. Possibly outside a UI milestone's normal scope (backend/transport, not a panel/tab), kept in this list anyway since it's still wanted.
- **PR 41 — Runs with a simulation don't show the sim/reuse badge on steps that were actually reused.** Touches two existing `docs/todo.md` notes, not yet unified. Possibly merges with another PR rather than standing alone — not decided yet.
- **PR 42 — Prune old pages, possibly across a few PRs.** Gated mostly on PR 38 (flow authoring) landing first. See `Not yet scoped` for the piece-by-piece breakdown already done.
- **PR 43 — Grab-bag of closing-out items, expected to keep growing as more small polish surfaces — likely splits into more than one PR.** Page icon, page title, other small polish, doc updates around the API and React component layout, and a comment pass across the flow-graph work from PRs 29–34. Least scoped item on this list, deliberately so.

## Not yet scoped

Ideas with no PR number yet, no ordering commitment. Detail level varies — some of these are close to ready to plan, others are just named so they aren't lost.

- **Edit mode, actually editable** — currently just a read-only copy of View. Real scope unknown; likely a substantial lift given flow authoring/validation/publish-state semantics aren't designed yet.
- **A full-step "resolved preview" view** — a view showing _every_ field of a step (matching `StepHttpJsonDetails`' full field list), with each field showing its bound param value before a run and its actual resolved value after. Two distinct gaps motivate this: fields with zero refs are invisible in Run mode entirely; fields that do have refs are only ever shown at leaf-`bindPath` granularity in Field Resolution, never composed back up into the whole logical field. Needs its own design pass before it's scoped, the same way Step Results got one.
- **A generic "open in its own dockview panel" capability** for an event's raw payload — arbitrary content with no persistent identity at all, unlike artifacts (which graduated to a real panel kind, PR 22). Not scoped.
- **A dropdown/picker to select an _existing_ sim from a plain, no-run Flow Graph panel** — separate from picking a run to author _from_. Not scoped yet.
- **References for run params** — the reference-resolution family carved out of PR 27/28 (`FieldResolutionRow`'s "before/after" field view, `ReferenceRow`'s per-reference resolved value, `FlowVersionRunParamRow`'s Show-usages report). Not yet through a real discussion pass — the open question isn't just "where does this open" but "how should raw-vs-resolved step viewing work at all" now that `StepDetailsTab` and the params picker can coexist in the same panel.
- **Pruning old pages (PR 42, above) — the breakdown already done, piece by piece, not "prune everything old":**
  - Confirmed already dead, safe to remove any time: `pages/Runner-old.temp.tsx` (fully commented-out), `pages/flow-version/FlowVersionEdit.tsx` (identical to `FlowVersionView.tsx` except the name — "Edit mode" was never actually implemented), and `src/components/AddJsonFlow.tsx` (the bare-textarea flow-upload prototype PR 38 properly replaces — no strict pruning policy decided, batch vs. as-found doesn't matter enough to settle).
  - Gated on flow-authoring landing, then removable as a whole cluster: View/Run/Run History/Sims/Artifacts and their pages, `FlowVersionWorkspace.tsx`/`FlowVersionModeNav.tsx`, old `Flows.tsx`/`FlowsEdit.tsx`.
  - Decided to remove regardless, no Explorer-equivalent needed: `pages/Runner.tsx` (standalone flow-picker + sim-picker + run button) and the top-level `pages/Artifacts.tsx` (global artifact browser).
  - A third, older tier, predating even `FlowVersionModeNav`: `pages/RunDetails.tsx` (route `/runs/details`), plus `FlowsEdit.tsx`/`CreateSim.tsx`/`ViewSim.tsx`/`Runner.tsx` — each with its own fully duplicated `<ReactFlow>`+`graphLayout()` rendering, never routed through the shared `FlowGraph.tsx`. Not scoped or prioritized yet, needs its own look.
  - Stays regardless, on its own separate timeline: the old Evals page, tied to the current flow-def-embedded eval design — superseded only once the real evals rework lands.
  - `System.tsx` stays, but its content (dark-mode toggle, possibly component start/stop status) is a separate, later question. `docs/request-flow-map.md` is wanted eventually rebuilt as real swagger-style API documentation — tracked in `docs/todo.md`.
- **Sims generalizing beyond one parent run** — today a sim is always exactly one `parentRunId` plus a `reuse` list. The named future direction: a sim built from _zero_ run ids, where individual steps' outputs/exports are mocked directly rather than reused from something that actually ran. A materially different authoring model, not an extension of PR 18's flow.
- **Left-side navigation itself, further out.** Once enough of the above exists, the left nav wants a real revisit — the long-term shape wants multiple trees (this Explorer tree being only one view among several), with navigation happening mostly by changing _which tree_ is shown. Not scoped, genuinely unsure what it means yet beyond that direction.
- **A generic/preview Flow Graph panel, unresolved.** Borrowing VS Code's file-explorer preview-tab behavior: single-clicking a run/sim/version loads its content into _one_ reusable Flow Graph panel (the "preview"); an explicit pin gesture promotes it into its own permanent tab. The "dirty" rule (a value-changing action promotes a preview; inspecting doesn't) already maps cleanly onto existing reducers. This would be close to the opposite of PR 14/15's pattern (stable permanent ids) rather than an extension of it — a new `isDirty` field, tracking which panel is "the preview," and `Content.tsx` needing to re-derive cleanly when its own identity changes underneath an already-mounted instance (the one genuinely unproven mechanic). Suggested build order if/when this happens: the `isDirty` field first, alone; then spike the re-derivation-without-remount question in isolation; the tree-click branching last. A possible shortcut: sim authoring could piggyback on this same generic panel. The concrete case that surfaced this section's relevance for authoring, not just viewing: Simulate on a blank Flow Graph panel currently just says "Open a run to simulate from it" — two candidate mechanisms floated (drag a run onto a blank panel; a "select a run" button that arms a tree-click-selection mode), not decided between. PR 16's EventGraph hit this same tension from its own side and sidestepped it entirely by becoming a focus-following singleton instead — a dodge that doesn't generalize back to this section's bigger problem (a singleton, focus-following _Flow Graph_ panel would be the primary editing/comparison surface, not a secondary drill-in view).
- **Evals rework** — confirmed its own separate track, no longer a section here at all. See `docs/milestones/evals/`.
- **Parked, explicitly not now: building this as a VS Code extension instead of a native/Electron app.** Real, verified upside if ever revisited — VS Code's `TreeDataProvider` API natively supports lazy-loaded custom tree views, and `QuickPick` is a genuine free answer to the picker-mode problem. Real remaining cost: any custom visual content (flow graphs, artifact viewers) still has to be built as a Webview. Also a fundamentally developer-first distribution model, in tension with any non-technical-user goal. Interesting long-term direction, not a near-term plan.
- **Floated, explicitly not decided, a genuine parking lot**: card view vs. compact list view for the flow browser (possibly both, toggleable); auto-generated flow-diagram thumbnails via React Flow's server-side `renderToStaticMarkup` (confirmed real — official docs list this as a named use case; `FlowGraph.tsx` already computes explicit node positions itself, which happens to fit this approach's requirements); friendly auto-generated human-readable version names alongside mechanical labels/sequence numbers; color/icon markers for flows or versions; merging "Run" and "Run History" into a single mode; System (start/stop status for the engine/worker/etc.) and Settings/Config (API keys, concurrency/limiter settings, infra choice, theme, auth) both need a home in the eventual nav structure.
