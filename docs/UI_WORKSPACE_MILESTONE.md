# Flow-Version Workspace UI Rework

## Summary

This is the direction doc for the ongoing rework of `apps/web-app` away from a page-navigation web app toward a flow-version-centric workspace: drill into one flow version, and work with it entirely through panels/tabs for whichever mode you're in (Edit, View, Run, Run History, Sims, Artifacts, Evals) — rather than navigating to separate top-level pages for runs/sims/artifacts/evals that all have to be manually cross-referenced by id.

Not everything below is equally fleshed out. The point of writing it now is to capture the parts that _are_ settled (so they don't need re-deriving later) and name the parts that aren't (so they read as open, not forgotten). This doesn't map to a single GitHub Milestone or version bump — each concrete chunk below (starting with Run History) is its own small, closeable milestone; this doc is the throughline connecting them.

## Overall idea and purpose

The core problem with the current page-based UI: nearly everything lives at the "list all runs / list all sims / list all artifacts" level, globally, with no real organizing entity underneath it. That's the wrong default — the actual daily unit of work is _one specific flow version_. The rework makes that the primary workspace:

- **Flow version = the primary workspace.** Drill into one, and within that single context: edit it (if still a draft), run it, view its run history, create/view sims of it, browse/create artifacts scoped to it, construct and run evals against it — all via panels/tabs inside one persistent shell, VS-code-style (frames with tabs, panels loading different content).
- **Flow (all versions) = one level up.** Comparing sims/runs/artifacts/evals across every version of one flow — needed, but not the primary workspace.
- **Global (all flows/all runs/etc.) = top, rare.** Useful sometimes as a filterable escape hatch, but explicitly not where work usually happens — today's UI is almost entirely this level, which is the concrete reason it's been "not very useful."

Longer-term context worth keeping in view even though it's not being built yet: the eventual target runtime is Electron (not just a browser tab), with real multi-pane coexistence (view + edit + preview at once, like an IDE) rather than one panel at a time, and an explicit non-goal of supporting small/phone-sized screens — the panel/toolbar model is inherently a desktop pattern. Also an explicit constraint: this UI is being hand-designed and understood, not generated wholesale by an AI/design tool in one shot, the same ownership stance as the rest of this codebase.

## What's already built

- The routing shell: `/spike/:flowId/:versionId/<mode>` via `FlowVersionWorkspace` (real flow-version fetch) + `FlowVersionModeNav`, replacing the old flat `Spike.tsx` prototype. One persistent shell, one `Outlet` per mode, state scoped per mode rather than globally.
- **Edit / View modes**: routed and rendering (flow graph + JSON view, step details, settings/params/problems panels), but not yet functionally distinct from each other — Edit isn't actually editable yet. Matches the concrete panel pairing already envisioned: flow graph + JSON definition for authoring context.
- **Run mode**: fully working end to end — submit a run, watch it live (websocket-fed events, no polling), an animated flow chart showing live step status (pending/running/completed/failed) derived client-side from the run's own event stream, a params panel with artifact selection, and a preview feature showing how a selected param actually resolves everywhere it's referenced in the flow (including refs embedded in larger template strings). Matches the other envisioned panel pairing: flow graph + step execution detail for run/inspection context.
- **Step Results** (Run mode's right panel, PR #261): status, Output & Exports, Field Resolution (a field's final value with every `{{...}}` ref in it substituted, composed across multiple refs in one field), and References (each individual reference's own resolved value) — all sourced from the run's own event stream, deliberately with zero dependency on `job.<cap>.submitted`'s payload shape (see `docs/todo.md`).
- Reusable pieces this unlocked for later modes: `EventGraph` (decoupled from any one page's state, takes events/selection as plain props), `deriveStepRunInfo`/`useStepRunInfo` (a pure fold over any event array, not tied to live-only data — status plus output/export hashes), `findStepRefs`/`resolveRefHash`/`foldResolvedField` (`lib/ref-resolution.ts`, also event-array-agnostic).
- **Run History mode**: fully built across 3 small PRs (#262, #263, #264) — a flow-version-filtered run list (`listRunsByFlowVersionId`), a left-panel run list wired to routing with REST event backfill on selection, and Run mode's own graph/details panels (`FlowVersionRunGraphPanel`/`FlowVersionRunDetailsPanel`, `StepResultsTab`) reused as-is, fed by the selected historical run's events instead of the live one — confirmed those panels needed zero changes, since they were already pure props-in/callbacks-out with no coupling to the live Redux slice. Also produced two small shared extractions used by both Run and Run History: `useRunEventsWithStatus` (events backfill + `deriveStepRunInfo`, identical logic regardless of live vs. historical) and `lib/run-panel-state.types.ts` (tab/focused-content types hoisted out of the live slice, since they were never actually live-specific — each mode still keeps its own independent slice state, no shared/merged state between modes).
- **Sims mode**: fully built across 5 PRs (#265, #266, #267, #268, #269) — see "Sims mode" section below for the full design narrative (state machine, placement decisions, corrections). Summary: authoring a new sim reuses Run History's graph/details pieces with an added reused-step toggle; browsing _is_ viewing (the sim list stays visible and freely re-pickable, same pattern as authoring's run list, auto-defaulting to the most recent sim); a Settings tab (first, default-selected) shows a viewed sim's full name/description and its fork spec's raw parent run id, hidden while authoring. Two small polish passes landed in the same arc: a `FlowVersionSimsList` display fix (long descriptions were pushing the date off the row — now two independently-clamped lines instead of one shared block), and the reused-step switch showing (disabled) while browsing instead of only appearing during authoring.
- **Explorer arc, PRs 1–7 of several** (merged #284–#290; PR 8 is a retrospective ADR, no app changes — Workspaces, originally slotted there, was skipped and moved to the end of the PR log instead) — not a finished feature, still an arc in progress: a `/explorer` page with a real-data Flow → Version tree (both levels now containers, click always toggles + highlights, never opens a tab), `dockview-react` as the tab/panel host (open/close/switch/drag-and-drop, true multi-instance — two different versions' flow-graphs can be open side by side, each with its own independent right panel), four real view-only leaves — Flow Settings, Version Settings, JSON Definition, Flow Graph — and, on the Flow Graph tab, a first interactive piece: a bottom-center run toolbar plus a right panel for setting params and triggering a real run, with live step status overlaid on the graph. Panel state survives switching between tabs, in-app navigation away and back, and a real reload of the same tab — via a keyed Redux slice persisted to `sessionStorage`/`localStorage` (PRs 6–7; see ADR-0004). Only a genuinely new tab still seeds from whichever tab most recently wrote, and true cross-device sync remains unbuilt — both deliberately parked, not accidental gaps. Sim selection is a no-op, no step-level run diagnostics, no tree levels below Version, no editing yet. See the PR Log below for what's landed and what's next.

## Other bits of work (less fleshed out — sizes and shapes still provisional)

- **Edit mode, actually editable** — currently just a read-only copy of View. Real scope unknown; likely a substantial lift given flow authoring/validation/publish-state semantics aren't designed yet (e.g. whether a published version becomes immutable and editing forks a new draft version).
- **A full-step "resolved preview" view — parked, not scoped.** Raised while building Step Results: a view showing _every_ field of a step (matching `StepHttpJsonDetails`' full field list — URL/Method/Headers/Body/Exports — not just fields with refs), with each field showing its bound param value before a run and its actual resolved value after. Two distinct gaps motivate this, not one:
  - Fields with zero refs are invisible in Run mode entirely — only Edit/View's `StepHttpJsonDetails` shows them, and only unresolved.
  - Fields that _do_ have refs are only ever shown at leaf-`bindPath` granularity in Field Resolution (e.g. just `body.messages[1].content`), never composed back up into the whole logical field (`body`, `headers`) as it was actually sent — if `body` has refs at two different nested paths, Field Resolution shows two disjoint leaf rows, never one composed `body` object with both substitutions sitting in their natural positions. The natural grain for "the whole field, fully resolved" is the same field-level granularity `StepHttpJsonDetails` already uses; Field Resolution deliberately went finer because "what did this one reference become" wants the leaf, not the whole object.

  Also explicitly not Run-History-specific, and connects to an existing feature, not just Field Resolution: the per-param "show usages" report (`findParamRefs`/`renderParamRefReport`, `FlowVersionRunParamRow`) already lets you click a _param_ and see a markdown report of everywhere it's used — useful, but it's the reverse direction (param → its usages, leaf-level, textual report). What's missing is the other direction: click a _step_ in the live Params panel and see that whole step's fields composed with the currently-selected param artifacts filled in, ahead of submitting — same underlying resolution logic (`resolveRefHash`/`buildRefUsage`/`foldResolvedField`), organized by step instead of by param, at whole-field instead of leaf granularity. Deliberately not built yet because it's unclear how much it'd repeat Field Resolution/References; the resolution reached in discussion: judge that by whether it answers a _different question_ (a holistic "what did this step look like as one document" snapshot vs. drill-down provenance), not by whether it reuses the same underlying resolved-value logic — reusing `foldResolvedField` etc. across views isn't repetition, showing the same field list with the same framing twice would be. Needs its own design pass before it's scope, the same way Step Results got one.

- **Replay — acknowledged valuable, not scheduled (not "no reason exists" anymore).** Watching a historical run's execution animate at some controlled pace (a play-head over the event timeline instead of a range selection, reconstructing state at any point rather than just the final one) — technically straightforward given the architecture (`deriveStepRunInfo` already works on any event array, live or historical; this is UI/timing work, not new plumbing). The concrete reason it's worth building, not just "it'd be cool": it lets you re-experience the feel of watching a run live — pacing, what happened when — which a final-state view structurally can't reproduce. Still not the first thing to build; no committed timing.

## Evals: deliberately its own separate, future milestone

Explicitly not part of this arc's near-term scope — this is a real data-model rearchitecture, not a UI tab, and deserves its own milestone the same way the original eval vertical slice did (Milestone #9). Current state: evals are embedded inside the flow definition itself (an eval is just a flow with a judge step) — a smaller move than originally wanted. The actual goal: evals as standalone, reusable entities, decoupled from any one flow — a fixed template (System Prompt + Question + Context + Answer) that can be constructed and run against different flows. Inside this workspace, an Evals mode/tab would let you construct an eval run (bind the flow's actual output to the eval template's expected inputs) — results visualization might end up needing its own separate page if it doesn't fit inside that tab. Not scoped further here; needs its own dedicated design pass.

### ArtifactComposition and ComposedArtifacts

One proposal floated for solving the eval-binding problem: a more primitive object, `ArtifactComposition` — itself an artifact, but one with template references to other artifacts (plus arbitrary text) that compose together into a single output artifact, `ComposedArtifact`.

The core idea: map several artifacts into one output, which is exactly the shape needed to bind a run's outputs into an eval flow's expected inputs.

Not eval-specific, though — the same primitive could be used by any flow, and it reuses the existing artifact/templating system as a foundation rather than inventing something new. One open question: the templating language itself may need to diverge from what the rest of this system already uses, rather than being borrowed wholesale (tbd).

`ComposedArtifact`s would likely be created lazily at runtime — materialized right before a run is submitted, since that's when one is actually needed as a param input, not proactively the moment some other, related flow's run finishes.

## Global workspace / navigation direction — a real pivot, current guiding principles, not a PR

**A genuine pivot from the section below's original framing, not just a refinement — some already-built UI (the bottom `FlowVersionModeNav` mode toggle, one-mode-per-route) is expected to be redone, accepted as a real cost, not a mistake to avoid discovering.** Came out of actually using Postman (previously only judged from the outside) and recognizing it solves a closely-related problem: node-based API "Flows" plus "runs" of them, browsed via a left explorer, opened into a content-agnostic tab strip with a detail panel that follows whichever tab is active. Not tied to any single PR; meant to be revisited as building surfaces what actually works. Explicitly paused here per the user's own call, before turning this into an implementation plan — this section is the synthesis to plan from, not the plan itself.

- **The concrete shape now being aimed at: a left-side explorer tree (Flows as the root object, expanding into Versions, expanding further into that version's Runs/Artifacts/Sims/Evals) plus a dynamic tab/panel system that opens whatever's clicked, with a detail panel that follows the active tab.** This is deliberately _not_ the same thing as a flat global "all artifacts" browser — it's scoped browsing, nested under the flow/version that owns it, the same filtered-by-`flowVersionId` shape today's `FlowVersionArtifacts`/`FlowVersionRunHistory` pages already fetch. A true flat global browse (if ever built) would be a different root in the same tree, not this one.
- **A working heuristic for sorting which of today's modes become tree branches vs. stay closer to a standalone action**: is this mode fundamentally _a list you browse, then open something from_ (maps cleanly onto "tree node → tab"), or fundamentally _a distinct workflow/action_ that doesn't reduce to browse-then-open (stays more mode/form-like)? Artifacts and Run History read as the first kind; triggering a _new_ run reads more like the second. Not yet applied to every mode, just the lens to apply.
- **Naming collisions across scope levels (e.g. "Artifacts" globally vs. this-flow-version's "Artifacts") are resolved structurally by tree position, not by inventing different words.** A node nested under a specific flow version's branch is unambiguous by where it sits in the tree — the same positional-disambiguation idea considered earlier, now concrete instead of theoretical, and stronger than the earlier instinct to dodge collisions with fuller labels (e.g. `FlowVersionModeNav`'s "Run History" instead of a bare "Runs").
- **List scale/navigability is a real concern, deliberately deferred, and solved by a different mechanism than the tree itself** — confirmed by how VS Code actually handles it: a huge folder isn't made navigable by better tree design, it's made navigable by pairing the tree with a separate fuzzy filter/search that skips the hierarchy entirely. Filtering matters, just not before there's enough real content for it to bite.
- **Picker-mode vs. browse-mode clicks (e.g. selecting a Run as input while creating a Sim, vs. normally opening a Run in a tab) is a real, already-solved-elsewhere interaction pattern, not a new kind of problem.** Native file-picker dialogs reuse the same file browser with different click semantics; this codebase already has the matching mechanism (a dumb component driven entirely by whichever callback prop the caller wires up — `FlowVersionArtifactsList`'s `onSelectArtifact`, `SelectField`'s `onChange`) — the tree explorer would need the same `onOpen` vs. `onSelect` treatment, not a new pattern invented from scratch. Selecting in picker mode should highlight the item rather than navigate, giving clear "this is now chosen" feedback without leaving the current flow.
- **State/lifecycle implication, genuinely underappreciated at first**: today, switching modes is a real route change — the previous mode's component tree unmounts, the new one mounts fresh. A tab that's merely hidden and re-shown never does that. Several patterns built this session specifically lean on real unmount/remount timing and will need rethinking, not just porting: the `useLayoutEffect`-on-mount trick that clears a stale file breadcrumb in the upload panel only works because navigating away and back today genuinely destroys and recreates that component; hoisting `authoringDraft`/`draft` into Redux instead of local `useState` was specifically to survive an unmount tabs wouldn't cause in the first place.
  - **Deeper implication**: today's Redux slices assume exactly one "current" thing (one `authoringDraft`, one `draft`). If tabs ever allow two instances of the same content type open at once (two "create a sim" tabs, two artifact viewers side by side), a singleton slice stops being a coherent model — it becomes "which tab's draft is this," needing per-tab-keyed state instead of one shared slot. **Legitimate, deliberate scope-narrowing available here**: not supporting multiple simultaneous tabs of the same content type is a fine constraint to ship with initially (matching this arc's general "defer until a real second need proves it's needed" practice) — today's singleton pattern can keep working largely as-is under that constraint, with per-tab-keyed state only needed once/if true multi-instance is actually wanted.
  - This stopped being hypothetical once multi-instance panels landed for real in PR 5 — see [`UI_STATE_RESEARCH.md`](./UI_STATE_RESEARCH.md) for the full reasoning trail (identity-vs-runtime-acquired state, why a keyed slice not a singleton, cleanup discipline, workspace-switching implications) building toward a future ADR, once a real implementation validates it.
- **Sequencing to actually build this**: the left explorer + flow browser view first, since it's the root that drives everything else, built _alongside_ (not before, not fully after) the smallest possible tab/panel skeleton — a single tab strip, open/close/switch only, no drag, no split, no reordering, singleton-per-content-type state — so that clicking something in the explorer has somewhere real to land without either piece being fully built in isolation from the other. Same "build one real page, let the pattern emerge from it" instinct already used elsewhere (e.g. not building `DebouncedCodeEditor` until a second real caller existed).
  - **Deliberately not adopting a docking/tab-management library yet** (real options exist and are worth remembering later — `dockview`, `flexlayout-react`, `rc-dock`, all mature VS-Code-style docking libraries with drag/split/serializable layout). What they solve — drag hit-testing, drop zones, resize, layout serialization — was never the uncertain part; what's actually still unresolved (picker-vs-browse semantics, singleton-vs-multi-instance state, how the detail panel follows the active tab) is domain-specific and a library wouldn't resolve any of it. Revisit once the simple skeleton's real limits are actually felt, not before.
- **What this pivot does and doesn't invalidate, worth being explicit about since it's a real cost being accepted, not glossed over**: the backend (services, ports, adapters, routes, RTK Query endpoints — the majority of the actual engineering effort in this arc so far) is completely presentation-paradigm-agnostic and unaffected. Field-level components (`InputField`, `SwitchField`, `SelectField`, `CuratedParamsField`, `IdentityField`) are equally reusable regardless of container. What's actually being redone is narrower than "the whole UI": the page-as-mounting-boundary assumption, the bottom mode toggle as the primary nav, and the small number of components whose behavior specifically depended on real route-driven unmount/remount timing.
- **Visual direction (carried over, still holds): shift from web-page density toward desktop-tool density is three separable things, not one dial** — padding/type scale; _information architecture_ (how much shows by default vs. on demand — today's artifact rows are closer to a card than a compact file-browser row); _interaction model_ (small toolbar-icon actions instead of large always-visible CTA buttons like "Add File," which stop scaling once many panels each want their own primary action). A traditional top menu bar (File/Edit/...) is explicitly not the starting interaction model — real value there is as a comprehensive fallback/index once there's enough surface to need one, not as the first way to trigger anything done often.
- **Audience/positioning note, relevant to how much this pivot is allowed to lean technical/dense**: this is primarily a developer/orchestration tool (making sims, exposing observability, etc. are inherently technical concepts) — "friendly to non-technical people" is scoped specifically to _installation_ (the Electron packaging goal — no web server or Docker Compose to set up), not to simplifying the feature set or this UI's density. No non-technical-usability bar exists that this explorer/tab direction needs to hit. If broader non-technical accessibility is ever a real goal, the natural lever is a different, purpose-built frontend sitting on the same backend (this system already treats `apps/*` as thin, swappable callers of one shared service set — the same decoupling principle, one layer up), not retrofitting simplicity onto this explorer.
- **Parked, explicitly not now: building this as a VS Code extension instead of a native/Electron app.** Real, verified upside if ever revisited — VS Code's `TreeDataProvider` API natively supports lazy-loaded custom tree views (matches the explorer idea's own lazy-expansion need), and `QuickPick` is a genuine free answer to the picker-mode problem above. Real remaining cost: any custom visual content (flow graphs, artifact viewers) still has to be built as a Webview — VS Code gives you the tab container for free, nothing about what's rendered inside it (though `FlowGraph.tsx`'s existing React/`@xyflow/react` implementation could plausibly be reused inside one nearly as-is). Also a fundamentally developer-first distribution model (requires VS Code installed), in tension with any non-technical-user goal. Interesting long-term direction, not a near-term plan.
- **Floated, explicitly not decided, parking lot for later**: card view vs. compact list view for the flow browser (possibly both, toggleable, sequenced card-first rather than resolved up front); auto-generated flow-diagram thumbnails via React Flow's server-side `renderToStaticMarkup` (confirmed real — official docs list "dynamically creating Open Graph preview images" as a named use case; `FlowGraph.tsx` already computes explicit node positions itself rather than relying on browser measurement, which happens to fit this approach's requirements), generated at some lifecycle point (draft/version-creation/publish) and served as a plain http-server image resource, not necessarily a CAS artifact; friendly auto-generated human-readable version names ("yellow elephant"-style) alongside mechanical labels/sequence numbers; color/icon markers for flows or versions; merging "Run" and "Run History" into a single mode; System (start/stop status for the engine/worker/etc., not yet built) and Settings/Config (API keys, concurrency/limiter settings, infra choice, theme, auth — not yet built) both need a home in the eventual nav structure, with System's own operational settings (e.g. limiter tuning) possibly nesting under a System drill-down while more general preferences stay separate from any one system's runtime state.

#### PR 9 - Right Panel Icon Rail (Params/Sim migrated first) - merged (#292)

Supersedes this slot's original "Extend the tree with nested sub-lists" idea — displaced, not just renamed, for a reason worth keeping: exposing Runs as a tree node is very likely just a UI for setting `runId` on the Flow Graph panel that already exists (see below), not a new panel/tab kind that needs tree scaffolding first. That question is resolved for real once this rail exists to host it, not before.

This is also the point where this arc stops being framed as "the Explorer spike" and starts being the actual migration of the old page-based Edit/View and Run/Run History modes into the new dockview panel model — the Flow Graph panel already generalizes across what used to be four separate pages; what's left is resolving its right-hand panel's tab structure so it can absorb the rest of what those pages did.

**Design landed on, via discussion, before any implementation plan:** replace `ExplorerRunRightPanel`'s current horizontal `Tabs` with a Postman-style vertical icon rail — fixed-width, always visible, icon buttons with hover tooltips (not text labels), deliberately distinct from dockview's own draggable tabs. Layout, left to right: **Graph → drag handle → Rail (fixed width) → Content pane** (only rendered when a tab is active, appearing to the rail's right — this is why opening content visually "pushes the rail left": the `[Rail+Content]` block widens and Graph absorbs the difference). The rail itself is a plain fixed-width flex child, not a `react-resizable-panels` `Panel` — only the content pane is resizable, via one handle sitting at the rail's left edge. Closing is explicit only (the existing "x" button in the content header) — no drag-past-a-threshold auto-collapse, even though `react-resizable-panels` (already in use here) supports that natively via `collapsible`/`collapsedSize`; not adopted now, worth revisiting only if explicit-only is felt as a real missing convenience in practice.

**Scope of this PR specifically**: build the rail shell and migrate the two tabs that already exist today (Params, Sim) into it, unchanged in content/logic — proves the shell and interaction pattern in isolation before loading in tabs that still need their own design pass.

**Explicitly not this PR, named so it isn't lost:**

- A Step Details / resolved-value tab folding in View/Edit's step inspection — ties to the still-unscoped "full-step resolved preview" idea already parked earlier in this doc ("Other bits of work").
- Event Details + Step Results tabs folding in Run/Run History's post-run inspection. Likely implication once designed: Run History probably doesn't need its own panel/tab kind at all, just another way to set `runId` on this same Flow Graph panel (pick from a list instead of submitting fresh) — `useRunEventsWithStatus` was already built event-array-agnostic for exactly this reuse.
- Actually wiring up the Sim tab (still a no-op placeholder today).
- Any of Edit mode's real editability, or draft/publish semantics — separate, larger, backend-touching work, deliberately sequenced after migration.

**What actually landed**: the design above shipped essentially as planned — `ExplorerRunRail.tsx` (new) is the fixed-width icon rail, `ExplorerRunRightPanel.tsx` was renamed to `ExplorerRunRightPanelContent.tsx` and stripped of its `Tabs` header (plain conditional rendering instead, since `Tabs.Content`'s Presence context no longer wraps it), and `ExplorerFlowGraphContent.tsx` gained the two-branch (rail-only vs. `ResizablePanelGroup`) structure. Two real bugs found via manual testing after the initial build, both fixed:

- **Active-tab indication**: originally tried swapping the rail button's `variant` between `outline` and `ghost`, which caused a visible "flash" on the just-deactivated tab — `Button`'s base classes include `transition-all`, and `outline` carries a border + `shadow-xs` that `ghost` doesn't, so switching variants animated that border/shadow away, which read as a distinct bright flash. Fixed by decoupling the active indicator from `variant` entirely — `variant` stays fixed at `"ghost"`, and active state is just a conditional `bg-accent text-accent-foreground` className (the same tint `ghost`'s own hover state already uses) layered on top. Only one property changes now, so there's nothing uneven left for `transition-all` to animate.
- **Tooltip close stutter**: switching between rail tabs while a tooltip was visible caused a janky, inconsistent close animation. Root cause: Radix Tooltip's animated exit relies on detecting a CSS `animationend` event, which is unreliable at very short/zero durations across browsers — and separately, Floating UI's live repositioning can fight with a still-running CSS transform animation when the trigger changes quickly. Fixed by mirroring each tooltip's open state locally and only rendering `TooltipContent` while actually open, so closing unmounts it outright in the same render instead of going through Radix's animated-exit path at all. The hover-in fade is untouched; only the close side changed.

**Found, not fixed here — logged in `docs/todo.md` instead**: the Params tab has a real, felt render delay (confirmed via React DevTools profiling, not just suspected) driven by `ExplorerFlowGraphContent.tsx`'s `useListArtifactsQuery()` pulling every artifact in the project unscoped (336 in this dev DB) into each param row's compatible-artifacts filter and `Select` dropdown. Ruled out `SelectContent`'s `position` prop as a fix (tried `popper`, made the dropdown's own open animation worse via the same Floating-UI-vs-animation class of issue as the tooltip bug above, and didn't reduce the item count rendered either way). Confirmed the real lever by temporarily slicing the artifact list to 5 items, which dropped the worst render commit from ~50ms to ~2-3ms. Real fix is the already-known Artifacts-mode wiring gap (a curated/scoped artifact set instead of the global list) — out of scope for this PR since it changes picker behavior, not just performance.

#### PR 10 - Problems + Parameters migrated to the rail - merged (#293)

Supersedes the old loose "PR 10+ - other content types" placeholder with a concrete next three. Both `FlowProblemsList` (flow-analysis problems, from View/Edit's `FlowVersionDetailsPanel`) and `FlowParameters` (the flow's declared param schema — names + content types; a different concept from the rail's existing run-input picker, even though both get called "Params" colloquially) become new rail tabs. #### PR 16 - EventGraph, spawned from the Flow Graph panel itself - merged (#299)

Unlike every panel/tab so far, this one isn't opened by the tree — it's opened by _another panel's own content_, a genuine first for this arc. Adds a button to the Flow Graph panel's toolbar that opens (or focuses) an `EventGraph` panel, showing events live as they arrive, for any run state — not yet started, currently running, or already completed.

**Revised mid-build, after a first pass exposed real identity problems.** The first design gave every Flow Graph panel its own EventGraph, identified by `sourcePanelId` and reading that source's `runId` reactively. Building and testing it surfaced a run of genuine, compounding usability problems, all rooted in the same cause: panel ids were being asked to double as both a stable dedup key _and_ a stand-in for "what I'm currently looking at," and those two only agree when a panel's content never changes after creation — true for a specific run/sim's panel, false for a plain version panel or any panel that gets rerun-in-place. Concretely: closing a panel and reopening the same (plain) id later left its EventGraph frozen on stale data with no way to tell "source closed" apart from "source reopened but blank"; rerunning from inside an already-open run panel made its EventGraph silently start showing a different run than the tab's own title implied; and a rerun's EventGraph didn't line up with the one you'd get by separately opening that new run's own dedicated panel, even though both would show identical data. Chasing each of these individually kept surfacing another one — see the "same identity tension, seen from EventGraph's side" note that used to live in the "generic/preview Flow Graph panel" section below; it's resolved by this redesign, not left open.

**The redesign: EventGraph is a singleton that follows dockview focus, not a per-panel thing.** Only one EventGraph panel can ever be open at once — a fixed id, not derived from any source panel. Clicking "Events" on any Flow Graph panel creates it if none exists, or just focuses the existing one otherwise (unchanged: still goes through the same `OpenPanelRequest`/`explorerPanelId`/`openOrFocusPanel`/`ExplorerTabContent` machinery every other panel kind uses — this part of the original design held up fine and needed no rework). Once open, it live-tracks whichever Flow Graph panel is currently the dockview-active one, subscribing to `DockviewApi`'s active-panel-change event: while the active panel is a Flow Graph panel, the EventGraph reactively mirrors that panel's live `runId` straight out of Redux — switch focus between two open Flow Graph panels and it updates immediately, no separate "attach" step. The moment the active panel _isn't_ a Flow Graph panel (the tree, the EventGraph's own panel, anything else, or nothing) — including the case where the panel it was tracking just closed, since dockview reassigns active focus as a direct consequence of that close, which fires the same event — it takes one last snapshot of what it was just showing (the runId, plus enough to redisplay identity even if that panel is now gone) and freezes there, inert, until focus lands on a Flow Graph panel again. No latch, no per-panel Redux slice, no "is this the same one" question anywhere in this design — there's nothing to keep synchronized across time because there's no persistent per-target identity to lose sync with.

**The real, accepted cost**: no side-by-side comparison of two runs' events at once, unlike Flow Graph panels themselves (which exist specifically to support that, per PR 14). Decided this is fine — EventGraph is a secondary, drill-in debugging aid, not the primary comparison surface; comparing two runs' event timelines is a rare enough need that "toggle focus, singleton follows" is an acceptable workflow. A manual freeze/pin toggle (stop following focus on demand, to regain comparability for as long as you want it) is a named, plausible future addition, not built now.

**Display needs more than a runId.** Since there's no longer a tab-per-target, the tab title can't do the "which one is this" job it did in the first design — the panel's own content needs a small header (version, and sim name or run date/time when relevant) shown next to the graph, reusing the exact lookup logic already built for the discarded per-panel tab-label (sim-detection via a run's own `simId`, date formatting) rather than reinventing it. That header freezes together with the graph's content, from the same snapshot, so the two can never disagree about what's currently being shown.

**No persistence needed.** Nothing here survives a close or a page reload by design — reopening the EventGraph (fresh mount, fresh close, or after a reload) just starts from whatever's currently dockview-active right then, or a true empty state if nothing is. This also means the `event-graph-panels-slice`/`explorer-persistence.ts`/`store.ts` wiring built for the first design gets removed, not kept alongside the new approach.

**Named so it isn't lost, not scoped yet**: `EventGraph` will eventually need its own internal rail/side-panel, mirroring the Flow Graph panel's own pattern, starting with an Event Details tab (today's old-page equivalent) — that's real, separate work once the panel itself exists, not part of standing it up.

**What actually landed**: the singleton/focus-following design above landed as described, plus two real fixes found past the design during build and review:

- **Bootstrap case showed an empty placeholder instead of the source panel's data.** Creating the EventGraph panel makes dockview's own `activePanel` become the new panel itself before it can read "who was focused a moment ago" any other way, so its first render saw only itself and started blank. First attempted fix (`addPanel({inactive: true})`, so creation wouldn't steal focus) caused a worse regression — a lone inactive panel in a brand-new dockview group never becomes that group's selected tab, so it rendered as dockview's own "no tabs open" watermark instead. Landed fix: a one-shot `initialTrackedPanelId` on the `event-graph` `OpenPanelRequest`, set to the clicking panel's own id and consumed once via a `useState` lazy initializer on first mount only — creation keeps dockview's normal auto-activate behavior (so the panel is visible), and the seed sidesteps ever needing to ask dockview who was active.
- **Simplified while reviewing line-by-line after the above landed**: the tracking effect originally reset to "not tracking" (freezing the display) on _any_ focus that wasn't a Flow Graph panel, with a special-cased no-op carve-out for focusing the EventGraph's own panel (so watching it doesn't freeze it). Tracing through an edge case (focus a Flow Graph panel → focus something unrelated, like a JSON-definition panel → click straight onto the EventGraph tab) showed the carve-out didn't actually help there, since tracking had already been cleared by the unrelated detour. Simplified to one rule instead of two: tracking is sticky, only ever updated when a Flow Graph panel becomes active, left untouched by focusing anything else at all. The tracked panel actually closing is still handled correctly — by a separate, pre-existing `dockviewApi.getPanel(...)` existence check, not by this — so nothing was lost by dropping the special case, and the detour bug is gone.

Also extracted mid-review: the focus-tracking mechanism (dockview subscription, live-vs-frozen snapshot) moved out of `event-graph-panel/Content.tsx` into its own `use-tracked-flow-graph-panel.ts` hook, returning just `{runId, versionId}`. `Content.tsx` now reads as fetch-display-data-and-render only, with the one genuinely dense piece of logic isolated and named for exactly what it does.

Not addressed here, flagged for a possible later pass: the header's sim-specific display may want more tweaking once there's real usage to react to — not a known issue, just an open "revisit if it doesn't feel right" item.

- `selectedEventId` and whether the side panel is open both become plain, directly-set Redux state in a new keyed slice (`Record<panelId, ...>`, matching `flow-graph-panels-slice`'s own shape) — deliberately kept keyed even though there's only one real key ever right now, rather than going flat. Two reasons, not just consistency for its own sake: (1) a flat slice has no way to distinguish "this mount is dockview restoring the panel that was actually open at save time" from "this mount is an ordinary reopen later in the same session, unrelated to whatever was last shown" — the keyed shape's per-id cleanup-on-close is exactly what makes that distinction safe, a flat slice would need to reinvent it; (2) there's a real future direction (a pinned, per-run EventGraph, promoted out of the singleton) that would need genuine multiple keys — building the keyed shape now means that later change only adds real keys, not a state-shape migration. The key itself is `event-graph-singleton`, sourced from the same id `explorerPanelId()` already computes in `explorer-panels.ts` (imported, not re-hardcoded as a second literal, so the two can't drift apart).
- Since this is the second slice with this exact keyed-by-panelId shape, the `panelRemoved`-style cleanup reducer/action (currently only implemented once, on `flow-graph-panels-slice`, and dispatched from `pages/Explorer.tsx`'s `onDidRemovePanel` listener) gets pulled into shared logic both slices call, rather than copy-pasting a second near-identical implementation. `pages/Explorer.tsx`'s listener dispatches it for both slices on every panel removal, keyed by that panel's own id — a no-op for whichever slice's key never existed.
- The tracked-panel _snapshot_ (`{runId, versionId}`, see PR 16) is different, because it's computed, not directly set. `dispatch()` during render isn't safe the way a component's own `setState` during render is (React special-cases the latter; there's no equivalent for an external store), so the render-time-derive trick PR 16 landed on can't just be swapped for a conditional dispatch in place. Landed shape instead: Redux is read from **exactly once**, at mount, to seed local state's starting value (same lazy-initializer pattern `initialTrackedPanelId` already uses) — from then on, for that mount's whole life, only local state is ever read or derived from, and a plain effect one-way-mirrors local state into Redux purely so the _next_ mount has something to seed from.
- Revised from PR 16's own note that `trackedPanelId` "stays local-only, never persisted": that held for same-session remounts (closing/reopening the singleton while flow-graph panels are still live, so focus is freshly re-observable via dockview's own API) but not across a real reload, where there's no live focus history left to re-derive from except whatever got mirrored out beforehand. Checked precisely against how `flow-graph-panels-slice` itself actually restores (`store.ts` loads persisted state synchronously at module load, before any component mounts, so Redux is never in a race with dockview's own `fromJSON()`; a flow-graph panel's live state is read from Redux only, keyed by `api.id`, never re-derived from a restored panel's `params`): `initialTrackedPanelId` (the one-shot params hint) only reflects _whichever flow-graph panel most recently had its "Events" button clicked_, since `openOrFocusPanel`'s dedup path keeps overwriting it live, all session, even though the already-mounted singleton never re-reads it. That's a different, weaker signal than "which flow-graph panel is actually being tracked right now" — they diverge if you click Events from panel A, then just refocus panel B directly (tracking correctly follows B, live, no reclick needed) — dockview's serialized params still say A. So `trackedPanelId` itself now also persists in this slice, mirrored the same way `snapshot` is; on mount, `reduxTrackedPanelId ?? initialTrackedPanelId ?? null` — Redux wins when present (the accurate signal), the params hint only still matters for true cold start, before this slice has ever been written to. Degrades safely if the persisted id points to a panel that's since closed, with no extra guard needed: `dockviewApi.getPanel(trackedPanelId)` returns `undefined`, the existing snapshot-update branch already no-ops on that, so `snapshot` just stays frozen on its last good value.

**Explicitly not this PR:**

- A generic "open this in its own panel" capability — `EventDetails`' existing "open in main tab" button has nothing to route to yet, since there's no dockview panel kind for arbitrary/non-artifact content (unlike `json-definition`, which is flow-definition-specific). Newly _possible_ now that `DockviewApiContext` reaches everywhere, but a real separate feature — see the "Candidate next chunks" note below.

#### PR 18 Simulate — author a sim from a run - merged (#301)

Renames the Flow Graph panel's toolbar "Sim" button to **Simulate**, and gives it an actual authoring flow — today it only pulls up a mostly-static sidebar. v1 is scoped to exactly what sims already support: a single base run (`parentRunId`) plus a `reuse` list of step ids, no individual output mocking yet.

**Design landed on, via discussion, before any implementation plan:**

- **Rename "Sim" to "Simulate."** The button's primary job is trending toward _doing_ something (authoring), with viewing an existing sim's info becoming the secondary case — a noun-named button ("Sim," like "Settings"/"Problems") fits viewing, not authoring. Cheap and reversible either way — one label, no logic change — but worth doing now rather than after the authoring flow exists and the mismatch is more visible. `RunToolbar.tsx`'s existing button/prop just gets relabeled; `onOpenSim` stays the handler name.
- **Precedent found and reused, not reinvented**: the old (pre-dockview) route-based flow — `pages/sims/CreateSim.tsx`, `components/sims/SimsFlowView.tsx`, `SaveSimButton.tsx`, `sims-slice.ts` — confirms the actual save payload: `postSim({ flowId, flowVersionId, parentRunId, reuse: string[], name, description? })`. `SimsFlowView.tsx`'s own separate React Flow renderer is **not** ported — `FlowGraph.tsx` (already used everywhere in the new Explorer) already accepts `reusedStepIds` and already visually marks them, so authoring reuses it directly instead of maintaining two graph renderers.
- **Entry point: the Simulate tab's empty state.** Today it's a static "This panel isn't viewing a sim." When there's a real run loaded and no sim yet, that same spot gets a way to start authoring one from this run instead — same button, same tab, branching by context, rather than a second button.
- **No graph-click mode overload.** Node clicks keep their one existing meaning (select/inspect a step) the whole time, authoring or not — never repurposed to mean "toggle reuse." This was considered and deliberately rejected: overloading a click with a second, invisible-state-dependent meaning is exactly the "accidentally did the wrong thing" problem tool-mode toolbars (cursor vs. pan, considered and explicitly not built here) exist to solve, and this flow doesn't need that machinery.
- **The reuse decision happens on Step Results, via a switch that already exists.** `components/flow-version/StepResultsTab.tsx` already has a `Switch` for "Reuse" (`isReused`/`onToggleReused` props) — currently always disabled in the new dockview UI, per its own comment, because `onToggleReused` is never passed. Wiring that through live while authoring is active means deciding reuse happens exactly where you're already looking to inspect a step, no separate selection surface needed. Its visibility gate (`effectiveIsReused !== undefined`) means every eligible step needs an explicit `true`/`false` passed while authoring, not left `undefined` — otherwise a step nobody's touched yet wouldn't show the switch at all, not just show it unchecked.
- **`parallel`/`join` steps: no switch rendered at all while authoring**, not merely disabled — same exclusion the old flow had, but re-homed here now that clicks aren't what gates it. The engine doesn't support reusing these pure-control-flow steps today; may be revisited later, not this PR's problem.
- **Persistent anchor: a new, separate top-center `Panel`, not the existing bottom-center `RunToolbar`.** `FlowGraph.tsx` already renders its toolbar via `@xyflow/react`'s `<Panel position="bottom-center">` — a library primitive that supports multiple independent panels at different positions at once. A second, small `<Panel position="top-center">`, visible only while authoring, holds a step-count and Save/Cancel — compact, not a full bar. This is the piece that solves "I lose track I'm authoring if I go inspect a different tab": it renders independent of the rail/side-panel, so switching to Problems or Step Details to look around never hides it. Kept as its own new component rather than added to `RunToolbar`, since it's authoring-specific and temporary, not a permanent toolbar member like Sim/Params/Events/Run.
- **Save opens a `Dialog` for name + description, not an always-visible inline form.** `Dialog` already exists as a UI primitive (`components/ui/dialog.tsx`, already used in `FlowVersionArtifacts.tsx`) — Name (required, blocks confirm if empty) and Description (optional) live there, and confirming is the actual `postSim` dispatch. Not really "double save": the toolbar's Save declares intent to finish, the dialog collects the metadata the record actually needs — same shape as a "Save As" dialog. `description` is already a real, optional field on `PostSimsReq` that the old UI never actually surfaced (only ever collected a name) — this isn't restoring something that existed before, it's adding UI for a field that was always available.
- **Run is disabled while authoring is active on this panel**, rather than allowing a rerun (or reopening this same panel at a different run) mid-authoring and having to define what that does to an in-progress draft. Sidesteps the question entirely instead of answering it — authoring has to be finished (saved) or explicitly cancelled before this panel's run can change at all.
- **After saving, the panel itself is unaffected** — its own `runId`/identity doesn't change, Run re-enables, and the Simulate tab just now shows the newly-created sim's info instead of the empty state (the same view every already-existing sim gets). Actually running _with_ the new sim means going to open it from wherever sims are listed (PR 15's sims-in-tree), same as any other sim — not something this panel does for you. See below for why that's deliberate, not an oversight.

**State**: the in-progress, not-yet-saved reuse selection is new fields on `flow-graph-panels-slice.ts` — keyed by `panelId`, same as `selectedParamHashes`/`sidePanelTab`/everything else there — rather than a new slice. This means it persists across reload for free, using the exact same already-wired persistence path (`explorer-persistence.ts`'s existing `flowGraphPanels` field) — no new plumbing needed, unlike PR 17's EventGraph work. Deliberate: losing a half-marked authoring session to an accidental reload would be a bad experience for zero cost to avoid, given the mechanism already exists.

#### PR 19 Panel/tab identity icons - merged (#302)

Ties each dockview panel/tab (and the tree row it came from) to the _kind_ of thing it actually is — a plain flow graph, a run, or a sim — with a small colored icon, rather than relying on tab-title text format alone. Cosmetic, but a real, already-felt pain point: today's titles distinguish these only by format (`"{version} Graph"` vs. `"{version} — {timestamp}"` vs. `"{version} — {sim.name}"`), so a run and a sim can look identical at a glance. This is PR 18's "general 'what am I looking at' signal" note, now scoped.

**Design landed on, via discussion, before any implementation plan:**

- **Icon reflects the entity kind a panel was opened as, fixed at open time — never the panel's current/live state.** A plain flow-graph panel keeps its flow-graph icon even after you run something from inside it; a run-opened panel keeps its run icon even if that run incidentally used a sim; a sim-opened panel keeps its sim icon. Simpler than tracking "what's currently applied" live, and matches the same fixed-at-creation identity model panel ids already use (`explorerPanelId()`).
- **Explicitly not showing an in-progress sim draft as its own marker** — not yet, at least.
- **Deliberately narrower than a full breadcrumb/status system.** The goal here is just tying a dockview panel concretely back to the tree item it represents. Fuller status signaling (a sim applied to a run, which run, etc.) stays a separate, later, more detailed idea.
- **Verified**: tree rows for Flow Graph/JSON Definition already have their own leaf-level icons (`NetworkIcon`/`CurlyBracesIcon`, `ExplorerVersionRow.tsx`), but individual run/sim rows have _no_ icon today — `HistoryIcon`/`BotIcon` currently sit only on the "Runs"/"Sims" _group-header_ rows. Decision: move those two icons down to each individual run/sim row (the actual leaf identity), and give the group headers a plain, undifferentiated folder icon instead — mirroring the convention from VS Code (and its file-icon theme extensions): containers get a generic folder glyph, only leaf items get a distinguishing icon. Concretely, the Runs/Sims headers get lucide's `Folder`/`FolderOpen` pair, switching with their own existing `isRunsExpanded`/`isSimsExpanded` state — same open/closed-folder convention VS Code uses.
- **Color, deliberately not tuned carefully — structure over polish for v1, adjustable later via a one-line `className` change per icon:** flow-graph (plain) = `text-blue-400`, json-definition = `text-yellow-400` (kept distinct from the `amber-600/700` already used for warnings elsewhere), sim = `text-violet-400`, run = `text-rose-400`. Deliberately avoided colors already carrying a different meaning in this app: red/amber-600+ (destructive/warning), green (the Run button's own action color), cyan (problems-count/eval badges). Single class per icon, no separate light-mode variant — this app's light mode hasn't had a real pass yet (dark mode is the primary dev target), so that tuning is deferred along with the rest of the eventual light-mode work.
- **`OpenPanelRequest`'s `"flow-graph"` variant gets a real discriminated sub-field, not optional fields.** Verified via `ExplorerTabContent.tsx`: `kind` already means "which component renders this panel," and plain/run/sim all render the exact same `FlowGraphPanelContent` today — so splitting `kind` itself into three variants would conflate two different axes (which renderer vs. which identity). Instead, `kind: "flow-graph"` stays a single variant, and its `runId?`/`simId?` optional fields become a proper nested union:
  ```ts
  | {
      kind: "flow-graph";
      label: string;
      versionId: string;
      openedAs:
        | { type: "plain" }
        | { type: "run"; runId: string }
        | { type: "sim"; simId: string };
    }
  ```
  Named `openedAs` (not `subject`/`entity`) specifically to name the _behavior_ — fixed at open time — not just the data shape. Leaves room for a genuinely future, separate idea (e.g. a context-menu action opening just the event graph for a specific run) as a new `kind` value later, orthogonal to `openedAs`.
- **No persistence version bump for this shape change.** The persisted dockview layout embeds each panel's `params`, so existing sessions have old-shaped (`{runId?, simId?}`) params on disk. Explicitly decided not to bump `explorer-persistence.ts`'s envelope version to invalidate them — this app has exactly one user (solo dev, alpha stage), so a manual `localStorage`/`sessionStorage` clear is an acceptable one-time fix if old panels render oddly after this ships, rather than adding version-bump churn this early.
- **Mechanism**: `dockview-core`'s `tabComponent` (parallel to the existing `components` content map, but for the tab itself), fed the same identity info already known at each of `ExplorerTree.tsx`'s three `openOrFocusPanel` call sites via `openedAs`. Confirmed greenfield — no `tabComponents` prop is registered on `DockviewReact` today, so this is new wiring, not extending an existing pattern.

**What actually landed, plus what changed from the plan once it was actually in the browser:**

- The design above landed as planned: `explorer-panels.ts`'s `openedAs` union, `explorer-tab-icons.ts` (icon+color constants plus `getExplorerTabIcon()`), `ExplorerTab.tsx` (wraps dockview's own `DockviewDefaultTab` with a colored icon prefix, rather than reimplementing its title/close/drag handling), tree-row icon relocation and coloring, and the Runs/Sims group headers becoming a plain open/closed `Folder`/`FolderOpen` glyph.
- **One real gap found only once wired up in the browser, not caught during planning**: registering `tabComponents={{ [EXPLORER_PANEL_COMPONENT]: ExplorerTab }}` on `DockviewReact` did nothing visible — dockview requires each individual panel to opt into a tab renderer via its own `tabComponent: string` field at `addPanel()` time (`PanelOptions.tabComponent?`), and `openOrFocusPanel()`'s `addPanel()` call never set one, so every panel kept using dockview's built-in default tab regardless of what was registered in the map. Fixed by switching to `defaultTabComponent={ExplorerTab}` instead — the fallback used for any panel with no `tabComponent` set, which fits better anyway since every panel in this app is meant to use the same tab renderer; no per-`addPanel()`-call wiring needed.

#### PR 26 Run Input Params — curated picker for sim-opened and plain panels

Sims and a plain (no run/sim) panel both keep an editable Run Input tab, unlike PR 25's run case — this PR is the picker improvements that only matter where editing still happens.

- **Sim seeding is not new mechanism, just a wider gate on PR 25's, blocking the same way.** By the time seeding would fire, a sim-opened panel's `runId` (Redux) already equals `parentRunId` — the existing sim effect sets that before this runs. Widening PR 25's seeding query/effect gate from `runOpened && runId` to `(runOpened || simId) && runId` makes it fire for sims too, reusing the same `paramsSeeded` reducer and one-shot ref — and the same `paramsLoading`/`paramsError` blocking treatment as PR 25's read-only case, not a quieter "seed in behind an already-interactive picker" mode. Considered rendering the picker immediately and seeding in silently (a sim panel is technically usable without seeded defaults), but decided against it: the risk is a user actively editing the picker just as a seed dispatch lands underneath them, which is worse than a brief, consistent loading state — even though in practice the fetch will usually resolve before the tab's ever selected. `readOnly={runOpened}` stays separate and untouched, so sims still end up editable once seeding completes, runs still don't. A plain panel has no run to seed from at all — starts empty, as today, since neither `runOpened` nor `simId` is set for it.
- **Restore-to-original, deferred.** Once a seeded sim param is edited, a way to restore it back to the parent run's original value (per-field or all-at-once) would be genuinely useful — explicitly deferred, not in this PR. Named here so it isn't lost.
- **Artifact list scoping — a second, separate query, not a replacement.** `use-flow-graph-panel.ts`'s existing `useListArtifactsQuery()` (unscoped) must stay exactly as-is: `FlowVersionRunParamRow.tsx` uses that same `artifacts` list for _lookup_ (the currently-selected hash's label, in both the read-only and editable rows) as well as for candidates today, and narrowing it to `{flowVersionId, curated: "true"}` in place would break PR 25's read-only label display for any run whose actual param artifact isn't curated (a plain upload, a prior step's output, etc.) — the exact same non-curated-lookup problem already named for PR 27. Instead, add a _second_ query scoped to `{flowVersionId: versionId, curated: "true"}` (matching `use-artifact-panel.ts`'s pattern), exposed separately (e.g. `curatedArtifacts`) and used only to build the editable picker's candidate list.
- **Curation filtering — additive prop, no fork, using the new list for candidates but the old one for existence checks.** New `curatedOnly?: boolean` on the existing shared `FlowVersionRunParamRow.tsx` plus a new `curatedArtifacts` prop, filtering _that_ list by `paramCurations` for this exact `(versionId, paramName)` pair. If that set is non-empty, show only those; if empty, no special-cased empty state needed — the `Select` naturally has nothing to pick beyond its existing placeholder, and the adjacent create-shortcut (below) is the obvious next move. The existing "selected artifact unavailable or incompatible" warning must keep checking existence/compatibility against the full (unscoped) `artifacts` list, not the curated one — otherwise a sim's freshly-seeded-but-uncurated param would falsely trigger that warning the moment seeding completes, which is exactly the common case, not an edge case. Old-mode's caller never passes `curatedOnly`/`curatedArtifacts`, so old-mode is unaffected — same safe, additive shape as PR 25's `readOnly`.
- **Create-from-picker shortcut, kept out of the shared component entirely — not optional.** `useDockviewApi()` throws if called outside `DockviewApiContext.Provider` (verified directly in `explorer-dockview-context.ts`), and old-mode's `FlowVersionRun.tsx` page has no such provider anywhere in its tree — no dockview, no tree, no panel-open mechanism at all, since it predates the dockview rework entirely. A hook call executes unconditionally regardless of props, so the create-shortcut (which needs `useDockviewApi()` + PR 24's `CreateArtifactDialog`) can never live inside `FlowVersionRunParamRow.tsx`, even prop-gated. Instead, the row gains a generic `extra?: React.ReactNode` slot, rendered alongside its existing Preview/Show-usages buttons — `ParamsTab.tsx` (dockview-only) supplies the actual "+ new artifact" button through it, pre-scoped to this `versionId` with this `paramName` pre-checked in `CreateArtifactDialog`'s curation field.
  - **Temporary, tied to old-mode's continued existence — not a pattern to keep.** Once old-mode's pages are retired, `extra` should be deleted and the create-button implemented directly inside `FlowVersionRunParamRow.tsx` — there'd be no more "shared with a non-dockview page" constraint to route around at that point.
  - **Auto-select on success needs to work for both of `CreateArtifactDialog`'s paths, including the one that hands off to a separate panel — real cross-panel plumbing, deliberately chosen over restricting the shortcut to upload-only.** The upload path creates synchronously inside the dialog, easy to auto-select from directly. The author path closes the dialog immediately and opens PR 24's independent, singleton-per-version authoring panel — the actual creation happens later, inside _that_ panel's own save handler, with no existing connection back to "which param, in which flow-graph panel, asked for this." Mechanism: a new optional `returnTo?: { panelId: string; paramName: string }` field on the `artifact-authoring` variant of `OpenPanelRequest` (`explorer-panels.ts`). The create-shortcut calls `openOrFocusPanel` with `returnTo` set to this flow-graph panel's id and param name; the tree's existing plain "+" keeps omitting it. `use-artifact-authoring-panel.ts`'s `handleSave`, on success, dispatches `paramHashSet({ panelId: returnTo.panelId, name: returnTo.paramName, hash })` in addition to its existing "open the new artifact's viewer panel" behavior.   - **Two accepted edge cases, not solved further** — both are the singleton-per-version authoring panel (PR 24's deliberate design) not holding up perfectly under this new reuse, not new problems: if two different flow-graph panels for the same version both use the create-shortcut before either saves, the second's `returnTo` silently overwrites the first's (same panel, refocused) — the first's request is just abandoned, not queued or errored. **What actually landed, plus two real follow-up rounds found from actually using it — a content-type mismatch that could fail a save outright, and an unrelated resize bug surfaced along the way:**

Fixed with `className="min-w-0"` on the 70% `ResizablePanel` (when the side panel's open) and `min-w-0` on the plain `flex-1` wrapper div (when it's closed, a different, simpler layout branch with the identical underlying cause).

Verified: typecheck/lint/202 vitest tests, plus manual browser testing of both rounds.

### Further out still: generic/preview Flow Graph panel, unresolved

Surfaced while discussing PR 14's runs list — specifically, whether arrow-keying through it should open a pile of new tabs or browse in place. That turned out to be one instance of a bigger, still-unsettled tension that applies to Flow Graph panels generally, not just runs: sometimes a tree click should pin its own tab (today's dockview default — click a run, get a new panel), and sometimes it should load its content into a fixed slot the tree just re-points at whatever's selected, closer to how the old page-based Run/View/Edit modes worked. The discussion got specific enough to be worth recording precisely, even though whether/when to build it is still an open call:

**The core idea**: borrow VS Code's file-explorer preview-tab behavior, precisely. Single-clicking a run/sim/version in the tree loads its content into _one_ reusable Flow Graph panel (swapping content via dockview's `updateParameters`, not spawning a new panel) — this panel is the "preview." An explicit pin gesture (a modifier-click, right-click, or shortcut — VS Code's own equivalent is double-clicking the tab) promotes it into its own permanent, separate tab, the same identity-per-target model PR 14/15 already built. The two live side by side, not as a global mode switch: previewing and pinning are just two different gestures available on every click, so the tree's own behavior stays consistent regardless of which one gets used.

**The "dirty" rule**: a preview panel gets implicitly promoted (stops being reusable, a fresh preview opens for the next click) once it's "dirty" — but dirty means a _value-changing_ action, not any interaction. This already maps cleanly onto existing reducers: `runSubmitted` (pushing Run) and `paramHashSet` (setting a param) would set it; `stepSelected` and `sidePanelTabSet` (selecting a node, switching side tabs) never would, specifically because inspecting a step needs to keep working while browsing in preview mode. A future real editing action would also dirty it, but there's no edit path to wire yet — a placeholder, not a gap.

**Why this would be close to the opposite of PR 14/15's pattern, not an extension of it**: those gave every run/sim a _stable, permanent_ id specifically so they coexist as separate tabs; a preview slot needs one _reusable, disposable_ id whose content swaps underneath it. That means: a new `isDirty` field on `FlowGraphPanelState` (small, mechanical, fully unit-testable alone); tracking which panel id is currently "the preview" as new state; the tree's click handlers branching between reuse-the-preview and spawn-a-pinned-panel; and, the one genuinely unproven mechanic, `Content.tsx` needing to re-derive cleanly when its own identity (versionId/runId/simId) changes underneath an already-mounted instance — including resetting per-panel Redux state (`selectedStepId`, `selectedParamHashes`) on a fresh preview load, a real behavior change from how a pinned panel's state persists forever today by design.

**Suggested build order if/when this happens**: the `isDirty` field first, completely alone (reducer tests, no tree/dockview involved) — lowest risk, nothing else depends on getting it wrong. Then spike the `Content.tsx` re-derivation-without-remount question in isolation, before writing any tree-click logic around it, since if that doesn't work cleanly (might need a forced remount via a `key` trick instead, with its own refetch/flicker tradeoffs) it changes the shape of everything built on top. The tree-click branching and panel-reuse logic last — least unit-testable part (dockview panel lifecycle + click behavior), mostly verified by hand.

**A possible shortcut for one other unscoped thing, not a separate concern**: sim authoring could piggyback on this same generic panel (mark reuse, save as a sim, no dedicated authoring page needed, mirroring how the old Sims page's authoring mode already reused Run History's own viewing pieces). Not scoped — named so the connection isn't lost.

**The concrete case that surfaced this section's relevance for authoring, not just viewing: Simulate on a blank Flow Graph panel.** Today it just says "Open a run to simulate from it," since authoring needs a real parent run and there's no concept yet of attaching one to a panel that hasn't run anything itself. Two candidate mechanisms floated, not decided between: (1) drag a run from the tree onto a blank Flow Graph panel to load it; (2) a "select a run" button in the Simulate tab that arms a tree-click-selection mode, applying either immediately or via a preview step first — mechanism (2) is really this section's preview/pin tension wearing a different hat, not a separate design problem. A plain dropdown was considered and rejected for (2): doesn't scale once a flow version has hundreds of runs. Deliberately not its own numbered PR — parked here since it's downstream of this section's bigger, still-unresolved tension, not separable from it. No dedicated planning pass until either this section resolves or a real need to jump ahead of it shows up.

**A related identity tension surfaced and resolved, not left open here**: PR 16's `EventGraph` panel hit exactly this same permanent-vs-mutable-identity tension from its own side while being built — a first design keyed it off `sourcePanelId` and inherited the same fragility described above (stale data after a source panel closed and reopened, drift between a rerun's EventGraph and a freshly-opened dedicated panel for that same run). Rather than build the per-instance identity tracking this section describes as the real fix, PR 16 sidestepped the whole question: it became a dockview-focus-following singleton instead of a per-target panel, which has no persistent identity to keep in sync in the first place. See PR 16's entry above for the resolved design. That dodge doesn't generalize back to this section's own problem, though — a singleton, focus-following _Flow Graph_ panel is a materially different, bigger change than a singleton EventGraph (it's the primary editing/comparison surface, not a secondary drill-in view), so this section's tension is still real and still unresolved on its own terms.

Explicitly in flux, not a plan — a refinement here is expected at some point, exact shape and timing undecided: building it now means anything built after fits it naturally and the eventual rewrite is smaller; deferring means moving faster today at the cost of more rework later.

## Process note

### Workflow for this arc, per PR

The rhythm each PR Log entry above actually follows: discuss the idea informally first, sometimes at real length with research baked in (PR 9's rail-shell design, or PR 14/15's Sims discussion) and sometimes brief (PR 10, PR 12) — then write the PR's idea down here, succinctly but completely enough to plan from (including for an AI picking this doc up cold later), _before_ any implementation plan gets made. Only after that: a real implementation plan, then building it, then reviewing/testing (typecheck/lint/vitest plus manual browser testing), then writing "What actually landed" (before or after opening the GitHub PR — either order, whichever fits), then the PR itself, then marking the heading "- merged (#N)" once it's actually merged. The write-down-the-idea step is the one easiest to skip under time pressure — worth resisting, since it's what lets a plan get made from this doc alone later without re-deriving the discussion.
