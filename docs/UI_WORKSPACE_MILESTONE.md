# Flow-Version Workspace UI Rework

## Summary

This is the direction doc for the ongoing rework of `apps/web-app` away from a page-navigation web app toward a flow-version-centric workspace: drill into one flow version, and work with it entirely through panels/tabs for whichever mode you're in (Edit, View, Run, Run History, Sims, Artifacts, Evals) — rather than navigating to separate top-level pages for runs/sims/artifacts/evals that all have to be manually cross-referenced by id.

Not everything below is equally fleshed out. The point of writing it now is to capture the parts that _are_ settled (so they don't need re-deriving later) and name the parts that aren't (so they read as open, not forgotten). This doesn't map to a single GitHub Milestone or version bump — each concrete chunk below (starting with Run History) is its own small, closeable milestone; this doc is the throughline connecting them.

## Overall idea and purpose

The core problem with the current page-based UI: nearly everything lives at the "list all runs / list all sims / list all artifacts" level, globally, with no real organizing entity underneath it. That's the wrong default — the actual daily unit of work is _one specific flow version_. The rework makes that the primary workspace:

- **Flow version = the primary workspace.** Drill into one, and within that single context: edit it (if still a draft), run it, view its run history, create/view sims of it, browse/create artifacts scoped to it, construct and run evals against it — all via panels/tabs inside one persistent shell, VS-code-style (frames with tabs, panels loading different content).
- **Flow (all versions) = one level up.** Comparing sims/runs/artifacts/evals across every version of one flow — needed, but not the primary workspace.
- **Global (all flows/all runs/etc.) = top, rare.** Useful sometimes as a filterable escape hatch, but explicitly not where work usually happens — today's UI is almost entirely this level, which is the concrete reason it's been "not very useful."

Longer-term context worth keeping in view even though it's not being built yet: the eventual target runtime is Tauri (not just a browser tab), with real multi-pane coexistence (view + edit + preview at once, like an IDE) rather than one panel at a time, and an explicit non-goal of supporting small/phone-sized screens — the panel/toolbar model is inherently a desktop pattern. Also an explicit constraint: this UI is being hand-designed and understood, not generated wholesale by an AI/design tool in one shot, the same ownership stance as the rest of this codebase.

## What's already built

- The routing shell: `/spike/:flowId/:versionId/<mode>` via `FlowVersionWorkspace` (real flow-version fetch) + `FlowVersionModeNav`, replacing the old flat `Spike.tsx` prototype. One persistent shell, one `Outlet` per mode, state scoped per mode rather than globally.
- **Edit / View modes**: routed and rendering (flow graph + JSON view, step details, settings/params/problems panels), but not yet functionally distinct from each other — Edit isn't actually editable yet. Matches the concrete panel pairing already envisioned: flow graph + JSON definition for authoring context.
- **Run mode**: fully working end to end — submit a run, watch it live (websocket-fed events, no polling), an animated flow chart showing live step status (pending/running/completed/failed) derived client-side from the run's own event stream, a params panel with artifact selection, and a preview feature showing how a selected param actually resolves everywhere it's referenced in the flow (including refs embedded in larger template strings). Matches the other envisioned panel pairing: flow graph + step execution detail for run/inspection context.
- **Step Results** (Run mode's right panel, PR #261): status, Output & Exports, Field Resolution (a field's final value with every `{{...}}` ref in it substituted, composed across multiple refs in one field), and References (each individual reference's own resolved value) — all sourced from the run's own event stream, deliberately with zero dependency on `job.<cap>.submitted`'s payload shape (see `docs/todo.md`).
- Reusable pieces this unlocked for later modes: `EventGraph` (decoupled from any one page's state, takes events/selection as plain props), `deriveStepRunInfo`/`useStepRunInfo` (a pure fold over any event array, not tied to live-only data — status plus output/export hashes), `findStepRefs`/`resolveRefHash`/`foldResolvedField` (`lib/ref-resolution.ts`, also event-array-agnostic).
- **Run History mode**: fully built across 3 small PRs (#262, #263, #264) — a flow-version-filtered run list (`listRunsByFlowVersionId`), a left-panel run list wired to routing with REST event backfill on selection, and Run mode's own graph/details panels (`FlowVersionRunGraphPanel`/`FlowVersionRunDetailsPanel`, `StepResultsTab`) reused as-is, fed by the selected historical run's events instead of the live one — confirmed those panels needed zero changes, since they were already pure props-in/callbacks-out with no coupling to the live Redux slice. Also produced two small shared extractions used by both Run and Run History: `useRunEventsWithStatus` (events backfill + `deriveStepRunInfo`, identical logic regardless of live vs. historical) and `lib/run-panel-state.types.ts` (tab/focused-content types hoisted out of the live slice, since they were never actually live-specific — each mode still keeps its own independent slice state, no shared/merged state between modes).
- **Sims mode**: fully built across 5 PRs (#265, #266, #267, #268, #269) — see "Sims mode" section below for the full design narrative (state machine, placement decisions, corrections). Summary: authoring a new sim reuses Run History's graph/details pieces with an added reused-step toggle; browsing _is_ viewing (the sim list stays visible and freely re-pickable, same pattern as authoring's run list, auto-defaulting to the most recent sim); a Settings tab (first, default-selected) shows a viewed sim's full name/description and its fork spec's raw parent run id, hidden while authoring. Two small polish passes landed in the same arc: a `FlowVersionSimsList` display fix (long descriptions were pushing the date off the row — now two independently-clamped lines instead of one shared block), and the reused-step switch showing (disabled) while browsing instead of only appearing during authoring.
- **Explorer arc, PR 1 of several** (merged #284) — not a finished feature, one small piece of an arc still in progress: a `/explorer` page with a real-data Flow → Version tree, no tab host or further tree levels yet. See the PR Log below for what this was and what's next.

## Sims mode (built — design narrative kept for the "why")

**Reuse target correction, settled in discussion**: this does _not_ reuse the old `RunnerSimSelector`/`Sims.tsx`/`CreateSim.tsx`/`ViewSim.tsx`/`SimsFlowView` components (as this doc previously assumed) — those are old-UI pieces bound for their own redesign, and today's step-reuse selection there is genuinely blind (toggles a step by ID/color on the static flow-def graph, with zero visibility into the parent run's actual output/exports). Instead, this reuses the _new_ flow-version-workspace pieces Run History just built: `FlowVersionRunHistoryList`, `useRunEventsWithStatus`, `FlowGraph`+`stepRunInfo`, `StepResultsTab` — the same "reuse is not the goal" distinction applies app-wide, delineating old components not worth carrying forward vs. new workspace pieces actively being built and reused hard.

**Backend needs no schema changes for the minimal version**: `Sim` already has a required, indexed `flowVersionId` FK (`schema.prisma`) — the 1:1 sim-to-flow-version association already exists. `ForkSpec` (`packages/types/src/engine/fork-spec.type.ts`) is already exactly `{parentRunId, reuse: string[]}` — the minimal "reuse steps from one parent run" capability the current system actually supports. The only backend gap is `listSimsByFlowVersionId`, essentially a copy of `listRunsByFlowVersionId`'s shape (port/service/route/adapter/tests). (Separately, whether fork-spec/sim data should eventually move from a CAS artifact to queryable SQL rows is a real, still-open question — deliberately deferred, not blocking this work; see `docs/todo.md`.)

**Left pane: page-state-driven content swap, not tabs.** A bare "Runs" tab would raise a real state-machine question (disabled? hidden? until when?) precisely because Runs isn't a co-equal destination — it only matters while creating a new sim. Model it as page state instead, extending the same pattern `flowVersionRunHistorySlice` already established.

**Corrected during PR 2 planning: 2 modes, not 3 — picking a run is never a one-way gate.** Originally sketched as a linear `browsing → picking-run → authoring` flow where picking a run locked you into authoring for it. Rejected: authoring needs to support freely switching between runs _while_ authoring — comparing what different runs produced — with in-progress reused-step selections and the currently-inspected step (both PR 3) surviving the switch. So:

- **browsing** → left pane shows the sim list (filtered by flowVersionId), with a "New" button
- **authoring** → left pane becomes the run list (`FlowVersionRunHistoryList`, reused as-is) and _stays_ there for the whole time you're authoring — not swapped away once a run's picked. `selectedRunId` is just a freely-updatable field within this mode, not a transition trigger; re-picking a different run updates the main content live. Main content becomes the graph+details view for marking/inspecting reused steps (PR 3); Save or Cancel returns to browsing.

**Interaction: node click means only "inspect," never double duty.** Marking a step reused needs a separate, explicit control — a toggle inside the details panel once a step is inspected, rather than overloading click. Built with shadcn `Switch` (not `Toggle` as originally planned — functionally the same idea, `Switch` just reads clearer for a plain on/off, and is what actually got installed). Right-click (`onNodeContextMenu`) is a clean, cheap option to add later if wanted — React Flow already exposes it as a genuinely distinct prop from `onNodeClick`, requiring only one small additive (non-breaking) prop on `FlowGraph` — but not needed for a first version, especially since this interaction is expected to get revisited once a visual flow editor exists (see `docs/todo.md`'s note on that longer-held, unscheduled goal) and nodes potentially become custom/richer.

**Authoring always shows all 3 panels, even before a run's picked — corrected during PR 3a review.** Originally the "no run selected yet" state showed a 2-panel idle-prompt layout instead of the real graph/details panels. Changed: the graph/details panels already handle empty data gracefully (no `stepRunInfo` just means unstyled nodes, `StepResultsTab` already handles `stepId === null` with its own prompt) — so there's no real reason to special-case that state with a different layout. `FlowVersionSims.tsx` now always renders 3 panels once `mode === "authoring"`, with a small "Select a run below" hint shown above the run list until one's picked.

**Where Cancel (and Save) live — moved out of the details panel, up into the left panel, above the run list.** First attempt put Cancel in the details panel's header; reconsidered because it read as context-less — not obvious _what_ you were cancelling. Left panel now shows a persistent "New Sim" header + Cancel button above the run list for the entire authoring session, regardless of whether a run's picked yet. **Sim Settings (name + description) should land here too, not as a details-panel tab as originally sketched** — same reasoning: a lone Save button in a details-panel tab would have the identical "naked, no context" problem Cancel had. Putting name/description + Save/Cancel together in the left panel, under a "New Sim:" heading, keeps a constant visual anchor for the whole authoring session ("you are creating a sim," not just "here's a random toggle"), and the buttons read as acting on something specific instead of floating alone. Built in PR 3b.

**PR 3b validation/error UI is deliberately minimal — real toast/notification system is future work.** Save requires a non-empty name, a selected run, and at least one reused step (a sim with an empty `reuse` array does nothing — enforced client-side only, `post.ts` doesn't reject it server-side, and it's not yet decided whether that validation belongs at the API layer too). Errors from a failed save render as plain inline text next to the Save/Cancel row — no toast library exists anywhere in `apps/web-app` yet. A shadcn `Tooltip` was installed while exploring a richer treatment for the reused-step hint but held off on — the plan is to revisit inline validation/error rendering once there's a unified toast/notification pattern, rather than build one-off treatments per form. Tracked in `docs/todo.md`.

**Corrected during PR 4 planning: browsing _is_ viewing — not a third mode.** First pass at PR 4 proposed a `"viewing"` mode mirroring how `"authoring"` swaps the left pane to the run list. Rejected: there's no separate viewing mode, because browsing already _is_ viewing. Exactly like authoring keeps the run list visible and lets you freely re-pick `selectedRunId` (a field, not a mode transition), browsing keeps the sim list visible and lets you freely re-pick a new `selectedSimId` field — same pattern, still only 2 modes (`"browsing" | "authoring"`). The middle/right panels stopped branching on `isAuthoring` entirely as a result — they always render now, fed by `inspectingRunId`/`inspectingReusedStepIds` (authoring's own state, or a viewed sim's `parentRunId`/`reuse` fetched via `useGetSimQuery`). Browsing also auto-selects the most recent sim instead of showing nothing, which is what makes Save land you back viewing your just-created sim automatically (`resetToBrowsing` nulls `selectedSimId`, and the list's auto-select effect picks the new latest one up immediately).

PR order:

1. **Backend**: `listSimsByFlowVersionId` — small, precedented, no design risk. Merged (#265).
2. **Scaffold**: the page + left-pane state machine above, sim list ↔ run list swap wired to real data. Merged (#266).
   3a. **Real graph/details wiring**: `FlowGraph`+`useRunEventsWithStatus`+`StepResultsTab` reused for inspection, the reused-step toggle (persisting across run switches, per the state-machine correction above), always-3-panels layout, Cancel anchored in the left panel. Merged (#267).
   3b. **Sim Settings + Save**: name/description inputs anchored in the left panel per the placement decision above, `POST /api/sims`, `sims-api.ts` cache tags so the browsing list picks up new saves. Split out from the original single PR 3 during planning — genuinely separable from 3a, and 3a alone was already a full unit of work. Merged (#268).
3. **View existing sim**: browsing-is-viewing per the correction above, plus a Settings tab (first, default-selected, hidden while authoring) showing the viewed sim's full name/description and raw parent run id. Merged (#269).

## Other bits of work (less fleshed out — sizes and shapes still provisional)

- **Edit mode, actually editable** — currently just a read-only copy of View. Real scope unknown; likely a substantial lift given flow authoring/validation/publish-state semantics aren't designed yet (e.g. whether a published version becomes immutable and editing forks a new draft version).
- **A full-step "resolved preview" view — parked, not scoped.** Raised while building Step Results: a view showing _every_ field of a step (matching `StepHttpJsonDetails`' full field list — URL/Method/Headers/Body/Exports — not just fields with refs), with each field showing its bound param value before a run and its actual resolved value after. Two distinct gaps motivate this, not one:
  - Fields with zero refs are invisible in Run mode entirely — only Edit/View's `StepHttpJsonDetails` shows them, and only unresolved.
  - Fields that _do_ have refs are only ever shown at leaf-`bindPath` granularity in Field Resolution (e.g. just `body.messages[1].content`), never composed back up into the whole logical field (`body`, `headers`) as it was actually sent — if `body` has refs at two different nested paths, Field Resolution shows two disjoint leaf rows, never one composed `body` object with both substitutions sitting in their natural positions. The natural grain for "the whole field, fully resolved" is the same field-level granularity `StepHttpJsonDetails` already uses; Field Resolution deliberately went finer because "what did this one reference become" wants the leaf, not the whole object.

  Also explicitly not Run-History-specific, and connects to an existing feature, not just Field Resolution: the per-param "show usages" report (`findParamRefs`/`renderParamRefReport`, `FlowVersionRunParamRow`) already lets you click a _param_ and see a markdown report of everywhere it's used — useful, but it's the reverse direction (param → its usages, leaf-level, textual report). What's missing is the other direction: click a _step_ in the live Params panel and see that whole step's fields composed with the currently-selected param artifacts filled in, ahead of submitting — same underlying resolution logic (`resolveRefHash`/`buildRefUsage`/`foldResolvedField`), organized by step instead of by param, at whole-field instead of leaf granularity. Deliberately not built yet because it's unclear how much it'd repeat Field Resolution/References; the resolution reached in discussion: judge that by whether it answers a _different question_ (a holistic "what did this step look like as one document" snapshot vs. drill-down provenance), not by whether it reuses the same underlying resolved-value logic — reusing `foldResolvedField` etc. across views isn't repetition, showing the same field list with the same framing twice would be. Needs its own design pass before it's scope, the same way Step Results got one.

- **Replay — acknowledged valuable, not scheduled (not "no reason exists" anymore).** Watching a historical run's execution animate at some controlled pace (a play-head over the event timeline instead of a range selection, reconstructing state at any point rather than just the final one) — technically straightforward given the architecture (`deriveStepRunInfo` already works on any event array, live or historical; this is UI/timing work, not new plumbing). The concrete reason it's worth building, not just "it'd be cool": it lets you re-experience the feel of watching a run live — pacing, what happened when — which a final-state view structurally can't reproduce. Still not the first thing to build; no committed timing.

## Evals: deliberately its own separate, future milestone

Explicitly not part of this arc's near-term scope — this is a real data-model rearchitecture, not a UI tab, and deserves its own milestone the same way the original eval vertical slice did (Milestone #9). Current state: evals are embedded inside the flow definition itself (an eval is just a flow with a judge step) — a smaller move than originally wanted. The actual goal: evals as standalone, reusable entities, decoupled from any one flow — a fixed template (System Prompt + Question + Context + Answer) that can be constructed and run against different flows. Inside this workspace, an Evals mode/tab would let you construct an eval run (bind the flow's actual output to the eval template's expected inputs) — results visualization might end up needing its own separate page if it doesn't fit inside that tab. Not scoped further here; needs its own dedicated design pass.

### ArtifactComposition and ComposedArtifacts

One proposal floated for solving the eval-binding problem: a more primitive object, `ArtifactComposition` — itself an artifact, but one with template references to other artifacts (plus arbitrary text) that compose together into a single output artifact, `ComposedArtifact`.

The core idea: map several artifacts into one output, which is exactly the shape needed to bind a run's outputs into an eval flow's expected inputs.

Not eval-specific, though — the same primitive could be used by any flow, and it reuses the existing artifact/templating system as a foundation rather than inventing something new. One open question: the templating language itself may need to diverge from what the rest of this system already uses, rather than being borrowed wholesale (tbd).

`ComposedArtifact`s would likely be created lazily at runtime — materialized right before a run is submitted, since that's when one is actually needed as a param input, not proactively the moment some other, related flow's run finishes.

## Global workspace / navigation direction — a real pivot, current guiding principles, not a PR

**A genuine pivot from the section below's original framing, not just a refinement — some already-built UI (the bottom `FlowVersionModeNav` mode toggle, one-mode-per-route) is expected to be redone, accepted as a real cost, not a mistake to avoid discovering.** Came out of actually using Postman (previously only judged from the outside) and recognizing it solves a closely-related problem: node-based API "Flows" plus "runs" of them, browsed via a left explorer, opened into a content-agnostic tab strip with a detail panel that follows whichever tab is active. Not tied to any single PR; meant to be revisited as building surfaces what actually works. Explicitly paused here per the user's own call, before turning this into an implementation plan — this section is the synthesis to plan from, not the plan itself.

- **The concrete shape now being aimed at: a left-side explorer tree (Flows as the root object, expanding into Versions, expanding further into that version's Runs/Artifacts/Sims/Evals) plus a dynamic tab/panel system that opens whatever's clicked, with a detail panel that follows the active tab.** This is deliberately _not_ the same thing as a flat global "all artifacts" browser — it's scoped browsing, nested under the flow/version that owns it, the same filtered-by-`flowVersionId` shape today's `FlowVersionArtifacts`/`FlowVersionRunHistory` pages already fetch. A true flat global browse (if ever built) would be a different root in the same tree, not this one.
- **A working heuristic for sorting which of today's modes become tree branches vs. stay closer to a standalone action**: is this mode fundamentally _a list you browse, then open something from_ (maps cleanly onto "tree node → tab"), or fundamentally _a distinct workflow/action_ that doesn't reduce to browse-then-open (stays more mode/form-like)? Artifacts and Run History read as the first kind; triggering a _new_ run reads more like the second. Not yet applied to every mode, just the lens to apply.
- **Naming collisions across scope levels (e.g. "Artifacts" globally vs. this-flow-version's "Artifacts") are resolved structurally by tree position, not by inventing different words.** A node nested under a specific flow version's branch is unambiguous by where it sits in the tree — the same positional-disambiguation idea considered earlier, now concrete instead of theoretical, and stronger than the earlier instinct to dodge collisions with fuller labels (e.g. `FlowVersionModeNav`'s "Run History" instead of a bare "Runs").
- **List scale/navigability is a real concern, deliberately deferred, and solved by a different mechanism than the tree itself** — confirmed by how VS Code actually handles it: a huge folder isn't made navigable by better tree design, it's made navigable by pairing the tree with a separate fuzzy filter/search that skips the hierarchy entirely. Filtering matters, just not before there's enough real content for it to bite.
- **Picker-mode vs. browse-mode clicks (e.g. selecting a Run as input while creating a Sim, vs. normally opening a Run in a tab) is a real, already-solved-elsewhere interaction pattern, not a new kind of problem.** Native file-picker dialogs reuse the same file browser with different click semantics; this codebase already has the matching mechanism (a dumb component driven entirely by whichever callback prop the caller wires up — `FlowVersionArtifactsList`'s `onSelectArtifact`, `SelectField`'s `onChange`) — the tree explorer would need the same `onOpen` vs. `onSelect` treatment, not a new pattern invented from scratch. Selecting in picker mode should highlight the item rather than navigate, giving clear "this is now chosen" feedback without leaving the current flow.
- **State/lifecycle implication, genuinely underappreciated at first**: today, switching modes is a real route change — the previous mode's component tree unmounts, the new one mounts fresh. A tab that's merely hidden and re-shown never does that. Several patterns built this session specifically lean on real unmount/remount timing and will need rethinking, not just porting: the `useLayoutEffect`-on-mount trick that clears a stale file breadcrumb in the upload panel only works because navigating away and back today genuinely destroys and recreates that component; hoisting `authoringDraft`/`draft` into Redux instead of local `useState` was specifically to survive an unmount tabs wouldn't cause in the first place.
  - **Deeper implication**: today's Redux slices assume exactly one "current" thing (one `authoringDraft`, one `draft`). If tabs ever allow two instances of the same content type open at once (two "create a sim" tabs, two artifact viewers side by side), a singleton slice stops being a coherent model — it becomes "which tab's draft is this," needing per-tab-keyed state instead of one shared slot. **Legitimate, deliberate scope-narrowing available here**: not supporting multiple simultaneous tabs of the same content type is a fine constraint to ship with initially (matching this arc's general "defer until a real second need proves it's needed" practice) — today's singleton pattern can keep working largely as-is under that constraint, with per-tab-keyed state only needed once/if true multi-instance is actually wanted.
- **Sequencing to actually build this**: the left explorer + flow browser view first, since it's the root that drives everything else, built _alongside_ (not before, not fully after) the smallest possible tab/panel skeleton — a single tab strip, open/close/switch only, no drag, no split, no reordering, singleton-per-content-type state — so that clicking something in the explorer has somewhere real to land without either piece being fully built in isolation from the other. Same "build one real page, let the pattern emerge from it" instinct already used elsewhere (e.g. not building `DebouncedCodeEditor` until a second real caller existed).
  - **Deliberately not adopting a docking/tab-management library yet** (real options exist and are worth remembering later — `dockview`, `flexlayout-react`, `rc-dock`, all mature VS-Code-style docking libraries with drag/split/serializable layout). What they solve — drag hit-testing, drop zones, resize, layout serialization — was never the uncertain part; what's actually still unresolved (picker-vs-browse semantics, singleton-vs-multi-instance state, how the detail panel follows the active tab) is domain-specific and a library wouldn't resolve any of it. Revisit once the simple skeleton's real limits are actually felt, not before.
- **What this pivot does and doesn't invalidate, worth being explicit about since it's a real cost being accepted, not glossed over**: the backend (services, ports, adapters, routes, RTK Query endpoints — the majority of the actual engineering effort in this arc so far) is completely presentation-paradigm-agnostic and unaffected. Field-level components (`InputField`, `SwitchField`, `SelectField`, `CuratedParamsField`, `IdentityField`) are equally reusable regardless of container. What's actually being redone is narrower than "the whole UI": the page-as-mounting-boundary assumption, the bottom mode toggle as the primary nav, and the small number of components whose behavior specifically depended on real route-driven unmount/remount timing.
- **Visual direction (carried over, still holds): shift from web-page density toward desktop-tool density is three separable things, not one dial** — padding/type scale; _information architecture_ (how much shows by default vs. on demand — today's artifact rows are closer to a card than a compact file-browser row); _interaction model_ (small toolbar-icon actions instead of large always-visible CTA buttons like "Add File," which stop scaling once many panels each want their own primary action). A traditional top menu bar (File/Edit/...) is explicitly not the starting interaction model — real value there is as a comprehensive fallback/index once there's enough surface to need one, not as the first way to trigger anything done often.
- **Audience/positioning note, relevant to how much this pivot is allowed to lean technical/dense**: this is primarily a developer/orchestration tool (making sims, exposing observability, etc. are inherently technical concepts) — "friendly to non-technical people" is scoped specifically to _installation_ (the Electron packaging goal — no web server or Docker Compose to set up), not to simplifying the feature set or this UI's density. No non-technical-usability bar exists that this explorer/tab direction needs to hit. If broader non-technical accessibility is ever a real goal, the natural lever is a different, purpose-built frontend sitting on the same backend (this system already treats `apps/*` as thin, swappable callers of one shared service set — the same decoupling principle, one layer up), not retrofitting simplicity onto this explorer.
- **Parked, explicitly not now: building this as a VS Code extension instead of a native/Electron app.** Real, verified upside if ever revisited — VS Code's `TreeDataProvider` API natively supports lazy-loaded custom tree views (matches the explorer idea's own lazy-expansion need), and `QuickPick` is a genuine free answer to the picker-mode problem above. Real remaining cost: any custom visual content (flow graphs, artifact viewers) still has to be built as a Webview — VS Code gives you the tab container for free, nothing about what's rendered inside it (though `FlowGraph.tsx`'s existing React/`@xyflow/react` implementation could plausibly be reused inside one nearly as-is). Also a fundamentally developer-first distribution model (requires VS Code installed), in tension with any non-technical-user goal. Interesting long-term direction, not a near-term plan.
- **Floated, explicitly not decided, parking lot for later**: card view vs. compact list view for the flow browser (possibly both, toggleable, sequenced card-first rather than resolved up front); auto-generated flow-diagram thumbnails via React Flow's server-side `renderToStaticMarkup` (confirmed real — official docs list "dynamically creating Open Graph preview images" as a named use case; `FlowGraph.tsx` already computes explicit node positions itself rather than relying on browser measurement, which happens to fit this approach's requirements), generated at some lifecycle point (draft/version-creation/publish) and served as a plain http-server image resource, not necessarily a CAS artifact; friendly auto-generated human-readable version names ("yellow elephant"-style) alongside mechanical labels/sequence numbers; color/icon markers for flows or versions; merging "Run" and "Run History" into a single mode; System (start/stop status for the engine/worker/etc., not yet built) and Settings/Config (API keys, concurrency/limiter settings, infra choice, theme, auth — not yet built) both need a home in the eventual nav structure, with System's own operational settings (e.g. limiter tuning) possibly nesting under a System drill-down while more general preferences stay separate from any one system's runtime state.

### PR Log — revisable, each entry roughly one implementation plan / PR

These plans are forecasts, moldable and changeable — they exist to keep the thread alive across sessions about what might get built and the reasoning behind it. Detail level varies: PRs further out are typically sketched more loosely than the next one up.

Before a PR gets a real implementation plan, it usually goes through an informal phase first — investigation, research, and back-and-forth design discussion between user and AI, refining and sometimes reshaping the rough idea recorded here.

Once that settles, an actual implementation plan gets produced (via Plan Mode), reviewed and edited before anything is built. Implementation follows; afterward, it's reviewed again — in code, via manual smoke-testing of the app, and by running the build/test/lint suites.

#### PR 2 - Tab/Panel Skeleton - merged (#285)

Original notes: **The smallest possible tab/panel skeleton** — open/close/switch between tabs, no drag/split/reorder, state assuming one instance per content type.

Design settled from discussion, going into Plan Mode next — still revisable, but no longer scratch:

- **Tab registry**: a discriminated union on `kind` (`TabEntry = { id, kind, label, ...kind-specific params }`), one Redux slice holding `tabs: TabEntry[]` + `activeTabId`. Entries carry only identifying params, never fetched content — the slice is a routing table, not a cache.
- **One tab per `kind` for now** — opening a tab for a `kind` that already exists overwrites/updates that entry instead of creating a duplicate (matches the singleton-per-content-type scope-narrowing already decided above). `id` stays a separate field from `kind` even though it can trivially equal it today, so relaxing "one per kind" later (multi-instance) is a reducer-logic change, not a storage migration.
- **One action per user intent, not a setter chain** — `openOrFocusTab` creates-or-updates the entry _and_ sets `activeTabId` in a single reducer case (Immer lets one case touch multiple fields); a plain reducer can't dispatch further actions itself regardless, so there was never really a "should a setter also dispatch" question.
- **Rendering**: a dispatch-on-`kind` switch maps a `TabEntry` to its real content component, passing the entry's params as props — the same dispatch-on-a-key idea the router already uses for `<mode>`, just relocated into Redux specifically so switching tabs doesn't cause a real unmount/remount. RTK Query calls live only inside the leaf content components, never the dispatcher.
- **Close/switch — Chrome's behavior, as a starting point, not necessarily final**: closing a non-active tab never touches `activeTabId`. Closing the active tab activates whichever tab is now at that same index (the one that "shifted into" the closed slot), or the new last tab if there wasn't one to its right. Zero tabs open → `activeTabId` is `null`, content area shows a plain placeholder message (unstyled for now).
- **Layout reuses `components/ui/resizable.tsx`** (`ResizablePanelGroup`/`ResizablePanel`/`ResizableHandle` — already installed, already used by nearly every existing `FlowVersion*` mode page) — the PR 1 tree in one resizable panel, a tab strip + content area in the other, both on `/explorer`. No right panel this PR.
- **Right panel explicitly deferred, re-confirmed after real discussion, not just left ambiguous.** Real complexity worth remembering precisely for whenever it's built: today's right panel reacts to one axis (clicks inside whatever page a mode mounted). Once tabs exist there will be two axes — which tab is active, plus whatever's clicked inside that tab's own content — and the panel needs to react to both, not just the one it handles today.
- **First real test uses a placeholder content `kind`, not a real content type** — proves open/close/switch works before PR 3 wires in real content. The trigger is PR 1's existing tree-row click (today it only sets `selectedRowId` for highlighting); this PR extends that same click to also dispatch `openOrFocusTab`, so the tree stops being purely cosmetic.
- **Still explicitly deferred, unchanged from before this discussion**: adopting a docking/tab library (`dockview`/`flexlayout-react`/`rc-dock`); tab-list persistence across a real page reload (a nicety for later, not blocking); movable tabs / multiple instances of the same content kind (the long-term want named in the Global workspace section above, still not this PR).

**Refined after actually using it, not just planned in advance**: Flow rows in the tree now always toggle expand/collapse on click and never open a tab — resolved a real tension (a click can't simultaneously mean "browse" and "open" without ambiguity) the same way VS Code resolves it for directories. Since that leaves no way to view/edit a Flow's own metadata, a fixed **Settings** row was added as the first child under an expanded Flow — a literal tree leaf, not a new interaction mechanism, reusing the exact same "leaf opens a tab" behavior everything else already had. This container-never-opens/leaf-always-opens split is now the tree's general rule going into PR 3, not just a Flow-specific fix. The now-unreachable `placeholder-flow` tab kind was removed as a result.

#### PR 3 - Content In Tab

Original notes: **Land the first real content type in a tab** — the flow graph (`FlowGraph.tsx` already exists), proving arbitrary existing React content can live in the new tab host cleanly, using something already built rather than something new.

Design settled from discussion, going into Plan Mode next — still revisable, but no longer scratch. Scope grew from "just the flow graph" to four real leaves, since the container/leaf split PR 2 landed on needed a second real test to confirm it generalizes, not just work once:

- **Version becomes a container**, same rule as Flow: click always toggles expand/collapse, never opens a tab. Confirms the container-never-opens/leaf-always-opens split from PR 2 is the tree's general rule, not a Flow-specific fix.
- **Four real leaves, not one** — Flow Settings (already exists as a placeholder since PR 2, now wired to real data), and three new leaves under Version: **Settings** (first child, fixed position — matches the existing Flow-level pattern), **JSON Definition**, and **Flow Graph**.
- **Both Settings leaves are read-only, and deliberately reuse the existing `Fields` components** (`InputField`/`IdentityField` etc., already built read-only-first for Artifacts mode) rather than inventing a new display pattern — even though there isn't much data to show yet (Flow: name/description; Version: versionLabel/sequence/description/createdAt). Consistency of pattern matters more here than the amount of content.
- **Flow Settings and Version Settings both use data already in memory** — `FlowRecord`/`FlowVersionRecord` are already fetched and held by `ExplorerTree`/`ExplorerFlowRow`/`ExplorerVersionRow` today (that's what renders the tree rows' own labels) — no new query needed for either.
- **JSON Definition and Flow Graph both need the actual flow definition fetched** — `getFlowVersionDef`/`useGetFlowVersionDefQuery` already exists (`GET /flows/versions/:versionId`) and is unused by the Explorer arc so far. Whether both leaves share one query call/cache entry or fetch independently is an implementation detail, not a design one — RTK Query's own cache should just handle this for free either way.
- **Everything stays view-only** — no edit fields, no save button, on any of the four leaves. Matches the standing "you don't ever edit yet, only view" constraint; editing is still blocked on the undesigned draft/published/authoring flow, not this PR's problem.
- **Genuinely still open, implementation-level rather than design-level** — exact new tab `kind` names/params replacing `placeholder-version` (now dead, same as `placeholder-flow` before it); which components live where; whether Flow Graph and JSON Definition end up sharing a fetch. Left for Plan Mode, not resolved here.
