- **`pnpm typecheck` never actually checks any package's `tests/` directory, repo-wide — now has a working fix, adopted incrementally, not repo-wide yet.** Root cause confirmed: every package's `tsconfig.json` has `"include": ["src"]` only, and `rootDir: "src"` means you can't just widen `include` to add `tests` in the same config (TS errors: files must be under `rootDir`). Vitest itself doesn't backstop this either: it transpiles `.test.ts` files with esbuild by default, which strips types without checking them, and most packages' `lint` script is a no-op stub (`echo lint`) anyway.

  **The fix, landed in `packages/artifacts` and `packages/adapters` (the two packages PR 6a touched), candidate #2 from the original list below**: a sibling `tsconfig.typecheck.json` per package, extending the base config, overriding `rootDir` to `.` and `include` to `["src", "tests"]`, with `noEmit: true` for safety if ever invoked directly. The base `tsconfig.json` (and thus `pnpm build`, which calls bare `tsc` with no `-p` flag) stays untouched — `include: ["src"]` only, never sees `tests/`. `package.json`'s `typecheck` script becomes `tsc --noEmit -p tsconfig.typecheck.json`. Verified: build output (`dist/`) has zero test-file leakage either way.

  **Turning this on immediately surfaced two real, previously-invisible errors** in `packages/adapters/tests/stream/*.test.ts` — both were extensionless relative imports (`"../../src/stream/inmemory.stream-registry"` instead of `"...-registry.js"`), which fail under this repo's `moduleResolution: "nodenext"` (confirmed in `tsconfig.base.json`) but were silently fine to Vitest's esbuild-based transpilation. Fixed both (one-line, unambiguous — add the extension, matching every other import in the codebase). Exactly the failure mode this whole entry originally predicted, caught the first time it was actually turned on.

  Not yet rolled out to the other ~15 packages — deliberately incremental, adopted as packages get touched for other reasons rather than a dedicated repo-wide sweep, per the user's own call. Original candidate list, for reference: widen `include` in one config (blocked by `rootDir`, see above — this is why the sibling-config approach won), a separate `tsconfig.tests.json` (same idea, different name), or vitest's own `test.typecheck` option (not tried, would be a different mechanism — vitest running `tsc` itself rather than a separate script).

  **Related, uncovered while doing this**: `turbo.json` already defines a `clean-dist` task (`cache: false`), but before now only 6 packages (`flow-analysis`, `ports`, `json-ref-binder`, `limiter`, `observability`, `runtime`) actually implemented it as a `rm -rf dist` script — the rest, including `artifacts`/`adapters` until now, had no matching script at all. Confirmed empirically (`pnpm turbo run clean-dist` before adding it to `artifacts`/`adapters`): turbo silently skips packages missing a task's script rather than failing the run — partial/incremental adoption of `clean-dist` across packages is safe, not an all-or-nothing rollout. Motivation for having it at all: stale `dist/*.d.ts` in one package can mask a real type error in a downstream package that resolves against that stale output instead of current source — e.g. a type moved from `packages/ports` to `packages/types` can leave the old package's stale `dist/` still exporting it, so a downstream typecheck may pass when it shouldn't. `clean-dist` is manual-only for now, deliberately — no decision yet on whether/how to make it automatic before builds, since that runs into turbo's own cache/staleness model not being aware of TypeScript's separate incremental-build staleness at all (two independent caching layers that can drift out of sync). TypeScript's own project-references/composite-build feature (`tsc --build`) is designed to solve exactly this cross-package staleness problem correctly, and would be the more structural fix — but adopting it would mean restructuring how every package's `tsconfig.json` relates to its dependencies, a much bigger change than today's ask. Worth a real look whenever this bites hard enough to justify it, not now.

- Real credentials for external APIs (e.g. a paid LLM) aren't safe to use yet: a flow step's `headers`/`body` get fully resolved (including anything credential-shaped) before the `job.<capability>.started` event is emitted, so a real secret would flow straight into the replay log and the web app's event viewer — already demonstrated with a placeholder value (`"Bearer local-key"`) showing up verbatim in a pasted event. - `EvalResultProjectionSink` and `SqlRunProjectionSink` both react to the same `run.completed` event via `ObservabilityTap`, and there's a real race between them: `SqlRunProjectionSink.handle()` is synchronous and internally fire-and-forgets its own flush (`void this.#flushLoop(...)`), so it never actually signals when its SQL write for that event has landed — `ObservabilityTap` dispatching sinks in order, or even awaiting `handle()`, doesn't help, since `handle()` returns long before the write finishes. `EvalResultProjectionSink` needs that write to exist (it reads the eval run's `judge.score` export via `RunQueryPort.getRunDetail` right after `run.completed`) and can lose the race, silently producing "no judge.score export — nothing to store." Band-aided for now with a short retry-with-backoff loop inside `EvalResultProjectionSink` (`#findScoreExportWithRetry`, `packages/observability/src/sinks/eval-result-projection.sink.ts`) rather than fixing the ordering at the source, since `SqlRunProjectionSink`'s dirty/flushing coalescing mechanism is already known to want a bigger refactor (carries over `run-history`'s in-memory index pattern) — a real fix means giving that sink a way to expose/await its actual flush completion, which touches that same pending rework. Revisit the retry band-aid once that refactor happens.
- **The bigger rework the above is waiting on**: `SqlRunProjectionSink`/`updateRunIndex`/`initRunIndex` (`packages/use-cases/run-history/src/*`) are old code — `RunIndex` originally meant an in-memory object mirrored to an on-disk JSON file, written only on `run.completed`/`run.failed`; when SQL replaced the filesystem, this same projection mechanism got carried over as-is rather than redesigned for SQL. Concrete, already-confirmed evidence it's stale: `updateRunIndex`'s own doc comment says it's deliberately built to tolerate events "out of order," and `flowVersionId` only gets set in `SqlRunProjectionSink.#updateState` from `run.requested`'s `data` payload (line 86) — but `flowversionid` is now a required header field on _every_ run/step event's scope (`RunScope`/`StepScope`, `packages/types/src/events/{run,step}/event.ts`), a system change made after this sink was written.
  - **Sharper framing, surfaced while building Run History's `getRunParams` route (`RunServicePort.getRunParams`, step 3)**: this isn't really an event-ordering problem for `flowVersionId` at all, for either write path. `RunRepositoryPort.createRun()` (`prisma-run-repository.ts:129-139`) already writes `flowVersionId` synchronously, straight from `RunRequest` (a required field), inside `RunService.requestRun()` — and that happens _before_ `runFlow()` ever emits `run.requested`. So by the time any event fires, including the one `SqlRunProjectionSink` reacts to, the value is already durably written by the direct path. The sink reading `event.flowversionid` unconditionally would still work, but it's solving a hazard that was never actually there for this field — same reason `RunParam` rows (also written directly in that same `createRun()` call) needed no defensive handling either. Net: `flowVersionId` can just be non-nullable in the schema outright (see the no-migration-constraint note below), and the sink's optional-handling for it can be deleted, not patched.
  - Scope of the actual rework, not just this one field: revise the SQL projection structurally (less of the two-query-plus-in-memory-Map-correlation pattern already discussed for `PrismaRunQuery.listRuns`/`getRunDetail`, aiming for SQL that's structurally correct for the data's real relationships rather than shaped by the old JSON-index carryover), revise the repository/query port methods and their API data structures if that serves efficiency better (explicitly not committed to today's shapes), and give the upsert path firmer guarantees — e.g. fields that are always relationally derivable from events (like `flowVersionId`, now that it's a base header field) becoming non-nullable in the schema, instead of defensively optional.

- **Separate open question from the run-SQL-projection rework above (that one's specifically about `Run`/`RunStepProjection`) — should sim/fork-spec data be modeled only in SQL rather than as a CAS artifact?** Today a `ForkSpec` (`packages/types/src/engine/fork-spec.type.ts` — just `{parentRunId, reuse: string[]}`) is stored as an opaque JSON blob in CAS, referenced by hash from the `Sim` row (`forkSpecHash`) and supplied to the engine as an optional hash on `run.requested`. - **New idea, genuinely undecided, not started: artifact "edit" and deletion, and a draft/publish delineation that would make it tractable.** Raised while designing the unified `ArtifactMetadata` write path for Artifacts mode PR 5 — a separate, harder question surfaced alongside it, deliberately not pulled into that PR's scope.
  - **"Editing" an artifact's content isn't a real operation given CAS semantics — it's always create-new, sometimes-plus-delete-old.** Content is hash-addressed (`hash = sha256(content)`); there's no such thing as mutating content at a fixed hash without it becoming a different artifact. A user's "I made a mistake, let me fix it" experience is really: create a new artifact, optionally re-point whatever referenced the old one, optionally garbage-collect the old one if nothing else needs it. Nothing about `ArtifactMetadata` (SQL-side, mutable-by-design metadata) needs to anticipate this — metadata and content are already cleanly separate concerns.

  - **Two different levels of "safe to change," worth keeping distinct.** Metadata-level associations (curations, `flowId`/`flowVersionId` association, `label`) are comparatively low-stakes — changing or removing one doesn't corrupt anything historical. What's actually load-bearing and must never dangle is a hash that's been _consumed or produced_ by a run/event (run params, step outputs, exports) — that's the real ledger; the traceability guarantee lives there, not in the curation/association layer.

  - **Deletion needs a reachability check — the real design question is eager-vs-lazy, not whether to check at all.** Considered and leaning away from a maintained boolean/flag set whenever a run/sim starts using an artifact — that's a write on every reference-creating action (run/sim creation, frequent) to speed up a check that's only ever needed at delete time (rare), the wrong end of that tradeoff. Also a real drift risk: a maintained flag can silently fall out of sync if any code path forgets to set it — the same class of problem already hit once in this codebase (`SqlRunProjectionSink`'s carried-over-from-filesystem-era projection mechanism, flagged elsewhere in this file). Leaning instead toward a lazy, on-demand reachability query at delete-time across every real reference source (run params, step outputs/exports, curated-param associations, the artifact's own `flowId`/`flowVersionId`) — correct against ground truth, no drift possible, cost only paid when actually needed. Exhaustiveness is the hard part either way: missing even one reference source turns "delete" into silent corruption elsewhere.

  - **A draft/publish delineation would make this dramatically more tractable, not just nicer UX.** If an artifact starts as a "draft" — not eligible for any consuming action (can't be a run param, can't be curated, nothing that touches runs/events can reference it) — then by construction a draft can _never_ be referenced, so it can be freely edited/deleted with zero reachability risk, no check needed at all. Only once "published" does an artifact become consumable, and only published artifacts ever need the expensive reachability check before deletion. This narrows the hard problem (is this referenced _anywhere_) down to a much smaller one (is this published) — the same well-trodden pattern as draft-vs-published content in a CMS, not a novel risky idea.
