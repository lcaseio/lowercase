## Change C4 - `MessageLogPort` + Redis-backed adapter - merged (PR #363)

### Discussion

- **A remote-only concern given the current architecture, not something today's local path needs.** `httpjson` (the primary step type) already dispatches to the worker via a direct in-process call (`JobExecutorPort`), bypassing the bus/router/queue path entirely — only `mcp` (already treated as semi-dead) still goes through the old bus-mediated route. So this adapter's real payoff is specifically for a remote worker; it doesn't unlock anything for today's local-only execution.
- **No separate event bus — resolved, not left open.** The worry going in: worker lifecycle needs to reach both the engine (to advance the run plan) and observability (durable event history for debug/replay), genuinely different consumers needing every event, not a subset. Resolved without a second messaging technology: Redis Streams' consumer-group model already gives multiple independent durable readers of the same stream — exclusivity (an entry delivered to only one consumer) is scoped to consumers _within_ one group, not across groups — so distinct concerns can each run their own consumer group on the same stream and each see everything, acking independently. Messages split across separate streams per category (commands, lifecycle events, telemetry, metrics), matching the category split `docs/component-architecture/model.md` already draws. Redis Streams is the sole carrier; there is no `EventBus` adapter in this initiative.
- **The registries already have a placeholder for this swap.** `packages/runtime/src/registries/bus.registry.ts` and `queue.registry.ts` both already declare a `redis` placement key, currently just falling back to `InMemoryEventBus`/`InMemoryQueue` regardless — the config-selection slot already exists, just unimplemented.
- **Explicitly out of scope for this Change (and this initiative's early Changes generally): swapping the bus behind the engine's own real-time state transitions** (`step.planned`/`started`/`completed`/`failed`). That bus is genuinely load-bearing today and delivers synchronously, same-process — introducing a network-mediated transport there risks real new latency/ordering questions in a system that cares about deterministic behavior, for a proof point (bus-mediated dispatch) the primary step type has already moved away from. If ever revisited, the safer version is additive — mirroring select events to a Redis Stream purely for observability's own consumer group, never gating the engine's own synchronous path — which is the same shape as the already-tracked `LifecycleEventIngress` idea (see `worker-tools-artifacts`'s "Not yet scoped"), not something to build ahead of an actual need.
- **Commissioned research on the runtime-composition/messaging design before locking in a stream shape**, since this Change is where the four-category commitment (commands, lifecycle events, telemetry, metrics) actually has to become real config and real adapter behavior, not just a stated intent. Full output: [`research/runtime-composition-strategies.md`](../research/runtime-composition-strategies.md) and its follow-up, [`research/runtime-composition-follow-up.md`](../research/runtime-composition-follow-up.md) (the latter specifically resolves the messaging shape — topology vs. publication routes vs. subscriptions as three separate concerns, retention owned once at the topology level, and consumer-group naming). Change C13 (below) is where the resulting config vocabulary actually lands; this Change needs it mainly to know what the adapter itself has to support (per-category streams — see below for why the engine's result-reading doesn't need a stream of its own yet).
- **Commands don't ride the same passive-publication path as the other three categories.** A command is an authoritative request that makes a component act, not an observed fact — publishing it to Redis alongside also invoking it directly would create two live delivery paths for the same actionable thing, risking a job executing twice. So command delivery lives under the job-execution _binding_ (`bindings.jobExecution`, `direct` vs. `redis-streams`) rather than a generic publication switch. `commands` is still a real stream in the shared Redis topology — the distinction is who's allowed to treat it as authoritative (only the worker's ingress consumer group), not whether it exists.
- **A job result is conceptually not a lifecycle event, even though the first version deliberately doesn't act on that distinction yet.** Worth recording the conflict this surfaced: the four-category list never named replies, while `docs/component-architecture/model.md` categorizes a reply/result separately and the Worker V2 plan says explicitly `JobResult` is the caller's control-flow answer, not a lifecycle event. A job result is a correlated, one-recipient reply the engine's own forward progress depends on (closer to a function's return value than a broadcast fact any number of independent consumer groups might read on their own schedule), which is a different kind of thing from a durable historical fact observability reads independently.
- **Decided anyway: collapse onto one lifecycle stream for the first version, engine included as its own dedicated consumer group.** No separate `protocolStreams.jobExecutionResults` channel gets built yet. The engine reads the same lifecycle stream as observability, under its own consumer group, and correlates entries to its own pending calls itself. This defers the real cost the conceptual distinction above is about — coupling the engine's control flow to whatever operational policy (retention, throughput, other attached consumers) the shared lifecycle stream ends up needing for unrelated reasons — but that cost only actually bites once there's more than one engine replica or a real external lifecycle consumer, and today there's neither. Revisit if either shows up.
- **When the multi-engine-replica problem does need solving, prefer durable shared state over reply-routing.** The research's own follow-up flagged an unsolved piece of the (now-deferred) private-channel design: once there's more than one engine replica, a correlated reply needs to reach the specific replica holding the matching pending call — solved there via things like per-instance reply streams or partitioned reply routing. The preferred direction here is different: keep run/step state durable and externally readable (e.g. in SQL), so _any_ engine replica can pick up a job's outcome and continue working on it, rather than a reply needing to find its way back to the one replica that originally issued the command. Don't reach for per-replica streams or consumer-group proliferation as the default solution later — treat durable shared state as the first thing to try.
- **The worker's `job.<capability>.completed`/`failed` lifecycle event gets slimmed down as part of this work regardless of the above, not left as-is.** Today it carries the full result payload inline — already flagged in `CLAUDE.md` as a known rough edge, and confirmed here to be exactly that: a relic of not having anywhere else to put the result yet, not a deliberate design. Event payloads should stay small — carrying an entire response body inside a public fact stream is bad hygiene on its own, independent of whether the engine also reads it. So the event narrows to what a lifecycle fact actually needs (job id, status, timing, and whatever reference the engine needs to locate real outputs — e.g. an artifact hash — not the output content itself), and the engine reads that same trimmed event via its own consumer group rather than a separate channel.
- **Redis Streams is not just replacing `QueuePort` — it's the eventual replacement for `EventBusPort` too, and that second one is genuinely load-bearing today, unlike the queue.** `QueuePort` (`InMemoryQueue`, `NodeRouter`) is nearly dead — only the semi-dead `mcp` path still uses it — so retiring it is low-risk, and it's heading for retirement alongside the router itself. `EventBusPort` is different: observability taps it directly for its own sinks, and the engine's own reducer/planner/effect loop is driven by events read off the bus — a deliberate "event-driven" design stance from earlier in the project that's since fallen out of favor in principle, but the engine hasn't been refactored to drop the dependency yet (per `CLAUDE.md`'s "keep engine changes incremental unless a larger rewrite is explicitly intended"). `httpjson`'s move to direct in-process invocation only replaced the worker's own dispatch path — the core+inbound/outbound-port structure that made that possible has so far only been built for the worker, not any other component. So most of the system still runs on `EventBusPort` as its only inter-component transport, and this Change's port design needs to not foreclose eventually backing that role too, even though actually wiring it there stays out of scope for this initiative (same reasoning as the bullet above on the engine's synchronous-ish bus dependency).
- **`EventBusPort`'s actual semantics, confirmed by reading `InMemoryEventBus`: fire-and-forget, not durable.** `publish()` defers delivery via `queueMicrotask` and returns without waiting for subscriber completion; `subscribe()`'s handler isn't awaited or caught, so an async handler's rejection currently goes unhandled — a separate, pre-existing gap, not something this initiative touches. There's no persistence, retry, or delivery guarantee today. This matters for any future `EventBusPort` retrofit onto Redis Streams: the change wouldn't be "synchronous becomes asynchronous" (it's already asynchronous, just in-process and lossy) — it would be trading unordered, best-effort, no-persistence delivery for a durable, ordered, ack/retry-bearing transport with real network latency. That's a materially bigger behavioral shift than a transport swap, and another reason it isn't something to attempt inside this initiative.
- **A concrete prerequisite for ever doing that `EventBusPort` retrofit: the worker's lifecycle events are currently thrown away, not captured.** `createConsoleWorkerLifecycleEventSink()` is an explicit placeholder (its own code comment says so) — it `console.log`s and nothing else, where the worker previously published real events onto the bus that both observability and the engine consumed. Already planned, separately from this initiative: giving the worker — and, by the same reasoning, any other component the observer cares about — a real durable sink is one of the next component refactors to the core+inbound/outbound-port structure now being applied project-wide. Not part of this Change; recorded here because it's a real, load-bearing dependency for the `EventBusPort` question above, not a hypothetical one.
- **The port itself is settled: `MessageLogPort`, deliberately not a Redis-specific or "Streams" name.** What Redis Streams (and Kafka, NATS JetStream, RabbitMQ Streams) actually provide as a category of infrastructure is a durable, ordered, replayable log of discrete messages that independent consumer groups can each read at their own pace — not a byte/chunk transport, which is a different primitive this project already has a real name for. "Streams" specifically was ruled out: it's already spoken for by `packages/ports/src/stream.port.ts`'s `StreamPort`/`ConsumerStreamPort`/`ProducerStreamPort` — a real, working, hand-built mechanism from an early version of this project that let one step's output stream directly to another in-process, deliberately shelved (not abandoned) to cut scope while the workflow engine itself got built, kept intentionally intact as an archive piece worth revisiting long-term. Reusing "Stream" for this Redis-backed port would collide with that already-real meaning. `MessageLogPort`'s own name may still shift later alongside a broader event→message rename already under consideration project-wide; not a blocker now.
- **Method surface, and why `start()`/`health()` aren't on it.** `publish`, `readGroup`, `ack`, `claimPending`, `ensureStream`, `ensureConsumerGroup`, `close()`. Provisioning (`ensureStream`/`ensureConsumerGroup`) is part of the port, not pushed to a separate concern — creating a stream/group is genuinely backend-specific mechanics (`XGROUP CREATE ... MKSTREAM`, handling `BUSYGROUP` on a group that already exists), even though _whether_ to create (`createIfMissing`) stays a config decision made by the caller, not the port. No `start()`/`health()`: checked precedent across every port in `packages/ports` — passive store-shaped ports (`ArtifactStorePort`, `QueuePort`, `EventStorePort`, the `Run*`/`Flow*`/`Sim*` repositories) carry no lifecycle methods at all, relying entirely on external `ManagedResource` wrapping; long-running component-shaped ports (`RouterPort`, `EnginePort`, `LimiterPort`, `ObservabilitySinkPort`/`Tap`) bake `start()`/`stop()` in because they're actual self-driven components. `EventBusPort` and `StreamPort` sit in a third bucket — `close()` only, no `start()` — and that's the shape `MessageLogPort` matches: not inert storage, but not a self-driven component either.
- **Payload type: `AnyEvent`, matching `EventBusPort`'s own precedent, not a generic `publish<M>()`.** One shared envelope is the actual plan — every message this port ever carries (command, lifecycle fact, telemetry, metric) rides the existing `CloudEvent<T>`-based type system, distinguished by a new `kind` field to be added alongside the already-established per-type `domain`/`action`/`entity` fields on `CloudEvent<T>` (pulled from `EventMap[T]`, the same mechanism, purely additive — `type` stays exactly what it already is, the specific dotted event name, not repurposed into a coarse category). That `kind` field isn't part of this Change — it's only needed once command/telemetry/metric message types actually get modeled, likely Change C13 or later — but the port's typing decision assumes it's coming rather than staying generic and deciding later.
- **Redis client: `node-redis` (the official client, npm package `redis`), not `ioredis`.** Redis itself has deprecated its earlier recommendation of `ioredis` in favor of `node-redis` — new features land there first, TypeScript support is built in, and it covers every Stream command needed (`xAdd`, `xReadGroup`, `xAck`, `xClaim`/`xAutoClaim`, `xGroupCreate`). `ioredis`'s real edge — Cluster/Sentinel ergonomics, heavy pipelining — doesn't apply to this initiative's single-Redis-instance scope.
- **Tentative, not settled: idempotency-against-redelivery probably doesn't belong in `MessageLogPort` at all, even as a per-adapter-implemented contract.** Surfaced while reviewing the Redis adapter's use of `xAdd`'s auto-generated entry id (unrelated to any application-level id inside the payload) and whether Redis 8.6+'s `IDMPAUTO`/`IDMP` options could help. Reasoning so far, offered as a thing to think through more rigorously later rather than a conclusion: rejecting a Redis-native dedup mechanism because Kafka/NATS/an in-memory implementation wouldn't have an equivalent is the easy, vendor-neutrality argument — but there's a sharper reason underneath it. The `direct` job-execution binding never touches `MessageLogPort` at all, and has no redelivery mechanism to protect against in the first place (nothing claims or re-delivers a plain in-process call). So "publish is idempotent given a key" would be a guarantee meaningful only for the `redis-streams` binding, not something every implementation of this port could honor in a way that means anything — structurally different from `ensureStream`/`ensureConsumerGroup`, which every real implementation needs regardless of binding. If that reasoning holds, idempotency-against-redelivery belongs one level up, at whoever actually executes a command checking durable state before acting — which is already named, in different words, in the follow-up research doc's note on command consumers needing "idempotent job execution plus duplicate suppression at the terminal write." Not acted on here; flagged so it isn't lost, and to be revisited with more rigor once a real `redis-streams` job-execution binding is actually being built (Change C13).
- **Testing: real-Redis integration tests as the primary proof, not mocks — narrow unit tests only for any pure logic factored out with no connection involved.** The entire point of this adapter is proving Redis's actual distributed semantics (consumer-group delivery, ack, pending-entry ownership); a mocked client would just replay assumptions about that behavior, hiding exactly the bugs this Change exists to catch — same reasoning Change C1 already applied against real MinIO. `claimPending` specifically needs a deliberate two-consumer scenario, not just a call that doesn't throw: consumer A reads via `readGroup` and doesn't ack (simulating a crash mid-processing); after a short `minIdleMs` window, consumer B calls `claimPending`; assert B receives the message, B can `ack` it, and a fresh `readGroup` for new entries does not return it again. That last assertion is what actually proves ownership transferred through Redis's real pending-entries mechanism, rather than the message being silently duplicated or lost.

### What actually landed

Matches the settled design above on every structural point — `MessageLogPort` in `packages/ports/src/message-log/`, `RedisMessageLog` in `packages/adapters/src/message-log/` against `node-redis` 6.2.1, no wiring into `packages/runtime`, nothing touching `QueuePort`/`EventBusPort`/`NodeRouter` — with several things found or decided only once this got built and reviewed, not just planned:

- **`node-redis`'s reply types needed one explicit inline type annotation `tsc` couldn't infer on its own** — `readGroup`'s `.flatMap`/`.map` callback silently hit an implicit-`any` several layers into the library's own generic reply-mapping machinery, fixed by annotating the callback parameter directly rather than fighting the library's types. Confirmed, not assumed, that the annotation is actually faithful to runtime behavior: read `node-redis`'s own `RESP/types.d.ts` directly and confirmed `MapReply<K,V>`'s default resolved type (no custom `TYPE_MAPPING`) is a plain `Record<string, string>`, even though `createClient()` defaults to RESP3 — so `decodeEntry`'s `JSON.parse`-based decode needed no RESP-version branching.
- **Testing ended up as 4 integration tests (real Redis) plus 1 mocked unit test, not integration-only as originally planned.** The integration suite (provisioning idempotency, publish/read round-trip, ack removing pending state, and the `claimPending` recovery scenario — two consumers, one abandons a read, the other claims and acks it, a fresh read never returns it again) covers everything reachable against a real backend. Review surfaced one branch it structurally can't reach: `ensureStream`/`ensureConsumerGroup` swallowing `BUSYGROUP` as idempotent success only ever gets its swallow path exercised for real; forcing a _different_ `xGroupCreate` failure deterministically against real Redis isn't practical, so that path got one small mocked-client unit test instead — not a parallel suite duplicating the integration coverage, just the one gap.
- **Test env-var handling grew into its own small piece of infra, triggered directly by this Change growing the var count.** Added `.env.test.local`/`.env.test.local.example`, split cleanly from the real `.env`/`.env.example` (which stays `DATABASE_URL`-only, matching Prisma's actual usage), loaded via a new vitest `setupFiles` entry (`packages/adapters/tests/setup-env.ts`) using the same explicit `dotenv.config()` pattern `packages/db-prisma` already uses elsewhere in the repo — not a new convention. Applied retroactively to the existing S3 integration test too, not just Redis, so both now load from one file; verified by running the full integration suite with zero inline/exported vars and confirming both suites picked values up from the file and passed.
- **The `docker-compose.yml`/CI project name changed from `lowercase` to `lowercase-test`** — a repeat ask from Change C3's review, done now — so these containers can't get mixed up with any future non-test docker infra. Old `lowercase-*` containers torn down before the rename rather than left orphaned.
- **Two design questions surfaced during review, resolved differently than first assumed:**
  - Whether `RedisMessageLog` should lean on Redis 8.6+'s `IDMPAUTO`/`IDMP` idempotent-add options for dedup: no — not just because other backends lack an equivalent, but because the `direct` job-execution binding never touches `MessageLogPort` at all and has no redelivery mechanism to protect against in the first place, so an idempotency guarantee at the port level wouldn't be meaningful for every binding that could exist. Recorded above as tentative, not settled — a placement question to revisit with more rigor once a real `redis-streams` binding is actually being built.
  - Whether `MessageLogPort`'s methods should return `DomainError<Code>` (matching `ArtifactStorePort`): no, but not for the reason first given (no HTTP-facing boundary) — `DomainError` isn't scoped to HTTP boundaries at all, it's a general convention applied wherever a structured, closed-union error code helps. The actually-correct reason: none of this port's operations have a genuinely distinguishable _expected_ failure mode to standardize on — its one real error path (`BUSYGROUP`) is already swallowed internally, and everything else (e.g. `NOGROUP` from calling `readGroup` before `ensureConsumerGroup`) represents a caller violating this port's own ordering contract, not a normal outcome to branch on gracefully.
- **Verified**: `packages/ports`/`packages/adapters` typecheck clean individually; full workspace `build` (27 tasks), `typecheck` (26 tasks), and `test` (26 tasks) all pass; the integration suite runs green against a real `docker compose up -d minio redis` with zero inline env vars, purely via `.env.test.local`.

## Changes C5, C7–C9, C11–C13 — from one Change to seven

What Change C4's discussion originally scoped as one Change ("extend `local-system` with a `redis-streams` messaging branch") turned out, once actually strategized, to be five smaller, mostly-independent pieces — expected, not a sign anything went wrong: every Change ordering here is a best-effort guess at the time it's made, and the initiative's own "Evolution" section already documents this happening once before (the original CAS single-Change plan becoming Changes C1–C3). It then expanded once more, from five to six, during Change C8's own discussion — see that Change below for why a local-only port consolidation got inserted ahead of the Redis work, pushing what had been Changes C8–C10 down to C10–C11. It expanded a third time, from six to seven, after commissioned research on the worker component split the Message cutover into a behavior-preserving structural runway (Change C11) and the authority change itself (Change C12) — see Change C11 below. That third pass also moved the engine's lint/typecheck work out of this arc entirely, into [`package-tooling.md`](./package-tooling.md) as Change C10, and pushed the SQL Changes down to C14–C15. Two cross-cutting conclusions came out of the original strategy pass, both still standing:

- **A full `EventBusPort` retirement is not this initiative's next step, and doesn't need to be.** Mapped every real consumer first (`packages/events`' `EmitterFactory`, the engine, observability's tap, the limiter, replay, the already-fully-migrated worker) before concluding this. Most of that surface stays untouched — what actually needs to move for a real remote worker is much narrower than "retire the bus," and is exactly Changes C7–C9 and C11–C12 below.
- **The engine's own step/run self-loop is a real, separate bug — correct to fix, but deliberately deferred, not part of Changes C5, C7–C9, and C11–C13.** Eight of the engine's twelve `EventBusPort` subscriptions (`step.planned`/`started`/`reused`/`completed`/`failed`, `run.started`/`completed`/`failed`) exist purely so the engine can react to events it just published itself, to advance its own internal reducer queue — a same-process round-trip through the bus for communication that never actually leaves the process. The corresponding effect handlers (`emitStepPlannedFx`, `emitRunStartedFx`, etc.) currently only publish and rely on that subscription loop-back; `executeHttpJsonJobFx` already shows the fix (enqueue internally _and_ publish externally, from one build, no subscription needed). Applying that pattern to the other eight would shrink the engine's real `EventBusPort` dependency from 12 subscriptions to 2 genuinely external ones (`run.requested`, `replay.mode.submitted`). Checked against every Change below and it's genuinely decoupled from all of them — nothing here depends on it, and it doesn't ease anything here either, since the self-loop never touches `MessageLogPort`/Redis at all. Deferred to whenever the engine gets its real core/inbound-outbound refactor; tracked in `INITIATIVE.md`'s "Not yet scoped" so it isn't lost.

## Change C5 - Package hygiene: delete `NodeRouter`/`QueuePort`, real ESLint for `adapters` - merged (PR #364)

### Discussion

- **Two unrelated hygiene items folded into one Change, added after the dead-code deletion was already scoped, not part of the original strategy pass.** Both are mechanical, low-risk, and outside the Redis/engine work entirely — bundled here rather than spun into a separate Change.
- **Real ESLint for `packages/adapters`, following already-established precedent — one more increment of an ongoing, broader ESLint-adoption push, not a one-shot fix-everything pass.** `CLAUDE.md`'s claim that real ESLint is workbench-only is stale: `packages/ports` and `packages/components/worker` already have working Node-flavored configs (`js.configs.recommended` + `tseslint.configs.recommended` + `@typescript-eslint/consistent-type-imports`). `packages/adapters` copies worker's version specifically (not ports' stricter types-only one) because worker's config also ignores `_`-prefixed unused vars/args, which matters here given `packages/adapters`' own mocked-client test helpers (e.g. the Redis adapter's `fakeClient()`, the S3 `aws-sdk-client-mock` tests). Deliberately scoped to just this package for now, not rolled out to every other still-stubbed (`"lint": "echo lint"`) package while in here — that stays incremental, as it's been happening.
- **`clean-node-modules` turned out to already be implemented almost everywhere — `packages/adapters` (and `packages/components/engine`) are just gaps in an otherwise near-complete rollout, not missing infrastructure.** `turbo.json` already declares the task, and `packages/events`/`artifacts`/`replay`/`ports`/`integrations`/`runtime` and three of the four `components/*` packages already carry `"clean-node-modules": "rm -rf ./node_modules"`. So this is just filling the one gap in `packages/adapters` to match existing convention, not introducing anything new or touching `turbo.json`.
- **Confirmed fully dead, not just bypassed for `httpjson` — deleting outright, not migrating.** Grepped the whole repo (including `packages/archive`) for any caller of `QueuePort`'s `reserve`/`dequeue`/`peek`: none exist. The comment in `node.router.ts` warning about "a still-running legacy consumer" is stale — that consumer is already gone. Consequence worth naming: `mcp` steps don't just have doubted reliability (as previously recorded) — they're currently unreachable at runtime, full stop. A job enqueued via the router's `mcp` path is never dequeued by anything, so the engine's `job.mcp.completed`/`.failed` subscriptions never fire and the step hangs forever. Deliberately not being fixed as part of this — `mcp` has been intentionally inert since it was never implemented in the worker, not a regression this Change causes or needs to address.
- Also removes a problem that looked real earlier in this discussion: Redis Streams has no wildcard topic matching, which only mattered because of `NodeRouter`'s `"job.*.submitted"` wildcard subscribe. Deleting the router instead of porting it makes that gap moot rather than something to solve.

## Change C7 - `JobExecutorPort` envelope-fidelity fix - merged (PR #366)

### Discussion

- **Local only — no Redis, no `MessageLogPort` — but a prerequisite for the Redis dispatch work (now Change C13), not a stylistic cleanup.** Building a Redis adapter against the current, already-wrong contract would mean redoing it once this fix lands anyway.
- **Surfaced a real, pre-existing bug while scoping the remote dispatch adapter, not a remote-readiness question: `JobExecutorPort`'s input has already lost envelope fidelity, today, locally.** In `stepPlannedPlanner.ts` (`packages/components/engine/src/planners/step-planned.planner.ts:100-162`), `EmitJobHttpJsonSubmittedFx` (the real `job.httpjson.submitted` CloudEvent envelope, published for observability) and `ExecuteHttpJsonJobFx.request` (the bespoke `JobExecutionRequest` actually passed to `JobExecutorPort.execute()`) are built side by side from the same step data — but as two independently-constructed objects, down to each generating its **own random `jobId`** that doesn't correlate with the other's. The comment there already flags this as "a small, known, accepted divergence." It isn't small: it means the thing observability records and the thing actually dispatched aren't even the same job identity, and it happened silently because local execution never had to prove envelope fidelity — observability was already being fed by a separate publish, so nobody noticed the executor's input drifting into its own bespoke shape.
- **Fix: build the canonical envelope once per submission, and have both the dispatch call and whatever records it work from that same object** — the same "build once, use twice" shape `executeHttpJsonJobFx` already uses correctly on the _completion_ side (one event, used for both the internal `enqueue` and the external `publishEvent`). `JobExecutorPort.execute()`'s input moves from the bespoke `JobExecutionRequest` to (or a strict, identity-preserving derivation of) the real envelope. - `LocalWorkerJobExecutor` needs updating to translate from the envelope-shaped input instead of today's `JobExecutionRequest` — a contained change to one existing adapter (already in the translation business) plus the port and one planner, not a sprawling rewrite.

### What actually landed

Two things sharpened during discussion, not in the original framing above:

- **`traceId` is required (`string`), not optional, on the new `JobExecutionRequest`** — `RunContext.traceId` (`packages/types/src/engine/run-context.ts`) is itself required, so the planner always has a real one; the old `traceId?: string` was slack that didn't reflect reality.

**Left open, not resolved here**: whether the engine keeps explicitly publishing a `job.*.submitted` observability event once the bus is fully retired, or that record falls out for free from whichever adapter does the real Redis publish in Change C13. Flagged as a new bullet in `INITIATIVE.md`'s "Not yet scoped" section rather than guessed at here.

## Change C8 - Consolidate onto one `JobExecutionPort`; retire `packages/integrations` - merged (PR #367)

### Discussion

- **Local only — no Redis, no `MessageLogPort`. Same role Change C7 played: settle the contract before building a transport against it.** Inserted ahead of the Redis dispatch work (now Change C10) after a strategy pass that started as "where exactly do the two new Redis adapters live" and turned into a bigger question about whether the engine↔worker seam should have two ports at all. It deletes a package rather than adding one, so the Redis work lands against a smaller, settled surface.
- **Commissioned research on the integration/port structure before committing.** Full output: [`research/integration-architecture-revision.md`](../research/integration-architecture-revision.md). Its central model is adopted; two of its recommendations are explicitly not (see below). Its factual claims were checked against the code rather than taken on faith — `packages/integrations` really does contain nothing but the engine-worker bridge (3 source files, 2 tests, one consumer), `createWorker()` already returns a `JobExecutionPort`, and `resourceHint` (the one field on `ExecuteJobCommand` with no counterpart in Change C7's envelope) has zero producers repo-wide.
- **The shared contract is the message, not either component's type.** Not `ExecuteJobCommand` — that's worker's own internal vocabulary, the shape on the far side of worker's boundary, not a thing the engine should speak. Each core keeps its own translation layer (worker translates a message into its command; the engine translates a message out of its own planner/effect vocabulary), and what's consistent across the system is that the layer between components is always messages. That keeps observability honest — the fact observability records is the same object the components actually exchanged — and it means every component interprets the same message the same way regardless of who sent it or how it arrived.
- **Consequence: the mapper relocates, it doesn't die.** The research doc treats `mapper.ts` as waste ("mostly rearranges the same job information and then rearranges the result back"), but under the framing above that translation is legitimate work — it's the worker turning a message into its internal command. What's actually wrong with it is its address: it lives in a package that knows both components. Message → `ExecuteJobCommand` belongs inside worker, as worker's own boundary translation, where it is then the same translation whether the message arrived by direct call or off a stream. `resourceHint` follows the same logic — it stays a worker-internal concern on `ExecuteJobCommand`, and the message gains a field for it if something ever actually produces one.
- **There is no local inbound adapter, because in-process there is no boundary to adapt.** Locally the worker simply _is_ the `JobExecutionPort`; `local-system.profile.ts` goes from `new LocalWorkerJobExecutor(workerCore)` to `workerCore`. Adapters appear only where a real transport boundary does (Change C10). This corrects an earlier framing in this arc's own discussion that had the worker owning "two adapters, local and Redis" for its inbound port.
- **This relaxes a rule in `docs/component-architecture/model.md`, so amending that doc is part of this Change's scope, not a follow-up.** Worth being precise that nothing drifted: the current code is a faithful implementation of model.md as written — `JobExecutorPort` is literally its `WorkerDispatch` outbound-port example, `JobExecutionPort` is its `JobExecution` inbound-port example, and `LocalWorkerJobExecutor` is its "Integration Adapter" category, whose own example is `LocalWorkAdmission`. The rule being relaxed is "the caller owns the outbound port because the port should be named in the caller's language." The argument against it is forward-looking rather than aesthetic: as written it mints a bridge per component _pair_, so worker↔limiter and worker↔observability each acquire one too — model.md's own `LocalWorkAdmission` example is precisely that second bridge. Replacement rule, roughly the research doc's: use a shared capability contract when caller and provider agree on the operation; introduce separate ports and an integration adapter only when there is a real semantic or policy translation.
- **Keep both vocabularies, since they answer different questions** — inbound/outbound describes direction of dependency relative to a component; ingress/egress describes literally receiving or transmitting across a process/transport boundary. `JobExecutionPort` is worker's inbound capability; `WorkerLifecycleEventSink` is worker outbound; a Redis command reader is an ingress. The two axes are independent, and conflating them is what made the earlier "two adapters for worker's inbound port" framing wrong.
- **Not adopted from the research doc, deliberately.** Its recommendation to give remote job results their own correlated result channel contradicts a decision Change C4 already reasoned through and recorded (collapse onto one lifecycle stream for the first version, engine as its own consumer group, revisit when there's more than one engine replica or a real external lifecycle consumer). The doc re-lands the other way but presents no new fact — it's a re-weighting, not a discovery — so C4's deferral stands on its own terms. Its suggested directory tree is read as a sketch of an endpoint several Changes out, not an instruction. Its proposed redirect of the old Change C9 is adopted only in half; see Change C9 below.
- **What Change C7 won survives the consolidation.** C7's actual value was one identity built once, with no divergence between what gets dispatched and what gets recorded — that discipline is independent of which type the port names, so moving the contract's home doesn't undo it.

## Change C9 - In-process Message router + mailbox foundation (inert) - merged (PR #368)

### Discussion

- **Fourth revision of this slot, and the first that changes the _shape_ of the exchange rather than its payload type.** The sequence was: Redis-backed lifecycle sink + bus bridge → worker forms/encodes each fact once + a real sink → `JobExecutionPort` carries the literal event → this. Every earlier version kept the exchange as request/response and argued only about which type crossed it. That is what kept regenerating the same problems: a correlated pending-map on the remote side, an inbound/outbound split that "genuinely collapses," and an engine that still reconstructs facts it was handed. The design guide is [`docs/component-architecture/in-process-messaging/`](../../../component-architecture/in-process-messaging/README.md) (contract + growth path) and its [`MVP-IMPLEMENTATION.md`](../../../component-architecture/in-process-messaging/MVP-IMPLEMENTATION.md) (application to this repository); the fuller destination is [`research/message-carrier-architecture.md`](../research/message-carrier-architecture.md), deliberately not built here.
- **The pivot in one line: local publication means _admission_, not recipient completion.** A sender may await infrastructure accepting its Message; it never awaits the recipient processing it. That single rule removes the correlated client, the pending map, the reply channel, and the local/remote protocol split all at once — the engine stops awaiting a job and instead consumes the terminal Message from its own subscription, exactly as observability does. The correlated-client design from the superseded Redis-dispatch Change is **dropped, not deferred**: there is no version of it that comes back later.
- **What survives from the superseded revisions, and what doesn't.** Survives: Messages are the protocol between components (Change C8's core claim); `buildEvent()` is the right construct-and-validate helper; worker owns translating a Message into `ExecuteJobCommand`; no package is named after a component pair. Doesn't: `JobExecutionPort` in any form, `JobExecutionRequest`/`JobExecutionOutcome`, the `direct | redis-streams` binding, and the idea that the engine advances from a returned value. Merged Changes C4, C7, and C8 stay exactly as recorded — they were real work against the understanding at the time, and C8's deletion of `packages/integrations` is unaffected by any of this.
- **Scope is the foundation only, and it is inert when merged.** In: `MessageOf<T>`/`MessagePublisher<T>`/`MessageHandler<T>` plus the publication/subscription/binding declaration types under `packages/ports/src/messaging/` (types only — that package bans runtime declarations); `subscription-mailbox.ts` and `in-process-message-router.ts` under `packages/runtime/src/messaging/in-process/`; topology validation rejecting the six cases the guide lists; snapshot-per-destination prepared before any enqueue; non-reentrant microtask dispatch; catch-report-continue failure isolation; the outstanding-delivery counter behind `whenIdle()`; and the full contract-test suite. Out: any component wiring, any topology _values_, Redis, bounded queues, drain/seal, retry, health, competing members, and the lossless-JSON codec. Nothing imports the router until Change C12.
- **Split from the cutover deliberately, against the guide's mild preference for one Change.** The guide prefers foundation-plus-use-case together so the abstraction is proven immediately. The counterweight here is size: the cutover alone is roughly Change C8-sized across four packages plus two apps, and the foundation is ~300 source lines plus a comparable test suite. Together that is not reviewable. The usual risk of building an unused abstraction is low in this specific case because the consumer shape is pinned in advance — two publications, four subscriptions, exact publisher and handler signatures — so this is building to a spec Change C12 consumes immediately, not speculative design.
- **Deviation from the guide, taken deliberately: worker's mailbox gets real concurrency in this Change.** The guide specifies `maxInFlight: 1` everywhere for the MVP and treats configurable concurrency as a later improvement. Taken literally that ships a real latency regression — parallel HTTP steps in a flow currently execute concurrently up to `maxConcurrentJobs` via `withWorkerCapacity`'s semaphore, and a serial mailbox would make them strictly sequential. The expensive part of concurrency is shared capacity groups and fair scheduling _across_ several subscriptions hosted by one component; worker has exactly one subscription, so `maxInFlight` on a single mailbox is bookkeeping, not scheduling. Engine and observability stay at `1`, where serialization is what's actually wanted.
- **Consequence to record before it confuses someone: `withWorkerCapacity`'s semaphore becomes effectively inert in the local profile.** With mailbox `maxInFlight` set from the same `maxConcurrentJobs`, the semaphore never blocks. Keep it — it is a real invariant if the worker core is ever driven by something other than this mailbox — but the mailbox is what actually bounds concurrency once this lands.
- **Head-of-line blocking is inherited, not introduced.** `resourceKey` isn't known until refs are resolved and the request materialized (`#prepareProtocolRun`), so per-resource gating cannot move up to the mailbox and stays inside worker. N lanes occupied by jobs contending for one `resourceKey` will block jobs for other resources behind them — which is already exactly what happens today, since the semaphore slot is held across the whole `core.execute()` including the permit wait. Not a regression; just a property that follows the design across. A real global _rate_ limit (distinct from any concurrency bound, and absent today) belongs to the `rate-limiting` initiative, not here.
- **Snapshot isolation is `structuredClone` + recursive freeze, and must not be recorded as wire-safety.** Clone-per-destination is deliberate beyond mutation safety: independent copies make local delivery match Redis, where each consumer decodes its own. But `structuredClone` preserves `Date`, `Map`, `Set`, `BigInt`, `undefined`, and cycles — all of which JSON drops, coerces, or rejects — so a Message can pass `buildEvent()`'s zod validation, pass cloning, work locally, and only break when it later crosses a wire. The exposure today is narrow and worth stating: the only schema field wide enough to carry such a value is `args`, which is an author-supplied passthrough from `step.args` with no live producer or consumer anywhere in the system. Keeping snapshotting behind one named `snapshotMessage()` seam is what lets the strict codec drop in later without touching publishers, handlers, or topology.

### What actually landed

Matches the plan in shape: `MessageOf<T>`/`MessagePublisher<T>`/`MessageHandler<T>` plus the `Publication`/`LogicalSubscription`/`MessageBinding` declarations in `packages/ports/src/messaging/` (folder index, exported from the root index alongside `events/` and `bus/`), and `snapshot-message.ts`/`subscription-mailbox.ts`/`in-process-message-router.ts` under `packages/runtime/src/messaging/in-process/`. No dependency changes — `@lcase/ports` and `@lcase/types` were already type-only devDependencies of runtime, and everything imported here is a type.

- **`MessageOf<EventType>` versus `AnyEvent` turned out to be load-bearing, not stylistic.** The mailbox was first written storing `AnyEvent` and didn't compile. `AnyEvent` defaults to `AnyEvent<EventType>` — one non-distributed type whose `type` is the whole union and whose `data` is the union of every event's data — while `MessageOf<EventType>` distributes into a union of complete envelopes, each with its `data` correlated to its own `type`. They are not interchangeable, and the doc comment on `MessageOf` explaining why is describing a real constraint the implementation immediately hit. The mailbox moves `MessageOf<EventType>` (aliased `DeliveredMessage`) throughout.
- **Construction is phased — declare, resolve publishers, bind, seal — which the plan did not anticipate and a usage walkthrough forced.** The first version took `bindings` at construction, and writing out what the cutover's wiring would actually look like exposed that as unsolvable: worker's handler needs the terminal publisher, the router hands out publishers, and the router needs worker's handler to route to it. The tell was already in this Change's own test suite, where the multi-hop case had to assign a handler's downstream publisher through a mutable `let` after construction — precisely the "service location or mutable component dependencies" workaround the MVP guide warns against. It passed, which is what makes it worth recording: a green test can still be the API telling you it is wrong. `publisher()` now resolves its destination mailboxes at publish time rather than capturing them when the publisher is created, so a publisher can be handed to a component before that component's own handler exists. `seal()` is one-way and runs the one check needing the whole picture (no publication without a subscription); binding after seal and publishing before it both throw. Nothing can add a route at runtime, and there is deliberately no `unbind()`.
- **`Publication` is parameterised on the list of types, not on the union they form — the second thing a usage walkthrough caught.** The plan's `Publication<T extends EventType>` with `types: readonly T[]` looked type-safe and wasn't: `readonly T[]` requires every element to be a member of `T`, never that the list _covers_ `T`, so `types: ["job.httpjson.completed"]` satisfies `Publication<"job.httpjson.completed" | "job.httpjson.failed">` and even `[]` would. The type parameter and the runtime array were two independent declarations that agreed only by discipline, and disagreement fails in the worst direction — the compiler permits a publish the router then rejects at runtime. TypeScript cannot express list-covers-union as a constraint on a plain property, so the list became the source of truth instead: `Publication<Types extends readonly EventType[]>`, with the union derived as `Types[number]`. Two builders in `runtime/src/messaging/define-publication.ts` construct them — `definePublication()` when the list owns the contract, and `definePublicationFor<All>()()` when an already-named union is authoritative and the list must cover it exactly, which fails with an error naming the missing member. A `Readonly<Record<T, true>>` shape was also verified to enforce coverage, but was rejected: it needs a separate `Partial<Record<...>>` type for erased storage, whereas parameterising on the array makes `readonly Publication[]` work as the storage form for free.
- **Found while testing that: `packages/runtime` typechecks no test file.** Its `tsconfig.json` includes only `src` and vitest transpiles without checking, so `pnpm typecheck` sees zero tests there. Two consequences worth recording. First, it is why a latent type error survived in this Change's own new test (`message.data.output` on the erased `DeliveredMessage` union, where `data` is the union of every event's data) — correct at runtime, unsound on paper, caught only by running `tsc` over the tests by hand. Second, `@ts-expect-error`-based type-level tests would be silently inert here, so the publication builders' guarantees are verified by construction and by manual probe rather than by a test that looks like coverage while checking nothing. This turned out to be an unfinished migration rather than a missing idea — `adapters`, `artifacts`, `events`, and `worker` already ran `typecheck` against a `tsconfig.typecheck.json` adding `tests` while leaving the build config alone — so `runtime` was migrated to it here rather than deferred, along with real ESLint, since the two have moved together in every package that has them.
- **Folding that migration in found real problems, not just config.** Three genuine `no-case-declarations` errors in `build-observability.ts`, where `const` bindings sat in unbraced `case` blocks and were therefore scoped to the whole `switch` — a later case could reach a binding from an untaken branch and hit a TDZ error at runtime. And `assemble-embedded-system.test.ts`'s helper returned `ManagedResource<unknown>` while being assigned into typed slots, now generic with the instance cast once (these doubles only exercise start/stop ordering, so the instance is never read). Verified afterwards that no `dist` in the workspace contains a test file: the split config is what keeps `build` on `include: ["src"]` while `typecheck` sees both. `engine` remains unmigrated on both axes and is the one Change C12 will feel; now scoped as Change C10, in [`package-tooling.md`](./package-tooling.md).
- **The plan's binding-widening helper turned out to be unnecessary surface.** The plan assumed the router config could accept `MessageBinding[]` with one cast to widen a narrow binding. It can't: `MessageHandler<T>` is contravariant in its Message parameter, so `MessageBinding<"job.httpjson.completed">` is not assignable to any single erased binding type, and TypeScript rejects even a direct `as` as too large a jump. The first answer was an exported `hostSubscription()` producing an erased `HostedSubscription`; walking the types to answer a review question then showed `bind()` could simply be generic instead, putting the same cast inside the router and producing an identical compile error at the call site with no wrapper. Both the helper and the erased type are gone, leaving the router three exports. The cast still sits on the _Message at the moment of invocation_ rather than on the binding, so subscription identity, `maxInFlight`, and handler shape stay fully checked and only the narrowing is asserted — at exactly the point where the invariant justifying it holds. What was given up is holding a heterogeneous array of bindings across publications, which only the test suite wanted; it defers with a thunk instead, and the erased type can return if a real need appears.
- **One further documented cast, at the publish boundary.** TypeScript cannot verify that `MessageOf<T>` is a member of `MessageOf<EventType>` for an unresolved `T` — the same correlated-generic limitation `buildEvent()` already documents. The cast sits directly beneath the runtime check that justifies it (the Message's type is one the publication declared), rather than at the top of the function.
- **Not exported from runtime's barrel**, deliberately. `src/index.ts` exports `assembly/`, `config/`, and the local-system profile; the messaging module is internal composition machinery, matching `src/worker/create-worker.ts`, which is also unexported. C12's profile will import it by relative path.
- **The one-way dependency rule holds and was verified by grep**: nothing under `src/messaging/` imports runtime's `config/`, `assembly/`, or `profiles/` — only `@lcase/ports` and `@lcase/types`. Lifting this into its own package later is a directory move plus a `package.json`, if the trigger named in the discussion above ever fires.
- **Two tests beyond the plan's list, both guarding invariants the router leans on**: that a throwing failure-reporter cannot take the processing loop down with it, and that the router's settled-delivery bookkeeping fires for failures as well as successes — the second is what makes `whenIdle()` resolve rather than hang after a failed handler.
- **Verified**: runtime's suite went from 5 files/19 tests to 8/50 (7 mailbox, 20 router, 4 snapshot). The snapshot tests were added last, after a review question about nesting pointed out that `snapshotMessage` was the one already-extracted seam with no direct test — its cycle-safety branch, which exists because `structuredClone` preserves cycles, had nothing exercising it. Confirmed non-vacuous by deleting the `WeakSet` guard and watching the new test blow the stack. Full workspace `pnpm build` 25/25 and `typecheck`/`test`/`lint` 24/24, package count unchanged. Inertness confirmed by grep: the only references to the router anywhere in `packages`/`apps` are its own module and its own test, so nothing in a running profile behaves differently than before this Change.

## Change C11 - Worker component root + `JobRunner` (behavior-preserving runway) - not started

### Discussion

- **A new Change, inserted after commissioned research on the worker itself, that splits what had been a single cutover into two.** The trigger was a complaint about the worker's shape rather than about messaging: the live construction chain wraps the component three times (`createWorker` → `withMessageJobExecution` → `createCommandWorker` → `withWorkerCapacity` → a module-private `Worker` class), and every layer renames the thing beneath it, so `createWorker()` returns a `JobExecutionPort`, `Worker` names only the one-job algorithm, and runtime ends up holding a value called `jobExecution` with no worker identity at all. Adding a submitted-Message handler as a fourth wrapper would have made that worse. The resulting design is [`docs/component-architecture/worker/README.md`](../../../component-architecture/worker/README.md) (durable target) and its [`MIGRATION.md`](../../../component-architecture/worker/MIGRATION.md) (sequence); together they supersede `worker-v2`'s direct request/return boundary and decorator-based public shape.
- **What lands: one stable component root, and collaborators that stop impersonating it.** `Worker` becomes the exported root owning execution sequencing and the accepted/started/terminal lifecycle-fact recording; the current one-job algorithm (ref resolution, request materialization, resource-key resolution and permit use, timeout and protocol invocation, output storage, modeled outcomes) becomes an internal `JobRunner`; `withWorkerCapacity` becomes a `WorkerCapacity` collaborator Worker retains rather than a decorator wrapped around it; `withMessageJobExecution` and `createCommandWorker` are both deleted; and runtime's `createWorkerCore` becomes `buildWorker`, returning and retaining the actual Worker.
- **The temporary direct `execute()` is what makes this independently mergeable, and it is deliberate throwaway work.** Worker itself keeps satisfying `JobExecutionPort` for the duration, performing the existing request-to-command and result-to-outcome projections around capacity and JobRunner. The engine is untouched, the mailbox stays inert, and no event authority moves — so this Change changes structure and nothing else. That method is deleted in Change C12. Accepted knowingly: a method written to be removed one Change later buys a cutover PR that is purely an authority change instead of an authority change plus a worker rewrite.
- **Capacity becomes owned composition, not a deletion — the conclusion changed during discussion and the reasoning is worth keeping.** Deleting `withWorkerCapacity` outright looked defensible on three counts: its telemetry hooks are unwired (`createWorkerCore` passes none), its `signal?.aborted` path never fires (the engine calls `execute(effect.request)` with one argument, so `options` is always `undefined`), and mailbox `maxInFlight` is configured from the same `maxConcurrentJobs`. The first two hold; the third does not. Carrier `maxInFlight` bounds how many deliveries the _carrier_ presents, which stops being the same gate the moment a second subscription binds to the same Worker or a log-backed host reads in batches. Worker-wide capacity has to remain a Worker-owned invariant regardless of carrier behavior — which is what Change C9 already recorded when it decided to keep the semaphore. So the fix is the one the complaint actually asked for: stop it being a Worker-shaped wrapper, not stop it existing.
- **Rehoming `JobExecutionOptions` is this Change's job, and it blocks the port file's deletion in Change C12.** It is declared in `packages/ports/src/job-execution/job-execution.port.ts`, but worker's core, its capacity code, and `job.contracts.ts` all use the contained `AbortSignal` internally. It becomes a worker-internal execution-control type here, with the structurally compatible port type left in place only while the temporary direct boundary remains. `AbortSignal` never enters Message data or the retained submitted envelope — cross-process cancellation stays a later Message or durable-state protocol, tracked in `INITIATIVE.md`'s "Not yet scoped."
- **Scope boundary, and why the intermediate state is safe.** `packages/components/worker/*` plus the one rename in `packages/runtime/src/worker/create-worker.ts`. No topology values, no mailbox wiring, no engine or observability edit, no config change. The migration guide's forbidden intermediate states are what keep this honest: no mergeable revision may publish a migrated type through the mailbox while also invoking worker directly for the same occurrence, so a half-cutover cannot be smuggled in under a "structural" label.

## Change C12 - Cut the HTTP JSON job conversation onto Messages - not started

### Discussion

- **Worker's structural prerequisite was refined after Change C9 without changing this Change's protocol boundary.** The active [Worker architecture](../../../component-architecture/worker/README.md) and [migration guide](../../../component-architecture/worker/MIGRATION.md) supersede the earlier idea of wrapping `createCommandWorker()` in a standalone submitted-Message handler. Runtime retains one actual Worker, binds its handler, and keeps capacity as a Worker-owned collaborator. That behavior-preserving runway is now Change C11 above, so this Change adds Worker's real handler to an already-correct component root; the three-Message cutover here remains atomic regardless.
- **Replaces the Redis-dispatch design that previously occupied this slot ("worker-side host + engine-side correlated client") outright.** That design assumed the engine awaits a job and a remote client fakes a return value across a stream. Under Change C9's admission rule there is nothing to correlate: worker publishes one terminal Message, and the engine consumes it from its own subscription like any other subscriber. Nothing from the correlated-client reasoning carries forward except the observation that neither side ever needs to import the other — which this design gets for free, since runtime binds handlers and no component names another.
- **The three types move together, atomically, with exactly one authoritative path each.** `job.httpjson.submitted`, `.completed`, `.failed`. Engine publishes submitted once through `http-job-command.v1`; worker executes only from its subscription's delivery; worker constructs the terminal Message once from its modeled `JobResult` and publishes it through `http-job-terminal.v1`; engine advances only from its terminal subscription. None of the three is also published to `EventBusPort` afterward. Splitting this into "submitted first, terminal later," or merging a state where the engine can advance from both a direct return and a subscription, is the specific failure mode to avoid — dual authority over one occurrence is worse than either path alone.
- **The cutover is clean because nothing else listens.** Checked rather than assumed: no subscriber anywhere binds `job.httpjson.*` except observability's magic `observability` topic — the engine narrowed its own job subscriptions to `job.mcp.*` during the Worker V2 work and left a comment saying why. So removing these three types from the bus costs no other consumer.
- **Everything else stays on `EventBusPort`, untouched.** Engine's run/step self-loop, MCP, replay mode, component lifecycle, and the dormant limiter protocol. The limiter specifically does not join this topology just because a future architecture might use it there — it listens only to the dormant `worker.slot.*` protocol today, and worker already has live local capacity and permit mechanisms.
- **Two prerequisites found by reading the code, both easy to miss and both blocking.** First, `JobExecutionOptions` is declared in the port file being deleted, but worker's core, its capacity code, and `job.contracts.ts` all still use its `AbortSignal` — it has to be rehomed as a worker-internal execution option _before_ that file goes, or local cancellation breaks. Change C11 does that, which is part of why it comes first. Second, `buildEvent()` requires a `source` and `WorkerConfig` carries no worker identity, so runtime must pass an explicit worker source in; terminal Messages have to identify worker as their source rather than silently inheriting engine attribution. The CloudEvent `source` is sufficient identity for this slice — a separate worker ID waits until control, health, or multi-instance behavior gives it a distinct meaning.
- **`@lcase/worker` gains its first workspace runtime dependency, and that is a real boundary change rather than a detail.** Today it depends on `@lcase/json-ref-binder` and `ajv`, with `@lcase/ports` and `@lcase/types` as type-only devDependencies. Worker constructing its own terminal envelope means importing `buildEvent()` from `@lcase/events`, which is runtime code and brings zod in transitively alongside worker's existing ajv. Taken deliberately: `buildEvent()` already carries the mandatory `safeParse` (validation lives at construction, not at publish — `emit()` is just `publishEvent(bus, buildEvent(...))`), and the alternative of injecting an `EmitterFactory` or bus would hand worker exactly the transport dependency this design removes. A repo-wide move from zod to AJV is a separate, later refactor and is not a reason to avoid the events package now.
- **Worker's architecture test needs a deliberate edit, not an incidental pass.** `tests/architecture.test.ts` bans `AnyEvent` in worker's import lines alongside `EventBusPort`, `QueuePort`, and `EmitterFactoryPort`. That ban was written when Messages were _not_ the universal protocol and worker's translation layer existed specifically to keep it off the event schema; that separation is what this design removes, so the ban is now describing an obsolete constraint. It would also pass on a technicality, since worker imports `MessageOf` rather than `AnyEvent` — which is precisely why relaxing it should be explicit. Drop `AnyEvent`, keep the other three, and add the bans worth having now: mailbox, router, runtime, and Redis imports, none of which may ever enter worker.
- **The failed terminal cannot carry `code` or `retryable`, and that limit gets tested rather than papered over.** `JobFailedData` carries `status`, `output`, and an optional `message` only, so worker's modeled `JobExecutionError` loses its code on the way out — including the existing `CANCELLED` code. That preserves current behavior exactly (the engine's synthesized failed event already dropped it), but it means the canonical failed Message does not distinguish cancellation from any other failure. Preserve it as-is and assert the limit in a test; expanding the schema is a separate decision, tracked with the cancel/abort protocol in `INITIATIVE.md`'s "Not yet scoped."
- **Trace propagation gets an explicit, tested decision instead of an assumed one.** `buildEvent({ fromEvent })` carries the inbound `traceid` into the new event, but job events have no registered deterministic span policy: it mints a new random span rather than establishing the inbound `spanid` as `parentspanid`, and it does not copy every optional trace field. So this Change should prove trace-ID continuity, choose and test exactly which fields propagate, and record that full causal parent-span linkage is not yet guaranteed — rather than claiming causality the helper does not implement.
- **`jobFinishedReducer` is not duplicate-safe and crashes on an unknown run.** It dereferences `run.steps[stepId]` before its own `if (!run) return;` guard, so an unrecognized `runid` throws inside the immer producer. The first-slice topology always supplies a real active run, so this Change only needs the terminal handler to report an unknown or stale terminal rather than let a mailbox loop take a `TypeError`. Real active-job identity and duplicate handling are at-least-once/Redis prerequisites, not local ones — the mailbox performs no deduplication and publishing the same terminal twice would advance the engine twice.
- **Accepted limitation: no graceful mailbox drain — inherited rather than introduced, which changes what to do about it.** The router has no lifecycle and is deliberately not a managed resource, so handlers can still be running while or after engine, observability, and sinks stop. The CLI looks like the one place that feels this, but checking it shows the gap already exists: `cliRunAction` calls `requestRun` and returns immediately, and `main.ts` calls `runtime.stop()` as soon as `parseAsync()` resolves, so the CLI already abandons an entire run through the bus today. `http-server` is long-running and unaffected in practice. So this Change documents the limitation rather than building a drain for it, and `whenIdle()` stays runtime/test-only — it counts only mailbox deliveries, not legacy bus callbacks or the engine's existing fire-and-forget effects, so it could not honestly serve as one anyway.
- **`job.httpjson.started` is deferred for the third consecutive design, and that should stop being incidental.** The original motivation for this slot was worker's real execution timing reaching observability. Every design since has correctly judged it non-essential to proving its own boundary, and this one does too. If it still matters it needs its own Change, not another ride-along — the type already exists in the schema and has never had a live publisher.
- **The engine's synchronous core is what makes the vertical test trustworthy.** `handleJobFinished` → `enqueue` → `processAll()` is fully synchronous, so a terminal handler resolving genuinely means engine state has advanced. That is why `whenIdle()` is a sound signal for state assertions here, and it is a direct payoff of keeping the reducer/planner loop non-awaiting. The publish effect must still catch its own admission rejection rather than leaving an unhandled rejection in the fire-and-forget effect runner.

## Change C13 - Log-backed (Redis) delivery under the same Message boundary - not started

### Discussion

- **A placeholder for the next infrastructure milestone, not a planned design.** It replaces the earlier `bindings.jobExecution: direct | redis-streams` design that occupied this slot, which assumed a port whose implementation gets swapped. There is no such port anymore: components hold a bound publisher or a handler, and which carrier moves the Message is runtime's business. The Redis work reappears as a second carrier implementation underneath an unchanged component boundary — which is the whole point of the boundary, and the reason `MessageLogPort` and `RedisMessageLog` (Change C4) are still useful rather than wasted.
- **What comes between Change C12 and this is chosen from evidence, deliberately not pre-numbered.** The guide's post-MVP progression is instrumentation, then worker throughput, then the strict codec, then intake-stop/causal drain, then bounded capacity with a non-deadlocking overflow policy, then retained failures and health. Some of those are genuine prerequisites for a log-backed carrier that acknowledges honestly; others may never be needed. Planning them now would repeat the mistake this slot has already made three times.
- **The known-hard parts are already documented and shouldn't be rediscovered.** `research/message-carrier-architecture.md` covers them in detail: capacity-aware reads bounded by available lanes, a dedicated connection per blocking read loop, cursor-driven pending recovery (today's `claimPending` always starts at `0` and discards the continuation cursor), and the fact that reclaiming a long-running job command too early causes two workers to execute it. Its `MessageLogPort` capability split — writer, group session, provisioner, provider — is the shape to revisit when this Change is actually scoped.
- **Picks up the idempotency-placement thread Change C4 left open, which pointed here under its old numbering.** C4's tentative reasoning — that idempotency-against-redelivery doesn't belong in `MessageLogPort`, because the non-Redis path has no redelivery mechanism to protect against and the guarantee would be meaningful for only one implementation — survives the pivot intact, and the mailbox strengthens it: local delivery genuinely has no redelivery, so a port-level dedup contract would be honored by exactly one carrier. The question of where it _does_ belong (a consumer checking durable state before acting) is the same one, and becomes real here rather than before.
- **Still open, and unchanged from the previous revision: what makes this a genuine swappability proof.** Change C3 counted only once an app config pointed at MinIO and real bytes round-tripped. The equivalent here is most likely running the worker as a separate process against real Redis and confirming a job completes — which also drags in shared artifact storage, since a separate worker host must resolve input refs and publish output refs the engine can read. That dependency is real and is why a genuinely remote worker is still tracked in `INITIATIVE.md`'s "Not yet scoped" rather than numbered here.
