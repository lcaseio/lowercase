# Prove Swappable Infrastructure Initiative — Arc: SQL Adapter (Changes C15–C16)

**Previous:** [`work-tracking-migration.md`](./work-tracking-migration.md) (Change C6) · **Related:** [`queue-adapter.md`](./queue-adapter.md) (Changes C4–C5, C7–C9, C11–C14), [`package-tooling.md`](./package-tooling.md) (Change C10)

Part of the [`INITIATIVE.md`](../INITIATIVE.md) Change log, split out to keep that doc scannable. Adds Postgres via Prisma **alongside** SQLite, and wires the choice into `packages/runtime`'s config selection.

**SQLite is not being replaced.** It is the lightweight install option for this application and stays a supported profile branch indefinitely — the point of this arc is that `sql` becomes a real config axis with two live backends, the same as `artifacts` (`filesystem`/`s3`) and `messaging` (`in-process`/`redis-streams`). An earlier revision of this arc described Postgres as replacing SQLite and the SQLite migration history as collapsing; that was never the intent and both statements are corrected below.

Background research, including a compile probe against a real generated Postgres client: [`research/prisma-sql-backend-strategy.md`](../research/prisma-sql-backend-strategy.md).

## Change C15 - Postgres adapter (Prisma) - not started

### Discussion

- **The behavior is portable; the types are not.** `schema.prisma` has no SQLite-specific workarounds (real `enum` blocks, no `@db.*` native-type pins, no JSON-as-string hacks), a repo-wide grep finds zero `$queryRaw`/`$executeRaw` outside the generated client, and changing only `datasource.provider` plus the generator output produced a working Postgres client from the current ten-model schema. What does not carry across is TypeScript: a Prisma driver adapter selects how a generated client reaches a database, but it does not change the provider that client was generated for. The initial scaffold's assumption — that this is one client with a swapped driver adapter — is wrong.
- **Two providers means two of nearly everything, and that is Prisma's design rather than a workaround.** A schema has one datasource with one literal `provider`, and multi-file schemas merge into that same single logical schema rather than providing overlays or imports. Supporting both therefore requires two schema roots, two generated clients with different output directories, two driver adapters, and two migration histories. Prisma keeps none of it in sync; one authoritative model source rendered into both targets by a repository-owned derivation step is project tooling, not a Prisma feature.
- **The SQLite migration history is retained.** Collapsing it only followed from the replacement wording, which was a slip rather than a plan. Postgres gets a fresh history of its own, in its own directory, and the two are kept in parity by that derivation step plus a per-provider `migrate diff --exit-code` check. `migrate diff` cannot compare across providers — Prisma requires both inputs to use the same connector — so cross-provider model parity has to be guaranteed before the schemas are generated, not verified afterward.
- **The generated `PrismaClient` type must not be used as the shared database seam, and today it effectively is.** All seven repositories narrow with a model-level `Pick` (`Pick<PrismaClient, "flow" | "flowVersion">` and siblings), and the compile probe shows even that rejects the Postgres client — the picked delegate still carries its entire generic API, including a `groupBy` signature nothing calls whose namespaces differ per provider. `$transaction` differs for real, in both isolation-level and callback-client types.
- **The open question is how narrow the seam has to get, and it is worth spiking before committing to Prisma.** The untested rung is method-level rather than model-level: `Pick<PrismaClient["flow"], "findUnique" | "findMany" | "create">`. The surface it has to cover is small — eight distinct verbs (`findUnique`, `findMany`, `findFirst`, `create`, `createMany`, `update`, `upsert`, `deleteMany`) across ten models, with transactions used by only three repositories. If method-level picks suffice, this arc is schema and migration work and nothing more. If they do not, the fallback is project-owned per-repository capability types with mechanical provider bindings — and at that point the comparison against a query builder whose dialect genuinely is a runtime knob (Kysely, or MikroORM's single `EntityManager`) becomes a fair one rather than a reaction to inconvenience.
- **The twelve existing SQL tests are SQLite-shaped in a way that will not survive.** Every Prisma adapter test and five `apps/http-server` route tests construct `PrismaBetterSqlite3` directly against a temp file and hand-apply migration SQL by splitting the file on `;`. That works only because SQLite migrations here are flat `CREATE TABLE`s with enums erased to `TEXT`. The behavior assertions want to become shared contract suites run against both real databases, with setup and teardown staying provider-specific.

## Change C16 - Extend the `local-system` profile with the `postgres` SQL branch - not started

### Discussion

- **Less mechanical than the original scaffold assumed, because there is no config selection on this axis yet to extend.** `SqlConfig` is threaded through `LocalSystemConfig` and both app configs, but nothing reads it: `packages/db-prisma/src/client.ts` exports a module-global `prisma` constructed at import time from `DATABASE_URL`, and both the profile and its observability builder import it by deep relative path into `dist` rather than through the package export. So the first half of this Change is removing that singleton in favor of provider-specific client construction, and only then does Change C3's `buildArtifactStore` pattern apply.
- **Provider selection is per process, decided at composition, and is not hot-swappable.** One selected client instance is shared by every repository including observability's, which means `buildObservability()` receives repositories rather than importing the global itself. Connect, health check, and disconnect join the managed runtime lifecycle. Changing the configured backend does not move data between them.
- **`apps/http-server` and `apps/cli` still pick it up for free** once the branch exists, the same way they did for the CAS and messaging axes.
