# Prove Swappable Infrastructure Initiative — Arc: SQL Adapter (Changes C15–C18)

**Previous:** [`work-tracking-migration.md`](./work-tracking-migration.md) (Change C6) · **Related:** [`queue-adapter.md`](./queue-adapter.md) (Changes C4–C5, C7–C9, C11–C14), [`package-tooling.md`](./package-tooling.md) (Change C10)

Part of the [`INITIATIVE.md`](../INITIATIVE.md) Change log, split out to keep that doc scannable. Adds Postgres via Prisma **alongside** SQLite, and wires the choice into `packages/runtime`'s config selection.

**SQLite is not being replaced.** It is the lightweight install option for this application and stays a supported profile branch indefinitely — the point of this arc is that `sql` becomes a real config axis with two live backends, the same as `artifacts` (`filesystem`/`s3`) and `messaging` (`in-process`/`redis-streams`). An earlier revision described Postgres as replacing SQLite, which was never the intent — "swappable" here means selected by configuration when a process is composed, with every implementation retained. Migration histories do still collapse, but for an unrelated reason (no users, no data to preserve, schema in flux) rather than because one backend is going away.

Background research: [`research/prisma-sql-backend-strategy.md`](../research/prisma-sql-backend-strategy.md) (what two providers costs under Prisma) and [`research/prisma-provider-type-seam-spike.md`](../research/prisma-provider-type-seam-spike.md) (a measured compile probe settling how narrow the shared type seam has to be).

## Arc shape

Originally scaffolded as two Changes — "Postgres adapter" then "profile branch" — which turned out to bundle four different kinds of work behind one number. Sized before planning: as a single Change it lands around 5,000–6,000 modified lines, combining a destructive migration reset, a semantic rewrite of three transactional writes, mechanical schema/generation plumbing, and a restructuring of roughly 3,700 lines of tests. Those four have different risk profiles and want different kinds of review, so they are split.

The cut deliberately puts the only semantically risky piece **first and alone**, before any Postgres exists, so it is reviewed on its own terms rather than found inside a much larger diff:

| Change | What it is                                         | Postgres involved? | Risk                                         |
| ------ | -------------------------------------------------- | ------------------ | -------------------------------------------- |
| C15    | Retire `$transaction` in favour of nested writes   | No                 | Semantic — the real one                      |
| C16    | Two provider schema roots, clients, narrowed seams | Generated only     | Mechanical, plus destructive migration reset |
| C17    | Shared contract suites against both real databases | Yes, running       | Test coverage fidelity                       |
| C18    | Profile selects the SQL backend by config          | Yes, running       | Composition                                  |

C16 lands **inert**: both clients generate and every repository accepts either, but nothing constructs a Postgres client. Change C12 set that precedent in this initiative — infrastructure landing ahead of the flip that uses it.

## Change C15 - Retire `$transaction` in favour of nested writes - in review

### Discussion

- **Wanted independently of Postgres, which is why it goes first.** The preference is to express these writes in explicit Prisma API terms rather than reach for a transaction wrapper, and `PrismaArtifactRepository.writeArtifact` already does exactly that — a parent-plus-relation write as a single `upsert()` with the relation as a nested `deleteMany`/`createMany`, deliberately instead of `$transaction`, with the reasoning written down at the call site. This Change finishes a conversion the codebase started.
- **Three call sites, all structurally identical to that one.** `run` with `runParam` (58 lines), `run-step-projection` with `runStepExport` (53 lines), and the artifact repository's own second method with `artifactParamCuration` (16 lines). Roughly 200 lines rewritten in total.
- **Atomicity is preserved, not traded away.** Prisma wraps a nested write in its own implicit transaction, which is its documented default for atomically writing a parent plus related rows. This is not a durability relaxation.
- **The existing SQLite tests are the verification, unchanged.** Nothing about the test setup moves in this Change, so a green suite means the behaviour is identical. That is only true because this lands before the test restructuring, not after — another reason for the ordering.
- **It also happens to remove the one type-level blocker to Postgres.** `$transaction`'s callback overload hands back a full client, which drags the whole-client provider incompatibility into any seam that includes it; the spike confirmed removing it makes all three affected repositories accept a Postgres client. That is a consequence rather than the motivation, and this Change stands on its own if the Postgres work were dropped entirely.

### What actually landed

All three `$transaction` call sites are gone, replaced by nested writes on the parent; the only remaining mentions in `packages/adapters` are comments explaining what the code does instead. The repository seams shrank as a result: `PrismaRunRepositoryDb` is now `Pick<PrismaClient, "run">` alone, and the artifact and run-step-projection seams dropped their `$transaction` member.

- **The `deleteMany`/`createMany` relation scoping holds, and is now tested rather than assumed.** A nested `deleteMany: {}` clears only the parent's rows; the rows given to a nested `createMany` omit the foreign key entirely because the parent supplies it. That was the one failure mode here that would have been silent and catastrophic — an unscoped delete would have wiped every run's params — so it has a dedicated test asserting that replacing one run's params leaves another run's intact.
- **Composite-key relations work in a nested write, checked rather than assumed.** `RunStepExport` relates to `RunStepProjection` through `[runId, stepId]` rather than a single key, and this was flagged before implementation as the likeliest thing to reject. Prisma fills both halves from the parent with no help.
- **`upsertStepProjection` lost a read as well as a transaction.** It used to write exports and then re-read them inside the same transaction to build its return value. `include: { exports: true }` on the upsert returns them directly, so one round trip replaces three. `toRunStepProjectionRecord` keeps its two-argument shape, and `runStepExport` stays in that repository's seam because `getStepProjection` and `listStepProjections` still read it directly.
- **The `undefined` versus `{}` distinction is preserved and was previously undocumented.** Absent params or exports mean "leave them alone"; an empty object means "clear them". The old code drew that line by guarding `deleteMany` on `!== undefined` rather than on row count, which was easy to lose in translation — it is now explicit at both call sites and covered by tests.
- **The riskiest conversion turned out to be the one nothing tested.** `createRun`'s params-writing branch had no coverage anywhere: its own suite never mentioned params, and `prisma-run-query` and `run-sql-routes` both seed `runParam` rows directly through Prisma, exercising only the read path. Two live callers write params — `RunService.requestRun` and `SqlRunProjectionSink`. Five cases were added covering create, wholesale replacement, clearing, omission, and cross-run isolation. Adapter tests 103 to 108.
- **Verified end to end, not just by unit test.** A two-step `httpjson` flow taking a `userId` param ran through `apps/http-server` to `run.completed`, with the param written and read back through `GET /api/runs/:id` and the first step's export chaining into the second — exercising both the `run.params` and `runStepProjection.exports` nested writes against a real database. Workspace `build` 25/25, `typecheck`/`test`/`lint` 24/24.

## Change C16 - Two provider schema roots, generated clients, narrowed seams (inert) - not started

### Discussion

- **The behavior is portable; the types are not.** `schema.prisma` has no SQLite-specific workarounds (real `enum` blocks, no `@db.*` native-type pins, no JSON-as-string hacks), a repo-wide grep finds zero `$queryRaw`/`$executeRaw` outside the generated client, and changing only `datasource.provider` plus the generator output produced a working Postgres client from the current ten-model schema. What does not carry across is TypeScript: a Prisma driver adapter selects how a generated client reaches a database, but it does not change the provider that client was generated for. The initial scaffold's assumption — that this is one client with a swapped driver adapter — is wrong.
- **Two providers means two of nearly everything, and that is Prisma's design rather than a workaround.** A schema has one datasource with one literal `provider`, and multi-file schemas merge into that same single logical schema rather than providing overlays or imports. Supporting both therefore requires two schema roots, two generated clients with different output directories, two driver adapters, and two migration histories. Prisma keeps none of it in sync; one authoritative model source rendered into both targets by a repository-owned derivation step is project tooling, not a Prisma feature.
- **Both migration histories collapse freely, and will keep collapsing until the schema is stable.** This is a standing policy rather than a one-time step for this Change: there is no user base and no data anywhere that has to survive, both schemas are in active flux, and the whole schema is expected to need a refactor. So SQLite's five-migration history collapses to a single init alongside Postgres's fresh one, and either may be collapsed again whenever the models move enough to make the history noise. The end condition is stability plus real users — at that point history starts being kept for real and this bullet stops applying. Note this supersedes the earlier framing (collapse because Postgres replaces SQLite), which rested on a premise that was never true, and also overrides the research document's "do not discard the SQLite migration history" caution, which assumed data worth preserving.
- **Cross-provider parity is checked before generation, not after.** The derivation step is what guarantees both targets carry the same models; `migrate diff --exit-code` then verifies each provider's own history against its own schema. `migrate diff` cannot compare across providers at all — Prisma requires both inputs to use the same connector — so there is no command that answers "do these two schemas describe the same models," and the repository-owned step has to be the thing that guarantees it.
- **The models themselves stay inside the SQLite/Postgres common subset, deliberately.** Today they already are: only `String`, `Int`, `Float`, `Boolean`, `DateTime` and three enums, with no `@db.*` native-type pins, scalar lists, `Json`, or `Unsupported`. Holding that line is what keeps the derivation step a copy rather than a rendering with per-provider overlays, and a shared model carrying a Postgres-only feature (`@db.Uuid`, `String[]`, `jsonb`, `@@schema`, GIN indexes, full-text search) would fail SQLite validation outright. Divergent _migration SQL_ is expected and fine — identical models produce `CREATE TYPE` on Postgres and `TEXT` on SQLite for the same enum — since that is Prisma's job and needs no overlay. The likeliest first pressure on this is `EvalResult.payload`, JSON stored as a string today, which Postgres would want as `jsonb` to query into; that pressure and the `groupBy` tripwire below are the same pressure and would probably arrive together.
- **The generated `PrismaClient` type must not be used as the shared database seam, and today it effectively is.** All seven repositories narrow with a model-level `Pick` (`Pick<PrismaClient, "flow" | "flowVersion">` and siblings), and the compile probe shows even that rejects the Postgres client — the picked delegate still carries its entire generic API, including a `groupBy` signature nothing calls whose namespaces differ per provider.
- **Settled by spike: a method-level `Pick` is sufficient, and this Change is schema and generation work rather than a seam-design problem.** See [`research/prisma-provider-type-seam-spike.md`](../research/prisma-provider-type-seam-spike.md). Typing the seam against the **SQLite** client makes the Postgres client satisfy it unchanged, because Postgres's generated input types are a strict superset (`mode?: QueryMode` and field-reference list inputs that SQLite lacks) and method parameters are contravariant. Fifteen of seventeen delegate methods pass across all ten models, and narrowing the seven existing aliases in place is non-breaking. With Change C15 already landed, all seven repositories accept either client. No capability types, forwarding functions, or casts are needed.
- **The ceiling this accepts, and the tripwire for revisiting it.** Shared repository code is limited to the SQLite-compatible subset of the Prisma API — no `aggregate`, no `groupBy`, no `mode: "insensitive"` — enforced by the compiler, which is a stronger guarantee than a single provider-agnostic query-builder type would give (that moves the same ceiling from compile time to runtime). `groupBy` and `aggregate` are ordinary SQL rather than exotic features, so their absence is a real long-term constraint: the moment eval or observability work wants aggregate statistics over runs, this reopens on its own merits. The ports boundary keeps that reversible — every repository already implements a port, so a later query-layer migration never reaches `app-services` or any component.
- **Nothing constructs a Postgres client in this Change.** The runtime keeps using the SQLite singleton exactly as it does today, and no Postgres server is needed to review or verify it — `prisma generate` is offline. What this Change proves is that both clients build and both satisfy every repository seam.

## Change C17 - Shared repository contract suites against real SQLite and Postgres - not started

### Discussion

- **The twelve existing SQL tests are SQLite-shaped in a way that will not survive.** Every Prisma adapter test and five `apps/http-server` route tests construct `PrismaBetterSqlite3` directly against a temp file and hand-apply migration SQL by splitting the file on `;`. That works only because SQLite migrations here are flat `CREATE TABLE`s with enums erased to `TEXT`; Postgres emits `CREATE TYPE ... AS ENUM` and the naive split stops being safe.
- **The duplication is the opportunity, not just the problem.** All twelve files carry the same 28-line `applySqlFile`/`applyMigrations` pair byte-for-byte — 336 duplicated lines that collapse into one harness. So the headline figure (3,691 lines across those files) badly overstates the churn: assertions largely move unchanged, and the total is as likely to shrink as grow.
- **This is where the repo-wide test-style question gets its first worked example.** A shared database harness has to be built here regardless, which makes it the cheapest available moment to establish the pattern against a real case rather than write a convention in the abstract. See the corresponding `docs/todo.md` entry; that broader review stays out of this arc.
- **Behavior assertions become provider-agnostic; setup and teardown stay provider-specific.** Database semantics are the thing this Change actually tests and the thing types cannot prove — transaction semantics, constraint and cascade behavior, collation and case sensitivity, timestamp precision, ordering of unordered queries, and error mapping.
- **Postgres joins `docker-compose.yml` and the CI integration job here**, alongside the existing MinIO and Redis services. Change C14's finding applies directly: any new environment variable must be added to `turbo.json`'s `test:integration` `env` array, or Turborepo strips it and the suite skips silently in CI while passing locally.

## Change C18 - Extend the `local-system` profile with the `postgres` SQL branch - not started

### Discussion

- **Less mechanical than the original scaffold assumed, because there is no config selection on this axis yet to extend.** `SqlConfig` is threaded through `LocalSystemConfig` and both app configs, but nothing reads it: `packages/db-prisma/src/client.ts` exports a module-global `prisma` constructed at import time from `DATABASE_URL`, and both the profile and its observability builder import it by deep relative path into `dist` rather than through the package export. So the first half of this Change is removing that singleton in favor of provider-specific client construction, and only then does Change C3's `buildArtifactStore` pattern apply.
- **Provider selection is per process, decided at composition, and is not hot-swappable.** One selected client instance is shared by every repository including observability's, which means `buildObservability()` receives repositories rather than importing the global itself. Connect, health check, and disconnect join the managed runtime lifecycle. Changing the configured backend does not move data between them.
- **`apps/http-server` and `apps/cli` still pick it up for free** once the branch exists, the same way they did for the CAS and messaging axes.
- **This is the Change that makes the arc count as a swappability proof.** Following the precedent set by Change C3 for MinIO and Change C14 for Redis, that means pointing an app config at Postgres, running a real flow end to end, confirming the data landed, and reverting the config afterward — a local edit rather than a permanent env-var branch.
